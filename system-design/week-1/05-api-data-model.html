API Design & Data Model

Week 1Design

Before drawing architecture boxes, define the contract (API) and the shape of the data (schema). This forces clarity — you can't design a good architecture around an API you haven't specified.

API design principles

  • Resource-oriented (REST): nouns, not verbs. POST /urls, not POST /createUrl.
  • Use HTTP methods correctly: GET (read, idempotent, cacheable), POST (create), PUT/PATCH (update — PUT replaces, PATCH partially updates), DELETE (remove).
  • Pagination on any list endpoint. Prefer cursor-based (?cursor=abc123&limit=20) over offset-based for large, frequently-changing datasets — offset pagination re-scans and can skip/duplicate items as data shifts.
  • Idempotency for writes: critical for POST/PUT under retries (client timeouts, network blips). Use an Idempotency-Key header so a retried request doesn't create a duplicate resource (e.g. double-charging a payment).
  • Versioning: /v1/... in the path or an Accept header, so you can evolve without breaking existing clients.
  • Rate limiting signaled via headers: X-RateLimit-Limit, X-RateLimit-Remaining, 429 Too Many Requests.
  • Consistent error format: a standard shape ({ "error": { "code", "message" } }) with correct HTTP status codes (400 bad input, 401/403 auth, 404 not found, 409 conflict, 429 rate-limited, 5xx server error).
REST vs gRPC vs GraphQL — quick take
REST: simple, cacheable, great for public/external APIs. gRPC: binary (protobuf), fast, strongly typed, ideal for internal service-to-service calls with strict schemas and streaming. GraphQL: client decides exactly what fields it needs in one round trip — great for complex, nested UI data (mobile apps hitting many entity types) but adds complexity around caching and query cost control.

Worked example: URL Shortener API

POST /v1/urls
Body: { "long_url": "https://example.com/very/long/path", "custom_alias": "optional", "ttl_days": 365 }
Response 201: { "short_code": "aZ3kD9", "short_url": "https://short.ly/aZ3kD9", "expires_at": "2027-08-08" }

GET /v1/urls/{short_code}
Response 302: redirect to long_url  (or 404 if not found/expired)

GET /v1/urls/{short_code}/stats
Response 200: { "clicks": 1204, "created_at": "...", "last_accessed": "..." }

DELETE /v1/urls/{short_code}
Response 204: no content

Data modeling

Two steps: identify entities and their relationships, then decide the physical schema based on access patterns (not just "what feels normalized").

1. Entity-relationship sketch

For a Twitter-like feed: User (1) —follows→ (many) User; User (1) —posts→ (many) Tweet; Tweet (1) —has→ (many) Like, Reply. Draw this before touching SQL/NoSQL — it's storage-agnostic.

Fig 2. Entity-relationship sketch for a Twitter-like feed.

2. Schema, driven by queries

In NoSQL/wide-column design especially, model for your read queries first, not for normalization. Ask "what's the most common query?" and design the partition/sort key to answer it in one lookup.

-- Relational schema (URL shortener)
CREATE TABLE urls (
  short_code   VARCHAR(10) PRIMARY KEY,
  long_url     TEXT NOT NULL,
  user_id      BIGINT REFERENCES users(id),
  created_at   TIMESTAMP DEFAULT now(),
  expires_at   TIMESTAMP,
  click_count  BIGINT DEFAULT 0
);
CREATE INDEX idx_urls_user_id ON urls(user_id);

-- Wide-column schema (chat messages, Cassandra-style)
-- Partition key = conversation_id → all messages for a chat live together
-- Clustering key = message_id (time-ordered, e.g. Snowflake ID) → naturally sorted for range scans
TABLE messages (
  conversation_id  UUID,
  message_id       BIGINT,   -- time-sortable ID
  sender_id        UUID,
  body             TEXT,
  sent_at          TIMESTAMP,
  PRIMARY KEY (conversation_id, message_id)
)
-- Query: "get last 50 messages in conversation X" is now a single, fast partition scan.

3. Generating unique, short, and scalable IDs

A recurring deep-dive: how do you generate short_code or message_id without a single point of contention?

  • Auto-increment / sequence: simple, but a single bottleneck and reveals volume/order — bad for multi-region.
  • UUID v4: globally unique, no coordination needed, but random (bad for DB index locality) and not sortable by time.
  • Snowflake-style IDs (Twitter's approach): 64-bit ID = timestamp + machine/shard ID + per-machine sequence number. Sortable by time, globally unique without central coordination, used everywhere in practice (Discord, Instagram adapted it too).
  • Base62 encoding of a counter: for URL shorteners specifically — take an incrementing 64-bit ID (from a distributed counter/range allocator) and encode it in base62 (a-z, A-Z, 0-9) to get a short, unique string like aZ3kD9.
Interview tip
When asked "how do you generate unique IDs at scale," Snowflake-style IDs are the strongest general answer — mention timestamp bits (sortability), shard/worker-ID bits (no coordination across machines), and sequence bits (multiple IDs per millisecond per machine).
