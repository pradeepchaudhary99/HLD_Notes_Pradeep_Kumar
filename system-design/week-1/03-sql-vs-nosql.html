SQL vs NoSQL — When and Why

Week 1Data Stores

This is one of the most-asked "justify your choice" questions in HLD interviews. The honest answer is almost never "NoSQL doesn't scale" or "SQL can't scale" — modern systems scale both. The real decision is about data shape, access patterns, and consistency needs.

Relational (SQL) databases

Examples: PostgreSQL, MySQL, SQL Server, Oracle.

  • Fixed schema with tables, rows, and typed columns, enforced at write time.
  • ACID transactions — Atomicity, Consistency, Isolation, Durability — across multiple rows/tables.
  • Joins are first-class, so relationships between entities (users, orders, products) are cheap to query.
  • Strong consistency by default (single primary), horizontal scaling needs extra work (read replicas, sharding, or tools like Vitess/Citus).

NoSQL databases

An umbrella term for four broad families — pick the one that matches your access pattern, not "NoSQL" as a single thing.

TypeExamplesBest for
Key-valueRedis, DynamoDB, MemcachedSimple lookups by ID: sessions, caches, feature flags
DocumentMongoDB, CouchbaseSemi-structured, nested data that changes shape often: user profiles, product catalogs, CMS content
Wide-columnCassandra, HBase, BigtableMassive write throughput, time-series, append-heavy data across many nodes
GraphNeo4j, NeptuneDeep relationship traversal: social graphs, recommendation engines, fraud detection
  • Flexible / schema-less — good when entities have varying or evolving shapes.
  • Horizontal scaling is native — most are built partition-first (consistent hashing across nodes).
  • Weaker transactional guarantees — typically no multi-document/multi-row ACID transactions (though modern MongoDB and DynamoDB have added limited support).
  • Usually AP in CAP terms — tunable consistency (e.g. Cassandra's quorum reads/writes) rather than strict by default.

Decision framework

Ask these questions in the interview
1. Do I need multi-row transactions (e.g. debit one account, credit another, atomically)? → SQL.
2. Is my data naturally tabular/relational with lots of joins? → SQL.
3. Is my write volume enormous and mostly append-only / time-ordered (metrics, logs, events)? → Wide-column NoSQL.
4. Does each record look different and evolve independently (user-generated content, catalogs)? → Document NoSQL.
5. Am I mostly doing simple key → value lookups at very high QPS with low latency? → Key-value store.
6. Is the core query "find things N hops away in a relationship graph"? → Graph DB.

Worked examples from common interview questions

SystemLikely choiceReasoning
URL ShortenerKey-value (or SQL for small scale)Simple short_code → long_url lookup, no relations needed
Instagram feed / postsSQL for user/relations + NoSQL/cache for feedFollow graph and metadata are relational; feed generation needs fast fan-out reads, often cached
Uber trip dataSQL (trip, payment) + wide-column (location pings)Payments need ACID; location pings are extremely high-volume time-series writes
WhatsApp messagesWide-column / document (e.g. Cassandra-like)Massive write throughput, mostly accessed by conversation_id + time range, no complex joins
E-commerce inventorySQLStock decrement must be atomic and consistent to avoid overselling
It's not either/or
Real systems are almost always polyglot persistence: SQL for the transactional core (users, orders, payments), a document/wide-column store for high-volume or flexible data, Redis for caching/sessions, Elasticsearch for search, and a graph DB for recommendations. In an interview, naming the right store per data type is a stronger signal than picking one database for everything.

NewSQL — the middle ground

Systems like Google Spanner, CockroachDB, and TiDB aim to give SQL semantics (schema, joins, ACID transactions) with horizontal scalability and strong consistency across regions, using synchronized clocks (TrueTime) or consensus protocols (Raft) under the hood. Worth name-dropping when the interviewer pushes on "but what if you need both scale AND transactions?"
