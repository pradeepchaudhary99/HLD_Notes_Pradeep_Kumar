Approaching an HLD Interview

Week 1Framework

A High-Level Design (HLD) interview isn't testing whether you know a specific "correct" architecture — it's testing whether you can take an ambiguous problem, scope it sensibly, and reason about trade-offs out loud. Interviewers at top product companies (Google, Amazon, Meta, Uber, etc.) are grading your process at least as much as your final diagram. This note gives you a repeatable framework you can apply to almost any "Design X" question — URL shortener, Instagram, WhatsApp, Uber, rate limiter, and so on.

Golden rule
Never jump straight to boxes and arrows. The candidates who fail HLD rounds almost always fail because they start designing before they've agreed with the interviewer on what they're designing.

The 6-step framework

1. Clarify requirements (5–7 minutes)

Split requirements into two buckets and say them out loud:

  • Functional requirements — what the system does. E.g. for a URL shortener: "users can shorten a URL, custom aliases are optional, shortened links redirect to the original, links can expire."
  • Non-functional requirements (NFRs) — the qualities the system must have: availability, latency, consistency, durability, scalability. These usually matter more for the design than the functional list.

Ask scoping questions to narrow an intentionally vague prompt:

  • What's the scale — number of users, requests/sec, data volume? (If not given, estimate it yourself in step 2.)
  • Read-heavy or write-heavy?
  • Do we need strong consistency anywhere, or is eventual consistency acceptable?
  • Is this a single-region or global system?
  • What's explicitly out of scope? (e.g., "let's skip analytics/ads for now and focus on the core read/write path")

2. Back-of-the-envelope estimation (5 minutes)

Convert requirements into numbers: QPS (read and write separately), storage growth per day/year, bandwidth, and peak-to-average ratios. This directly drives decisions later — e.g. 50K reads/sec tells you that you need a cache and probably read replicas; 500 writes/sec tells you a single relational primary might be fine for years. See the estimation note for the actual math.

3. Define the API / interface (3–5 minutes)

Write 3–6 core endpoints with request/response shape. This forces you to nail down the data model early and gives the interviewer a concrete contract to interrogate. See the API design note.

4. High-level architecture (10–15 minutes)

Now draw boxes. Start with the simplest thing that could work — client → load balancer → application servers → database — then layer in complexity only to solve a specific requirement you already identified:

  • Add a cache because reads are 100:1 vs writes.
  • Add a message queue because writes need to be decoupled from slow downstream work (e.g. sending notifications).
  • Add read replicas / sharding because a single DB node can't hold or serve the estimated volume.
  • Add a CDN because you're serving static/media content globally.

Narrate every box: what it does, why it's there, and what would break without it. This is the highest-signal part of the interview.

5. Deep dive into 1–2 components (10–15 minutes)

The interviewer will usually steer you here, but be ready to propose it yourself: "I'd like to go deeper into how we generate unique short codes at scale" or "let's dig into how we fan out a tweet to followers." This is where you show real depth — concurrency, failure handling, data partitioning, specific algorithms (e.g. consistent hashing, base62 encoding, leader election).

6. Address bottlenecks, failure modes, and trade-offs (5–10 minutes)

Proactively call out: single points of failure, hot partitions/celebrity problem, cache stampedes, retry storms, and how you'd monitor and roll out safely. Every design decision should come with a trade-off you considered and rejected — that's what "senior" signal looks like.

Time budget for a 45-minute interview

PhaseTime
Requirements & scoping5–7 min
Estimation5 min
API & data model5 min
High-level architecture12–15 min
Deep dive10–15 min
Wrap-up / trade-offs / Q&A5 min

Common mistakes

  • Silence. Think out loud, always. An interviewer can't grade a thought they can't hear.
  • Over-engineering early. Don't reach for Kafka + Cassandra + Kubernetes for a system doing 10 QPS. Justify every component with a number or requirement.
  • Ignoring the interviewer's hints. If they ask "what happens if this node dies?", that's a strong signal to talk about replication/failover right now, not later.
  • No opinions. When there are multiple valid options (SQL vs NoSQL, sync vs async), pick one, state your reasoning, and mention the alternative you rejected and why.
  • Skipping numbers. "It should scale well" is not an answer. "At 5K writes/sec we'll need to shard by user_id once a single Postgres primary saturates around ~10-15K TPS" is.
How to practice
Pick a well-known product every week (this is basically the syllabus of this course), give yourself 45 minutes, and force yourself through all 6 steps out loud — even alone. The framework becomes reflexive after 8–10 reps.
