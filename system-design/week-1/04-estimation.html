Back-of-Envelope Estimation

Week 1Math

Estimation converts a vague prompt ("design Twitter") into numbers that drive real decisions: whether you need a cache, whether one DB node is enough, whether you need sharding, how much this will cost. You don't need precision — you need the right order of magnitude.

Numbers worth memorizing

1 day~86,400 (~10⁵)
1 month~2.6 million
1 year~31.5 million (~3 × 10⁷)

Fig 1. The estimation funnel — each stage narrows the last into the number that actually drives architecture decisions.

The estimation checklist

  1. Users: total registered users → daily active users (DAU) → typically ~10–20% of total for a mature consumer app.
  2. Requests per user per day: how many times does a typical user perform the core action (post, read, search)?
  3. QPS (average): (DAU × actions per user per day) ÷ 86,400 seconds.
  4. Peak QPS: average QPS × peak factor (commonly 2–5×, since traffic isn't uniform across the day).
  5. Read:write ratio: most consumer apps are heavily read-skewed (100:1 or more) — this alone justifies caching.
  6. Storage per item and per day/year.
  7. Bandwidth: requests/sec × average payload size.

Worked example: URL Shortener

Assumptions
100M new short URLs created per month. Read:write ratio of 100:1 (people click links far more than they create them). Each URL record ≈ 500 bytes (short code, long URL, metadata, indexes). 
Writes/month  = 100,000,000
Writes/sec avg = 100,000,000 / 2,600,000 ≈ 38 writes/sec
Reads/sec avg  = 38 × 100 ≈ 3,800 reads/sec

Peak (assume 3x average):
  Peak writes ≈ 115/sec
  Peak reads  ≈ 11,400/sec

Storage:
  Per record ≈ 500 bytes
  Per month  = 100M × 500B = 50 GB/month
  Per year   ≈ 600 GB/year
  5-year storage ≈ 3 TB → fits comfortably on a single well-provisioned DB with room to spare;
  sharding is optional for storage, but the ~11K reads/sec at peak means you DEFINITELY want a cache
  (e.g. Redis) in front of the DB rather than hitting it directly.

Worked example: Chat app (WhatsApp-scale)

Assumptions
500M DAU, each sends 40 messages/day on average, average message size 100 bytes (text only; media handled separately via object storage + CDN). 
Messages/day = 500,000,000 × 40 = 20,000,000,000 (20B messages/day)
Messages/sec avg = 20,000,000,000 / 86,400 ≈ 231,000 msgs/sec
Peak (3x)         ≈ 700,000 msgs/sec

Storage/day = 20B × 100 bytes ≈ 2 TB/day (text only)
Storage/year ≈ 730 TB/year

Takeaways: this volume is IMPOSSIBLE for a single relational primary — you need
horizontal partitioning (shard by conversation_id or user_id), a wide-column /
log-structured store optimized for high write throughput, and message delivery
decoupled via queues per-connection (not synchronous DB writes on the hot path).
What the interviewer is actually grading
Not your arithmetic — your judgment about what the numbers imply. "3,800 reads/sec average, ~11K peak" should make you say "this justifies an in-memory cache in front of the database" out loud. If you compute numbers and then never refer to them again while drawing your architecture, you've wasted 5 minutes.

Rules of thumb

  • A single modern relational DB (well-tuned Postgres/MySQL) can typically handle low-thousands of writes/sec and tens of thousands of reads/sec with read replicas — beyond that, think caching, sharding, or a different store.
  • A single Redis instance can serve on the order of 100K+ simple ops/sec — it's rarely your bottleneck, but memory (RAM cost) is.
  • Round aggressively. 86,400 sec/day ≈ 10⁵ is a fine approximation for mental math.
  • Always sanity-check: does the peak QPS make sense given DAU? A number like "5M QPS for a 1M DAU app" should make you re-check your math.
