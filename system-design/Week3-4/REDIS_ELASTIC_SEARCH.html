1Redis Pub/Sub + ZADD Basics

Simulating seat state with sorted sets, broadcasting events with Pub/Sub

Terminal 1 — Subscriber (listens for booking events)

Terminal 1 
redis-cli
SUBSCRIBE seat_booking_channel

This blocks and waits for messages — leave it running for the whole demo.

Terminal 2 — Initialize seats in a sorted set

Terminal 2 
ZADD event:1001:seats 0 "A1" 0 "A2" 0 "A3" 0 "B1" 0 "B2"

Score 0 = available.

Check available seats

ZRANGEBYSCORE event:1001:seats 0 0

Lock a seat (score = lock timestamp)

ZADD event:1001:seats CH 1755763200 "A1"

CH returns the number of changed elements — useful to confirm the update actually happened.

Publish a lock event

PUBLISH seat_booking_channel "SEAT_LOCKED:A1:event:1001"

Confirm booking

ZADD event:1001:booked_seats 1755763200 "A1"
ZREM event:1001:seats "A1"
PUBLISH seat_booking_channel "SEAT_BOOKED:A1:event:1001"

Release seat if payment times out

ZSCORE event:1001:seats "A1"
ZADD event:1001:seats 0 "A1"
PUBLISH seat_booking_channel "SEAT_RELEASED:A1:event:1001"
Limitation: this timestamp-as-score approach needs a manual sweep to find stale locks. Section 2 fixes this properly with real TTL.

2TTL-Based Seat Locking (Refined)

The production-correct pattern — auto-expiring locks via key TTL, not manual sweeps

One-time setup — enable keyspace notifications

CONFIG SET notify-keyspace-events Ex

Ex = notify on key expired events.

Initialize seat inventory (score = status code)

ZADD event:1001:seats 0 "A1" 0 "A2" 0 "A3" 0 "B1" 0 "B2"
ScoreMeaning
0available
1locked
2booked

Terminal 1 — subscribe to lock expiry events

Terminal 1 
redis-cli
PSUBSCRIBE "__keyevent@0__:expired"

Terminal 2 — subscribe to app-level booking events

Terminal 2 
redis-cli
SUBSCRIBE seat_booking_channel

Terminal 3 — lock a seat atomically, 5-minute TTL

Terminal 3 
SET lock:event:1001:A1 "user:42" NX EX 300
FlagEffect
NXonly sets if the key doesn't exist — this is the atomic check-and-lock
EX 300auto-expires in 300 seconds

Reflect the lock + notify

ZADD event:1001:seats 1 "A1"
PUBLISH seat_booking_channel "SEAT_LOCKED:A1:user:42"

Confirm booking before TTL expires

DEL lock:event:1001:A1
ZADD event:1001:seats 2 "A1"
PUBLISH seat_booking_channel "SEAT_BOOKED:A1:user:42"

On timeout — no code needed, Terminal 1 fires automatically

pmessage __keyevent@0__:expired lock:event:1001:A1

Your app then runs cleanup:

ZADD event:1001:seats 0 "A1"
PUBLISH seat_booking_channel "SEAT_RELEASED:A1:expired"
Failure mode to flag: keyspace notifications are fire-and-forget. If the subscriber is down when a key expires, that event is lost and the seat map can go stale. Production systems add a periodic reconciliation job as a safety net.

3Seat Inventory Initialization

Where inventory really comes from — and when it gets loaded into Redis

Key point: Redis is a fast-access cache/index. The relational DB (Postgres/MySQL) is the source of truth. Redis gets pre-warmed at event-creation time — not when the first student clicks "view seat map."

Bulk populate (simulated — real systems pipeline this from app code)

redis-cli --pipe <

Guard against re-initializing a live sale

EXISTS event:1001:seats

Check before running init — never blindly overwrite in-progress locked/booked seats back to 0.

StrategyHowTrade-off
Eager (write-through)Populate Redis fully when event is publishedPredictable fast reads, costs memory upfront
Lazy (cache-aside)Populate only on first view, from DBSaves memory, but first request eats a cold-start DB read

High-traffic ticketing systems (BookMyShow/Ticketmaster-style) prefer eager init — avoids a DB read stampede when 50,000 people hit the page at sale-open.

4Redis → WebSocket Streaming Pattern

How live seat-map updates actually reach the browser

Redis PUBLISH → Backend WebSocket Server (subscriber) → Browser WebSocket ┌─────────────┐ Booking Service --> │ Redis │ PUBLISH seat_booking_channel │ (Pub/Sub) │ "SEAT_LOCKED:A1" └──────┬──────┘ │ SUBSCRIBE ▼ ┌─────────────────────┐ │ WS Server (Node/ │ │ Java/Go instance) │ └──────────┬──────────┘ │ fan-out to only │ clients watching event:1001 ┌────────────┼────────────┐ ▼ ▼ ▼ Browser A Browser B Browser C (watching (watching (watching event 1001) event 1001) event 2002)

Browsers can't speak the Redis protocol directly — the WebSocket server is always the bridge. Redis Pub/Sub is the cross-instance messaging bus that lets multiple horizontally-scaled WS server pods stay in sync.

Publish a structured event

PUBLISH seat_booking_channel '{"event_id":"1001","seat_id":"A1","status":"LOCKED","ts":1755763200}'

WS server fan-out logic

redisSubscriber.on('message', (channel, message) => {
  const data = JSON.parse(message);
  io.to(`event:${data.event_id}`).emit('seat_update', data);
});
Not durable: Pub/Sub messages are fire-and-forget. On WebSocket reconnect, the client should re-fetch full state via ZRANGE rather than trusting the incremental stream alone.

5Virtual Queue for High Demand

Throttling entry into the booking flow during a popular on-sale

Join the queue (score = arrival order)

ZADD event:1001:queue 1755763200.001 "user:42"
ZADD event:1001:queue 1755763200.002 "user:43"
ZADD event:1001:queue 1755763200.003 "user:44"

Get a user's position

ZRANK event:1001:queue "user:44"

Returns 0-indexed rank → O(log N), cheap even at massive scale.

Admission batch job — pop the front of the queue

ZPOPMIN event:1001:queue 100

Grant a TTL'd booking session + notify

SET session:event:1001:user:42 "active" NX EX 300
PUBLISH queue_channel:1001 '{"user_id":"42","status":"ADMITTED"}'
ApproachWhen used
Polling ZRANK every 5–10sCheap, scales to huge waiting crowds, slight staleness OK
WebSocket pushReserved for the critical "you're admitted" transition
SSE (Server-Sent Events)Lighter one-directional alternative to full WebSocket
Throttle to downstream capacity: admit on a fixed cadence matched to what the booking backend/DB can handle — not "admit everyone the instant they reach position zero."
Same resync pattern as before: if a WS server drops mid-session, the client could miss its "admitted" push. On reconnect, re-check status via REST (ZRANK + whether a session:* key exists) rather than trusting the push alone.

6Elasticsearch Query Cookbook

curl commands against a local Elasticsearch instance on localhost:9200

Cluster health check

curl 
curl -X GET "localhost:9200/_cluster/health?pretty"

1. Create an index with mapping

curl -X PUT "localhost:9200/products?pretty" -H 'Content-Type: application/json' -d'
{
  "mappings": {
    "properties": {
      "name":        { "type": "text" },
      "category":    { "type": "keyword" },
      "price":       { "type": "float" },
      "in_stock":    { "type": "boolean" },
      "rating":      { "type": "float" },
      "created_at":  { "type": "date" },
      "description": { "type": "text" }
    }
  }
}'

text = analyzed/tokenized for full-text search. keyword = exact match, used for filters/aggregations.

2. Index a single document

curl -X POST "localhost:9200/products/_doc/1?pretty" -H 'Content-Type: application/json' -d'
{
  "name": "Wireless Mechanical Keyboard",
  "category": "electronics",
  "price": 89.99,
  "in_stock": true,
  "rating": 4.5,
  "created_at": "2026-01-15",
  "description": "RGB backlit mechanical keyboard with hot-swappable switches"
}'

3. Bulk index multiple documents

curl -X POST "localhost:9200/_bulk?pretty" -H 'Content-Type: application/json' -d'
{ "index": { "_index": "products", "_id": "2" } }
{ "name": "USB-C Hub", "category": "electronics", "price": 34.99, "in_stock": true, "rating": 4.1, "created_at": "2026-02-01", "description": "7-in-1 USB-C hub with HDMI and card reader" }
{ "index": { "_index": "products", "_id": "3" } }
{ "name": "Standing Desk", "category": "furniture", "price": 349.00, "in_stock": false, "rating": 4.7, "created_at": "2026-01-20", "description": "Electric height-adjustable standing desk" }
{ "index": { "_index": "products", "_id": "4" } }
{ "name": "Mechanical Mouse", "category": "electronics", "price": 45.50, "in_stock": true, "rating": 3.9, "created_at": "2026-03-05", "description": "Ergonomic mechanical mouse with programmable buttons" }
'

Watch the trailing newline requirement in _bulk — each action line + doc line pair, no missing blank lines.

4. Full-text search — match

curl -X GET "localhost:9200/products/_search?pretty" -H 'Content-Type: application/json' -d'
{
  "query": {
    "match": { "description": "mechanical keyboard" }
  }
}'

5. Exact match — term (keyword fields)

curl -X GET "localhost:9200/products/_search?pretty" -H 'Content-Type: application/json' -d'
{
  "query": {
    "term": { "category": "electronics" }
  }
}'

6. Range query (price filter)

curl -X GET "localhost:9200/products/_search?pretty" -H 'Content-Type: application/json' -d'
{
  "query": {
    "range": { "price": { "gte": 30, "lte": 100 } }
  }
}'

7. Compound query — bool

curl -X GET "localhost:9200/products/_search?pretty" -H 'Content-Type: application/json' -d'
{
  "query": {
    "bool": {
      "must": [ { "match": { "description": "keyboard" } } ],
      "filter": [
        { "term": { "in_stock": true } },
        { "range": { "price": { "lte": 100 } } }
      ],
      "should": [ { "match": { "category": "electronics" } } ],
      "must_not": [ { "term": { "category": "furniture" } } ]
    }
  }
}'
ClauseRole
mustContributes to relevance score, required
filterRequired, score-neutral, cacheable/faster
shouldOptional, boosts score if matched
must_notExcludes matches

8. Aggregations — average price per category

curl -X GET "localhost:9200/products/_search?pretty" -H 'Content-Type: application/json' -d'
{
  "size": 0,
  "aggs": {
    "by_category": {
      "terms": { "field": "category" },
      "aggs": { "avg_price": { "avg": { "field": "price" } } }
    }
  }
}'

size: 0 = don't return raw docs, only aggregation buckets.

9. Sorting + pagination

curl -X GET "localhost:9200/products/_search?pretty" -H 'Content-Type: application/json' -d'
{
  "query": { "match_all": {} },
  "sort": [ { "rating": { "order": "desc" } } ],
  "from": 0,
  "size": 10
}'

10. Autocomplete — match_phrase_prefix

curl -X GET "localhost:9200/products/_search?pretty" -H 'Content-Type: application/json' -d'
{
  "query": {
    "match_phrase_prefix": { "name": "mechan" }
  }
}'

11. Fuzzy search (typo tolerance)

curl -X GET "localhost:9200/products/_search?pretty" -H 'Content-Type: application/json' -d'
{
  "query": {
    "fuzzy": {
      "name": { "value": "keybord", "fuzziness": "AUTO" }
    }
  }
}'

12. Partial update

curl -X POST "localhost:9200/products/_update/1?pretty" -H 'Content-Type: application/json' -d'
{
  "doc": { "price": 79.99, "in_stock": false }
}'

13. Delete a document

curl -X DELETE "localhost:9200/products/_doc/4?pretty"
HLD tie-in: Elasticsearch is a read-optimized search index, not the source of truth. Sync it from the primary DB via dual write (simple, but can drift) or CDC (Debezium/Kafka → ES — more resilient, eventually consistent).

7Docker: Running Elasticsearch + Kibana

Spin up a local ES cluster when nothing is installed natively

Single-node Elasticsearch (quickest for local testing)

docker 
docker run -d \
  --name elasticsearch \
  -p 9200:9200 -p 9300:9300 \
  -e "discovery.type=single-node" \
  -e "xpack.security.enabled=false" \
  -e "ES_JAVA_OPTS=-Xms512m -Xmx512m" \
  docker.elastic.co/elasticsearch/elasticsearch:8.15.0
FlagWhy
discovery.type=single-nodeSkips cluster formation, needed for local dev
xpack.security.enabled=falseDisables auth/TLS so curl works without credentials (local only, never prod)
ES_JAVA_OPTSCaps heap size so it doesn't hog your machine's RAM

Verify it's up

docker ps
curl -X GET "localhost:9200/_cluster/health?pretty"

Wait ~20–30 seconds after docker run before this returns healthy.

Optional: add Kibana for a visual query console

docker network create es-net

docker run -d \
  --name elasticsearch \
  --network es-net \
  -p 9200:9200 -p 9300:9300 \
  -e "discovery.type=single-node" \
  -e "xpack.security.enabled=false" \
  -e "ES_JAVA_OPTS=-Xms512m -Xmx512m" \
  docker.elastic.co/elasticsearch/elasticsearch:8.15.0

docker run -d \
  --name kibana \
  --network es-net \
  -p 5601:5601 \
  -e "ELASTICSEARCH_HOSTS=http://elasticsearch:9200" \
  docker.elastic.co/kibana/kibana:8.15.0

Open http://localhost:5601 → Dev Tools gives a query console, nicer than raw curl for live demos.

Docker Compose (reproducible for cohort teaching)

# docker-compose.yml
version: "3.8"
services:
  elasticsearch:
    image: docker.elastic.co/elasticsearch/elasticsearch:8.15.0
    container_name: elasticsearch
    environment:
      - discovery.type=single-node
      - xpack.security.enabled=false
      - ES_JAVA_OPTS=-Xms512m -Xmx512m
    ports:
      - "9200:9200"
      - "9300:9300"

  kibana:
    image: docker.elastic.co/kibana/kibana:8.15.0
    container_name: kibana
    environment:
      - ELASTICSEARCH_HOSTS=http://elasticsearch:9200
    ports:
      - "5601:5601"
    depends_on:
      - elasticsearch
docker-compose up -d
docker-compose logs -f elasticsearch

Cleanup

docker stop elasticsearch kibana
docker rm elasticsearch kibana
Once running, nothing else changes — all the curl -X GET "localhost:9200/..." commands from Section 6 work exactly as-is against the Dockerized instance.
