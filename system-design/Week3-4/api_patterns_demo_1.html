HTTP stateless

The base protocol everything below is built on
Definition

HTTP (HyperText Transfer Protocol) is the request/response protocol browsers and apps use to talk to servers over the internet. A client sends a request (method + URL + headers + optional body); the server sends back a status code and a response body. It's stateless — the server treats each request independently.

Everyday examples
  • 🌍 Typing a URL in your browser → an HTTP GET fetches the page
  • 🖼️ A webpage loading images/CSS/JS → each file is its own separate HTTP request
  • 📤 Submitting a login form → an HTTP POST with your credentials in the body
🧑‍💻
Client
🖥️
Server
Every HTTP exchange is a single request → single response. The client always speaks first; the server never contacts the client on its own. Once the response arrives, the logical exchange is done — Redis, REST, GraphQL, and even the WebSocket handshake below all start life as one of these.
Stateless means the server doesn't remember this request when the next one arrives — each call carries everything needed to understand it (headers, cookies, auth tokens). That's what makes plain HTTP a poor fit for "push me updates" — the server has no channel to reach back through.
▸ view client call (Java)
HttpClient client = HttpClient.newHttpClient();
HttpRequest req = HttpRequest.newBuilder()
    .uri(URI.create("https://api.example.com/hello"))
    .GET()
    .build();
HttpResponse<String> res = client.send(req, HttpResponse.BodyHandlers.ofString());
// res.statusCode() == 200, res.body() == {"message":"hi"}

REST API

HTTP, organized around resources and verbs
Definition

REST (REpresentational State Transfer) is a design style for building HTTP APIs around resources (nouns, like a seat or a booking) instead of custom actions. Each resource gets its own URL, and the HTTP verb (GET/POST/PATCH/DELETE) says what to do to it. Responses have a fixed shape per endpoint.

Everyday examples
  • 🐦 Twitter/X API — GET /tweets/{id}, POST /tweets
  • 🎟️ BookMyShow-style backend — GET /seats/A5, POST /bookings
  • 🌦️ A weather API — GET /weather?city=Bangalore returns current conditions
🧑‍💻

REST maps operations onto resources (nouns: seats, bookings) and HTTP verbs (the action). Each endpoint returns a fixed shape — GET /seats/A5 always returns the whole seat object, even if your screen only needed the status field. Need seat + movie + theater info together? That's 3 separate round trips. That over/under-fetching gap is exactly what GraphQL (next tab) fixes.
▸ view REST client (Java / Spring)
@GetMapping("/seats/{id}")
Seat getSeat(@PathVariable String id) {
    return seatRepository.findById(id);
}

@PostMapping("/bookings")
ResponseEntity<Booking> createBooking(@RequestBody BookingRequest req) {
    Booking b = bookingService.create(req);
    return ResponseEntity.status(201).body(b);
}

GraphQL

One endpoint, client chooses the exact shape
Definition

GraphQL is a query language for APIs where the client sends a single query describing exactly which fields it wants — including nested/related data — to one endpoint (usually /graphql). The server resolves the whole graph of data in one round trip and returns a response shaped exactly like the query. No over-fetching, no under-fetching.

Everyday examples
  • 📘 Facebook's API (GraphQL was created there) — fetch a post + its comments + author in one call
  • 🐙 GitHub's public GraphQL API — get a repo, its issues, and contributors together
  • 🛍️ Shopify's Storefront API — product + variants + pricing in a single query for a product page
🧑‍💻
Client
◈
/graphql
Query sent by the client: 
query {
  seat(id: "A5") {
    status
    movie { title }
    theater { name }
  }
}
One call to a single endpoint (/graphql) returns exactly the nested fields asked for — seat, movie title, and theater name together — the equivalent REST version needs 3 round trips (/seats/A5, /movies/{id}, /theaters/{id}). Fewer requests, no unused fields, but the server does more work per-request resolving that nested graph.
▸ view GraphQL client (Java)
String query = """
    query {
      seat(id: "A5") { status movie { title } theater { name } }
    }
""";
HttpRequest req = HttpRequest.newBuilder()
    .uri(URI.create("https://api.example.com/graphql"))
    .header("Content-Type", "application/json")
    .POST(HttpRequest.BodyPublishers.ofString(
        "{\"query\":\"" + query.replace("\n","") + "\"}"))
    .build();

WebSocket full-duplex

One handshake, then both sides push freely
Definition

WebSocket is a protocol that upgrades a single HTTP connection into a persistent, full-duplex channel — after the initial handshake, either the client or the server can send messages at any time without opening a new connection or waiting to be asked. It's the standard way to push real-time updates to a browser.

Everyday examples
  • 💬 WhatsApp Web / Slack — new messages appear instantly without refreshing
  • 📈 Live stock/crypto price tickers updating every second
  • 🎟️ A live movie seat map — seats turning grey the moment someone else holds them
🧑‍💻
Client
🖥️
Server
The connection starts as a normal HTTP request with Upgrade: websocket. If the server agrees (101 Switching Protocols), that same TCP connection stays open and both sides can send messages whenever they want — no new request needed, no polling. This is how live seat maps, chat, and stock tickers push instantly.
Trade-off: the server now has to hold that connection open per client (memory/resources), and if the connection drops, both sides have to notice and reconnect — unlike stateless HTTP where a dropped request just... didn't happen.
▸ view WebSocket handler (Java / Spring)
@Component
class SeatMapSocketHandler extends TextWebSocketHandler {

    @Override
    void handleTextMessage(WebSocketSession session, TextMessage msg) {
        // client -> server message arrives here anytime, no new request
    }

    void pushSeatUpdate(WebSocketSession session, String seatId, String status) {
        session.sendMessage(new TextMessage(
            "{\"seat\":\""+seatId+"\",\"status\":\""+status+"\"}"));
        // server pushed unprompted — client never asked for this specific message
    }
}

Webhook server → server push

A regular HTTP POST, but THEY call YOU
Definition

A webhook is just an HTTP POST request — but the calling direction is flipped. You register a URL with another service ahead of time; when their event happens, they call you, instead of you repeatedly polling them to ask "anything new?" It's "don't call us, we'll call you" as an API pattern.

Everyday examples
  • 💳 Stripe/Razorpay calling your server the moment a payment succeeds or fails
  • 🐙 GitHub calling your CI server when someone pushes code or opens a PR
  • 📬 A shipping provider (like Delhivery/FedEx) notifying your backend when a package status changes
💳
Payment Provider
🖥️
Your Server
You give the provider a URL upfront: https://yourapp.com/webhooks/payment. Later, when their event happens, they open the HTTP connection and POST the event to you — the direction is flipped compared to every tab before this one. Your server's only job is to respond fast with 200 OK to acknowledge receipt.
The alternative is polling: your server calling GET /payments/{id}/status every few seconds asking "done yet?" — wasteful and slower to notice. A webhook flips that into a single push exactly when it matters. It's still plain HTTP underneath — the pattern is just who initiates.
▸ view webhook receiver (Java / Spring)
@PostMapping("/webhooks/payment")
ResponseEntity<Void> onPaymentEvent(
        @RequestBody String payload,
        @RequestHeader("X-Signature") String signature) {

    if (!verifySignature(payload, signature)) {
        return ResponseEntity.status(401).build(); // reject forged calls
    }
    eventQueue.enqueue(payload);      // process async, respond fast
    return ResponseEntity.ok().build();   // 200 = "got it, thanks"
}

Stateful vs Stateless

Does the server remember you between requests?
Definition

Stateless means the server keeps no memory of previous requests — every request must carry everything needed to understand it (auth token, params, etc). Any server instance can handle any request, which makes stateless systems trivial to scale horizontally.

Stateful means the server remembers context from earlier requests (usually in a session), so later requests can be lighter — but that memory has to live somewhere, and it ties the client to whichever server (or shared store) holds it.

Everyday examples
  • 🌐 Stateless: a plain REST API using JWT tokens — each request re-sends the token, no server-side memory needed
  • 🛒 Stateful: a classic e-commerce session — server remembers your cart via a session ID after login
  • 🎮 Stateful: a multiplayer game server holding live player position in memory between moves
  • 🔑 Stateless-ish: Redis-backed sessions — server code stays stateless, but session data is remembered in a shared store (Redis) instead of one server's RAM

Watch the size of what the client has to send: in the stateless flow, the full auth token is re-sent on every single request because the server forgets everything the moment it responds. In the stateful flow, the credentials are sent once at login — after that, a small session ID cookie is enough because the server (or a shared store like Redis) is holding the context in between.
Trade-off: stateless is easier to scale — spin up 100 identical servers, any of them can handle any request. Stateful needs "sticky sessions" (always routing a client back to the same server) or a shared session store so every server instance can see the same state — which is exactly the kind of problem the Redis ZSET/lock pattern from earlier is used to solve.
