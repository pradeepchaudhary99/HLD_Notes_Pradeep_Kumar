System Design · Interview-Grade HLD

Design a Movie / Event
Ticketing Platform

A Ticketmaster / BookMyShow-style system: browse shows, pick seats on a live seat map, hold them, pay, and walk away with a confirmed booking — without ever double-selling a seat, even when 200,000 people hit "Buy" for the same show in the same minute.

Core hard problem: seat inventory contention
Consistency model: strong, per-show
Companion code: seat_lock.py
01

Problem Framing

Strip away the movie-poster UI and this is an inventory system with a deadline. Every show has a fixed, small pool of seats. Demand for popular shows can spike 50–100x baseline within seconds of going on sale. The system has to let a user browse and decide unhurried, but the moment they touch a seat, it has to behave like a bank ledger: exactly one owner, ever, per seat.

That tension — relaxed, cacheable reads vs. strict, serialized writes on a tiny hot key — is the whole design problem. Everything else (search, recommendations, notifications, payments) is standard e-commerce plumbing bolted around that core.

The framing that unlocks the design
A seat can only ever contend with other requests for the same show. A seat in Screen 4 of a Bengaluru multiplex never competes with a seat in a Mumbai stadium concert. That means the famous "hot show" problem is embarrassingly parallel across shows — we don't need one giant globally-consistent store, we need many small, strongly-consistent shards, one per show (or per venue-day), and horizontal scale falls out for free.

03

Functional & Non-Functional Requirements

Functional

  • Search/browse movies & events by city, date, venue
  • View showtimes and a live seat map per show
  • Hold selected seats for a short checkout window
  • Pay and receive a confirmed booking + e-ticket (QR code)
  • Cancel a booking / trigger refund
  • Notify user (confirmation, reminder, cancellation)
  • Admin: publish shows, configure venues & pricing

Non-Functional

  • Correctness over speed on writes — zero double-booking, ever
  • Strong consistency scoped to a single seat/show
  • Low read latency — search/browse is 100–1000x more frequent than booking
  • Elastic scale — absorb 50–100x spikes for minutes at a time
  • High availability for browse, even if booking briefly queues
  • Durability — a confirmed booking must never be lost
  • Fairness — first-come-first-served under load, not "whoever retries hardest"
The CAP framing to say out loud in an interview
For the seat inventory write path we deliberately choose CP (consistency over availability) at the shard level — better to briefly reject a hold than double-sell a seat. For the catalog/search read path we choose AP — a seat map that's 2 seconds stale is a fine UX trade-off; a booking that silently fails is not.

This reframes "handle the flash sale" from a database scaling problem into an admission-control and caching problem.

API Design

GET/events?city=blr&date=2026-08-15&q=inception
Search movies/events. Cache-friendly, served from search index, not the booking DB.
GET/events/{eventId}/shows?date=2026-08-15
List showtimes across venues for a given event/date.
GET/shows/{showId}/seatmap
Layout + current per-seat status (available/held/booked). Cached, eventually consistent (~1–2s staleness acceptable).
POST/shows/{showId}/holds  { seatIds: [...], userId }
Attempt to soft-lock seats for the checkout window (default 8 min TTL). Returns a holdId + fencing token per seat, or 409 for unavailable seats. Idempotency-Key header required.
DELETE/holds/{holdId}
Explicit release (user abandons checkout). Also auto-expires via TTL.
POST/bookings  { holdId, paymentToken }
Confirms payment and converts a valid, unexpired hold into a durable booking. Idempotent — safe to retry on client timeout.
POST/bookings/{bookingId}/cancel
Triggers refund workflow, releases seats back to inventory (or resale pool).
GET/waiting-room/{showId}/token  →  GET/waiting-room/status?token=…
For flash-sale shows: issues a queue position token and polls for admission — see §8.
Why hold is a separate step from booking
Splitting "reserve" from "pay & confirm" is what makes the payment gateway's unpredictable latency (2–30s, sometimes minutes with 3DS/OTP) a non-issue for inventory correctness. The seat is safely parked under a fencing token the moment the user picks it; the payment step only needs to prove it still holds a valid token.

Data Modeling

The interview-losing move here is reflexively reaching for "NoSQL because it scales." The stronger move is reasoning per entity, from its actual access pattern and consistency need:

EntityStoreWhy
Seat Inventory (show_id, seat_id → state, token, expiry)Relational (Postgres), sharded by show_idNeeds atomic compare-and-swap semantics (§8). Low cardinality per shard (hundreds of rows). ACID transactions are cheap at this scale and remove an entire class of correctness bugs.
Catalog (movies, venues, showtimes)Elasticsearch + Postgres source-of-truthRead-heavy, filter/facet/geo queries, tolerant of a few seconds of staleness. ES is the query engine; Postgres is the durable write path feeding it via CDC.
Bookings (confirmed orders)Relational, sharded by user_id or booking date rangeNeeds durability + transactional writes with payment, but no cross-show contention — shards purely for scale, not correctness.
Seat map cache (denormalized, for rendering)RedisRead-dominant, regenerated on every state change, short TTL fallback.
Sessions / waiting-room queueRedis (sorted sets)Ephemeral, high-churn, ordering matters (queue position) — a perfect fit for Redis's data structures, no durability requirement beyond the sale window.
Notifications / analytics eventsKafka → wide-column store (Cassandra) / warehouseAppend-only, massive volume, no update-in-place, read patterns are batch/analytical — this is where NoSQL genuinely wins.
Weak answer
"I'd use NoSQL like DynamoDB for everything since it scales better than SQL."
Strong answer
"Seat inventory needs linearizable read-modify-write per row and has tiny cardinality per shard — Postgres sharded by show_id gives me that for free and scales horizontally because shows don't share rows. Catalog is read-heavy and schema-flexible, so it's Elasticsearch. I pick the store per access pattern, not by default."

Core Schema (seat inventory shard)

-- one physical/logical shard per show_id (or show_id range)
CREATE TABLE seat_inventory (
  show_id      BIGINT      NOT NULL,
  seat_id      VARCHAR(8)  NOT NULL,
  state        SMALLINT    NOT NULL DEFAULT 0,  -- 0=available 1=held 2=booked
  hold_token   VARCHAR(64),
  held_by      BIGINT,
  version      INT         NOT NULL DEFAULT 0,  -- fencing counter
  expires_at   TIMESTAMPTZ,
  PRIMARY KEY (show_id, seat_id)
);
-- CAS hold: only succeeds if row is available OR its hold has expired
UPDATE seat_inventory
   SET state=1, hold_token=$new_token, held_by=$user, version=version+1,
       expires_at=now() + interval '8 minutes'
 WHERE show_id=$show AND seat_id=$seat
   AND (state=0 OR (state=1 AND expires_at < now()));
-- CAS confirm: only succeeds if the caller's token is still current
UPDATE seat_inventory
   SET state=2
 WHERE show_id=$show AND seat_id=$seat
   AND hold_token=$token AND expires_at >= now();

Architecture — Built Incrementally

Interview signal comes from showing why each stage stops working, not jumping straight to microservices.

Stage 1 — Monolith, single DB

Seat booking = one DB transaction. Works fine until concurrent traffic on a hot show and read traffic both hammer the same DB.

Breaks when: browse traffic (reads) and seat-hold traffic (writes) compete for the same connection pool and row locks — a viral show's read spike starves the booking path even though reads and writes aren't logically related.

Stage 2 — Split reads from writes, add caching

Read path (search/seat-map) hits cache + replicas. Write path (holds/bookings) still goes straight to primary — isolated from read load.

Breaks when: a single show goes viral — thousands of hold attempts per second on the same tiny set of DB rows. Row-lock contention on one show, cache stampede on seat-map reads, and no protection against bot/scalper traffic.

Stage 3 — Shard the hot path, add async settlement

A virtual waiting room throttles admission into the booking flow for hot shows. Redis provides a fast-path lock in front of the Postgres source of truth. A saga-based orchestrator sequences hold → pay → confirm with compensation on failure.

Breaks when: we now need this to work identically for 8,000 shows/day across many venues and regions, with observability, independent scaling of catalog vs. inventory vs. payments, and resilience to any single component failing mid-sale.

Stage 4 — Final design

Every box scales independently. Seat contention is contained to the Seat Inventory shard for one show — the rest of the system just routes and waits.

08

Component Deep Dives

8.1 — Seat Inventory & the Hold/Confirm Protocol

This is the component that decides whether the interview goes well. The protocol, end to end:

  1. Hold: client requests seats → CAS write on seat_inventory (or a Redis-fronted equivalent) sets state to HELD, stamps a monotonically increasing fencing token, and an 8-minute TTL. Fails fast (409) if the seat is already held/booked.
  2. Checkout: user enters payment; system has already reserved the seat, so payment gateway latency doesn't block anyone else.
  3. Confirm: booking service calls confirm with the same token issued at hold time. The DB only accepts the write if the token still matches and hasn't expired — this is the fencing mechanism that defeats the classic "stale worker" bug (a delayed payment webhook can never steal a seat that has since been re-issued to someone else).
  4. Expiry: unconfirmed holds revert to AVAILABLE either lazily (checked on next hold attempt) or via a background reaper — never blocking the hot path on cleanup.
Redis vs. DB lock — why both
Redis (SET NX PX) gives sub-millisecond lock acquisition for the hot path and absorbs burst QPS. But Redis alone risks losing a lock on failover. The pattern used here: Redis is the fast-path optimistic gate (reject obviously-taken seats instantly, protect the DB from thundering-herd writes), while Postgres with the fencing-token CAS is the durable source of truth that makes the final call. Losing the Redis node degrades performance, not correctness.

8.2 — Virtual Waiting Room

The actual mechanism Ticketmaster uses for major on-sales. When traffic to a show crosses a threshold, new arrivals get a queue token (Redis sorted set, score = arrival time) instead of hitting the booking flow directly. A background admitter releases N tokens/second into the real booking flow — N tuned to what the seat-inventory shard and payment gateway can sustain. Clients poll /waiting-room/status and get a live position estimate.

This turns an uncontrolled thundering herd into a controlled, fair, rate-limited stream — protecting every downstream service without needing any of them to be infinitely scalable.

8.3 — Booking Orchestrator (Saga)

Hold → Pay → Confirm spans three services (inventory, payment, booking) that can't share a single ACID transaction. Modeled as a saga with compensation:

StepForward actionCompensation on failure
1Place hold on seats—
2Charge payment (idempotency key = holdId)Release hold if charge fails/times out
3Write confirmed booking rowRefund payment if booking write fails
4Emit booking.confirmed eventN/A — booking already durable at this point

8.4 — Search / Catalog

Elasticsearch indexed off a CDC stream from the Postgres catalog (Debezium-style), so writes to shows/pricing/venues never touch the read-serving path directly. Geo + facet queries (city, date, genre, language) live entirely here; strong consistency isn't needed — a newly published show appearing 2 seconds later in search is invisible to users.

8.5 — Optimistic vs. Pessimistic Locking, in Full

Every "how do you prevent double-booking" answer eventually has to pick a locking strategy for the actual row update. The two options aren't interchangeable — they trade off differently under contention, and a real system typically uses both, in different parts of the flow.

Optimistic locking

Don't lock anything up front. Read the row, do your work in memory, then write back a conditional update that only succeeds if nothing changed underneath you (checked via a version number, or the row's current state). If the condition fails, someone else won — retry or fail fast. No lock is ever held across application logic or network calls.

Pessimistic locking

Acquire a real row-level lock before reading, inside a transaction (SELECT ... FOR UPDATE). Every other transaction wanting that row blocks until you commit or roll back. Simple to reason about, but the lock is held for the full duration of your transaction — including any slow application logic in between.

Optimistic — SQL (this is what §6/§8.1's fencing-token CAS already is)

-- no lock acquired; read is a plain SELECT, can even be read-committed / snapshot
SELECT state, version, expires_at FROM seat_inventory
 WHERE show_id = $1 AND seat_id = $2;

-- application checks state == AVAILABLE in memory, then issues:
UPDATE seat_inventory
   SET state = 1, hold_token = $new_token, held_by = $user,
       version = version + 1, expires_at = now() + interval '8 minutes'
 WHERE show_id = $1 AND seat_id = $2
   AND version = $version_read_earlier;      -- CAS guard: 0 rows updated = someone else won

-- driver/ORM checks rows-affected; 0 rows = OptimisticLockException / retry

Pessimistic — SQL (row lock held for the whole transaction)

-- lock acquired the instant this runs; other transactions on this row now block
BEGIN;

SELECT state, expires_at FROM seat_inventory
 WHERE show_id = $1 AND seat_id = $2
   FOR UPDATE;                                -- blocking row lock

-- application checks state == AVAILABLE, still holding the lock
UPDATE seat_inventory
   SET state = 1, hold_token = $token, held_by = $user,
       expires_at = now() + interval '8 minutes'
 WHERE show_id = $1 AND seat_id = $2;

COMMIT;                                        -- lock released only here

-- multi-seat booking (group of 4): lock ALL seats in one transaction,
-- in a FIXED, deterministic order — otherwise two users booking the
-- same 2 seats in opposite order deadlock each other
BEGIN;
SELECT * FROM seat_inventory
 WHERE show_id = $1 AND seat_id = ANY($seat_ids)
 ORDER BY seat_id                              -- deterministic lock order = no deadlock
   FOR UPDATE;
-- ... validate all 4 are AVAILABLE, then UPDATE all 4 ...
COMMIT;

Code changes needed — optimistic (Java / Spring Data JPA)

// 1. Add a @Version column — JPA auto-generates the CAS UPDATE + version bump
@Entity
class SeatInventory {
    @Id Long id;
    Long showId;
    String seatId;
    Integer state;
    String holdToken;
    @Version Long version;      // this one annotation is the entire mechanism
}

// 2. Catch the failure and turn it into a client-facing 409, don't silently retry
@Transactional
void holdSeatOptimistic(Long showId, String seatId, Long userId) {
    SeatInventory seat = repo.findByShowIdAndSeatId(showId, seatId);
    if (seat.getState() != AVAILABLE)
        throw new SeatUnavailableException(seatId);
    seat.setState(HELD);
    seat.setHoldToken(newToken());
    try {
        repo.saveAndFlush(seat);              // fires the version-guarded UPDATE
    } catch (OptimisticLockingFailureException e) {
        throw new SeatConflictException(seatId);  // -> HTTP 409, client re-reads seat map
    }
}

Code changes needed — pessimistic (Java / Spring Data JPA)

// 1. Request a PESSIMISTIC_WRITE lock hint on the query — JPA turns this into FOR UPDATE
interface SeatInventoryRepository extends JpaRepository<SeatInventory, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select s from SeatInventory s where s.showId=:showId and s.seatId in :seatIds order by s.seatId")
    List<SeatInventory> lockForHold(@Param("showId") Long showId,
                                     @Param("seatIds") List<String> seatIds);
}

// 2. The transaction now holds real row locks for its full duration —
//    keep it SHORT, and never call an external service (payment!) while inside it
@Transactional
void holdSeatsPessimistic(Long showId, List<String> seatIds, Long userId) {
    List<SeatInventory> seats = repo.lockForHold(showId, seatIds);   // blocks here if contended
    for (SeatInventory s : seats) {
        if (s.getState() != AVAILABLE) throw new SeatUnavailableException(s.getSeatId());
    }
    seats.forEach(s -> { s.setState(HELD); s.setHoldToken(newToken()); });
    // commit on method exit releases every lock at once
}

Why this design uses both, not one or the other
The hold step (§8.1) is optimistic — CAS on a single row, because contention on a specific seat is rare and the system must reject fast rather than make 5,000 concurrent buyers queue behind a DB lock. The group-booking confirm step, which must atomically flip 2–8 seats from HELD to BOOKED as one unit, is where a short-lived pessimistic transaction (FOR UPDATE ... ORDER BY seat_id) is the simpler correct answer — the seats are already reserved by this point (low contention), and "all seats confirm or none do" is naturally a transaction, not a per-row CAS loop with manual rollback.

Trade-off Analysis

Shard by show_id (chosen)

✓ Contention is naturally bounded per shard
✓ Horizontal scale is linear with number of shows
✓ Simple CAS semantics, no distributed transactions
✗ A single mega-event (one show, 50k+ seats/GA) can still create a hot shard — needs sub-sharding by seat range as an escape hatch

Single global inventory table

✓ Simpler mental model, one place to look
✗ Every hot show contends for the same lock manager / connection pool as every other show
✗ Scaling requires scaling the whole table, not just the hot part — rejected

Soft hold + fencing token (chosen)

✓ Decouples slow payment latency from inventory correctness
✓ Survives delayed/duplicate webhooks safely
✗ Adds a TTL-management + reaper responsibility

Pessimistic DB lock held through payment

✓ Conceptually simpler
✗ Holds a row lock (or connection) for the entire payment round-trip (seconds to minutes with 3DS) — catastrophic under load, rejected

Virtual waiting room for hot shows

✓ Predictable, bounded load on every downstream service
✓ Fair, transparent UX (queue position)
✗ Extra hop/latency for the (common) non-hot-show case — only engage it above a traffic threshold

No admission control, scale everything to peak

✓ Simpler, no queue UX
✗ Requires provisioning (and paying for) 50-100x baseline capacity that sits idle 99% of the time — rejected on cost + still doesn't bound DB contention

Failure Handling

  • Hold expires mid-payment: confirm() rejects with the fencing-token check; client is shown "seats released, please retry" rather than silently succeeding into a race.
  • Payment succeeds but confirm-write fails (DB blip): orchestrator retries the write (idempotent on holdId); if it still fails after backoff, auto-refund and notify the user — never leave a charged-but-unbooked state.
  • Duplicate client retries (network timeout, user double-clicks Pay): every write is idempotent via an Idempotency-Key, so retries are safe no-ops on the second call.
  • Redis node failure: fast-path gate degrades to "always ask Postgres" — slower, still correct, because Postgres CAS is the real source of truth.
  • Payment gateway down: circuit breaker trips, holds are extended (grace TTL) rather than expired, user sees "payment temporarily unavailable, your seats are safe."
  • One shard/DB partition down: only shows on that shard are affected — browse and booking for every other show continues unaffected (this is the payoff of sharding by show_id).
12

Security

  • AuthN/AuthZ: OAuth2/JWT for user sessions; booking mutation endpoints require a valid session tied to the holdId's owner.
  • Payment data: never touch raw card data — tokenize via PSP (PCI-DSS scope stays with the PSP, not us).
  • Bot/scalper mitigation: per-account purchase caps, device fingerprinting, CAPTCHA at waiting-room entry for hot shows, rate limiting on hold attempts per user/IP.
  • Idempotency keys double as light replay protection on mutating endpoints.
  • Ticket integrity: signed QR codes (short-lived signature) to prevent forged/duplicated e-tickets at venue entry.
  • Admin surfaces (publishing shows, pricing) behind separate RBAC-gated internal APIs, not the public gateway.
13

Observability

  • Per-show dashboards auto-created when a show crosses a traffic threshold: hold success rate, hold→confirm conversion, waiting-room queue depth & drain rate.
  • Golden signals per service: latency (p50/p99), error rate, saturation (DB connections, Redis memory), traffic.
  • Distributed tracing across the saga (hold → pay → confirm) with a single correlation ID, so a stuck booking can be traced across 3+ services in one view.
  • Alerting on: hold-rejection rate spike (contention or a stuck reaper), payment success-rate drop, waiting-room admit-rate falling behind arrival-rate (queue growing unbounded).
  • Business metric, not just infra: "seats sold / seats available" in real time per show — the number that actually matters to the business during a launch.

Cross-Questions & Weak vs. Strong Answers

"How exactly do you prevent double-booking under high concurrency?"

Weak
"I'd put a lock on the seat before someone books it."
Strong
"A compare-and-swap write scoped to (show_id, seat_id), guarded by a monotonic fencing token issued at hold time. Confirm only succeeds if the token is still current and unexpired — so even a delayed retry or stale worker physically cannot overwrite a newer hold. Redis in front absorbs burst QPS; Postgres CAS is the correctness guarantee."

"Why not just use DynamoDB/Cassandra for seats — isn't NoSQL better at scale?"

Weak
"NoSQL scales better than SQL, so it's the better choice."
Strong
"Scale here isn't about total data volume — a show has ~150–50,000 rows. It's about correctness under concurrent writes to the same few rows, which needs linearizable read-modify-write. A relational store sharded by show_id gives that for free, and horizontal scale comes from partitioning by show rather than from the storage engine — so the SQL-vs-NoSQL scaling argument doesn't even apply here."

"How do you handle a global-tour-level flash sale — millions of people, one show?"

Weak
"Just add more servers and a bigger database."
Strong
"Recognize that write volume is capped by seat count regardless of how many people show up — the real problem is read volume and fairness. A virtual waiting room admits users at a controlled rate into the booking flow; the seat shard never sees more concurrent writers than the admission rate allows. This converts an unbounded problem into a bounded, tunable one."

"What happens if the payment succeeds but your confirm-booking write fails right after?"

Weak
"That shouldn't really happen."
Strong
"It will happen at scale. The orchestrator retries the confirm write idempotently (keyed on holdId); if retries exhaust, it triggers an automatic refund and notifies the user rather than leaving a charged-but-unbooked state — the saga's compensation path exists precisely for this."

"Your seat map shows a seat as available, but it's actually just been held by someone else in checkout. Isn't that a bug?"

Weak
"That's a bug, the seat map should always be accurate."
Strong
"That's an intentional, bounded staleness — the seat-map read path is AP by design (§3), refreshed every 1-2s or via push. The correctness guarantee lives entirely in the write path's CAS check at hold time: worst case, a user selects a seat that's just been taken and gets an immediate, clear 409 — never a silent double-booking."

"A user double-clicks 'Select Seat' — does that fire two concurrent hold requests for the same seat from the same person?"

Weak
"The frontend should just disable the button after one click."
Strong
"UI debouncing is a nice-to-have, never the guarantee. Both requests race into the same CAS UPDATE; only one gets state=0 → 1 (rows_affected=1), the other sees rows_affected=0 and is told 'already held' — by the same fencing check that stops a stranger, since the DB doesn't distinguish 'your other tab' from another user at the row level. The client should also send an Idempotency-Key per attempt so an identical retry after a timeout doesn't even reach the CAS twice."

"User holds 4 seats for a group booking, pays, but the confirm transaction fails after seat 2 of 4 — do they end up with a half-confirmed booking?"

Weak
"We'd confirm each seat one at a time and hope they all go through."
Strong
"Never loop individual CAS updates for a group booking — that's exactly how you get 2-of-4 confirmed. The confirm step locks all 4 rows pessimistically in one transaction (SELECT ... FOR UPDATE ... ORDER BY seat_id, §8.5), flips all 4 to BOOKED, and commits atomically. If any row fails validation (e.g. one hold already expired), the whole transaction rolls back — the user keeps their other 3 holds (if still unexpired) and sees exactly which seat failed, not a partial booking."

"A seat's hold TTL expires at the exact millisecond the confirm request arrives — which one wins?"

Weak
"We'd need very precise clocks to handle that correctly."
Strong
"No clock precision needed — the DB is the single arbiter. Confirm's CAS is WHERE hold_token=$token AND expires_at >= now(), evaluated atomically inside one statement against Postgres's own clock at execution time. Either the row still has an unexpired matching token and confirm wins, or it doesn't and confirm is rejected with 'hold expired, please retry' — there's no window where both the reaper and the confirm can act on stale state, because whichever executes first wins the row and the second sees updated data."

"What stops a user from opening 10 browser tabs (or fake accounts) to hold way more seats than allowed?"

Weak
"We'd limit one hold per session."
Strong
"Session-scoped limits are trivial to bypass with incognito tabs or new accounts. The real control is a per-user-identity purchase cap enforced server-side at hold time (count active holds + confirmed bookings for that user_id across the show, reject the 11th), backed by device fingerprinting and rate limiting per IP to catch the multi-account case (§12). It's defense in depth, not a single check — no single signal fully stops a determined scalper, but stacking them raises the cost enough to matter."

"Your booking is General Admission (no seat numbers, just a headcount) — does the same CAS pattern still prevent overselling?"

Weak
"We'd just decrement a counter for each ticket sold."
Strong
"A plain decrement race-conditions under concurrency — 'read counter, subtract, write' loses updates the same way a naive seat check does. The fix is the same CAS discipline applied to a counter row: UPDATE ga_inventory SET sold = sold + $qty WHERE show_id=$1 AND sold + $qty <= capacity in one atomic statement — the WHERE clause is the inventory check and the write in a single round trip, so two concurrent buyers can't both read '5 left' and both succeed in buying 5. GA is a simplification of the seat-level model (§2), not a different one — a single row instead of one row per seat."

"The Redis fast-path lock says a seat is free, but Postgres — the actual source of truth — still shows it as HELD. How does that get resolved?"

Weak
"That shouldn't happen since Redis and Postgres are kept in sync."
Strong
"They're allowed to disagree briefly — Redis is a cache/gate, not a second source of truth (§8.1), so this isn't a consistency violation, it's an expected transient state. If Redis says available, the request still proceeds to the Postgres CAS, which is the actual authority and will correctly reject it if the row is still HELD there — worst case, Redis being stale costs one wasted round trip to Postgres, never a double-booking. This is precisely why the design never lets Redis alone authorize a booking."
