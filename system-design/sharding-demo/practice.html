Database Sharding — Hands-on Practice Lab

Take one logical database and split its rows across 3 real Postgres instances. You run the router, watch queries get routed, and feel the trade-offs first-hand.

Time: ~30 min  •  You need: a terminal, Docker Desktop, and the sharding-demo folder. Everything runs locally. Nothing touches the internet after the first image download.

i What you'll build

app code | v +---------------+ shard_of(user_id) = md5(user_id) % 3 | shard.py | <-- the ONLY thing that knows sharding exists +--+----+----+--+ | | | shard0 shard1 shard2 <-- 3 plain Postgres 16 containers :5433 :5434 :5435 each holds a DISJOINT set of users
  • 3 shards = 3 separate Postgres containers. None of them knows the others exist.
  • The shard key is user_id. A user and all their orders always live on the same shard.
  • The routing rule is md5(user_id) % 3 → shard 0, 1, or 2.
  • The router (shard.py) computes the shard, then talks to just that container.

0 Prerequisites

  1. Install Docker Desktop and open it — wait until the whale icon stops animating.
  2. Get the sharding-demo folder (from your mentor / repo). It contains docker-compose.yml, schema.sql, shard.py, README.md.
  3. Open a terminal and go into that folder. Every command below assumes you are inside it:
cd path/to/sharding-demo
Most common mistake: running docker compose ... from the wrong directory (e.g. your home folder). You'll see service "shard0" is not running. Fix: cd into sharding-demo first. Compose finds the project by the docker-compose.yml in your current directory.

1 Start the shards

docker compose up -d

First run downloads the postgres:16 image (~1 min). Then check all three are up:

docker compose ps

You should see shard0, shard1, shard2 with status Up and ports 5433, 5434, 5435.

Give Postgres ~5 seconds after up -d before the next step, so it finishes booting.

2 Create the schema

Apply the same users + orders tables to all three shards:

./shard.py init

Expected output:

  shard0: schema applied
  shard1: schema applied
  shard2: schema applied
On Windows, if ./shard.py doesn't run, use python shard.py init (and python instead of ./shard.py everywhere below).

3 Load sample data

Create 30 users, each with 0–3 random orders. Watch every insert get routed:

./shard.py seed 30

Each line shows the decision, e.g.:

user id 14 -> md5(14) % 3 = 1 -> shard1
  [shard1] INSERT INTO users(id,name,city) VALUES (14,'Priya13','Delhi');

At the end you get the distribution:

rows per shard:
  shard0:   9 users   14 orders  #########
  shard1:   8 users   11 orders  ########
  shard2:  13 users   23 orders  #############
  total: 30 users, 48 orders
Think: the counts aren't exactly 10/10/10. Is that a bug? (No — hashing is statistically even, not perfectly even. With 30 rows the wobble is visible; with 30 million it's <1%.)

4 See the actual data

Each shard is a normal database. Open a SQL shell on one:

docker compose exec shard0 psql -U demo -d appdb

At the appdb=# prompt:

\dt                       -- list tables
SELECT * FROM users ORDER BY id;
SELECT * FROM orders ORDER BY id;
SELECT count(*) FROM users;
\q                        -- quit

Now do the same on shard1 and shard2 — different rows every time, no overlap.

Or without opening a shell

docker compose exec shard0 psql -U demo -d appdb -c "SELECT * FROM users ORDER BY id;"
docker compose exec shard1 psql -U demo -d appdb -c "SELECT * FROM users ORDER BY id;"
docker compose exec shard2 psql -U demo -d appdb -c "SELECT * FROM users ORDER BY id;"

Or all shards at once, via the router

./shard.py query-all "SELECT * FROM users ORDER BY id;"
./shard.py distribution

Or in a GUI

Use TablePlus, DBeaver, or pgAdmin. Add three connections:

5 How routing works

Ask where any key lands — no DB call, just the hash:

./shard.py where 7
./shard.py where 8
./shard.py where 42
key 7 -> shard index 0 -> shard0

Open shard.py and read these 3 lines — that is the entire sharding algorithm:

def shard_index(key, n=3):
    h = hashlib.md5(str(key).encode()).hexdigest()
    return int(h, 16) % n
Think: why hash the id instead of just user_id % 3? (Sequential ids would still spread fine — but real keys are often not sequential, e.g. emails, and can cluster. Hashing removes any pattern in the key.)

6 Single-shard read — the payoff

./shard.py get-user 12
routing: user 12 -> shard2  (1 shard queried, not 3)
12 | Arjun11 | Hyderabad
orders:
13 | 3622.02
14 | 4250.64

The router hit one container. Orders are sharded by the same user_id, so "user + their orders" never crosses a shard. This is why you shard by the key you read by.

Think: what if the product now needs "all orders shipped to Pune this week"? That query has no user_id in it. What happens? (You're forced to ask every shard — see the next section.)

7 Cross-shard query — the cost

A query with no shard key must go to every shard (scatter), then the app merges the answers (gather):

./shard.py query-all "SELECT count(*), COALESCE(sum(amount),0) FROM orders;"
./shard.py top-cities

top-cities asks each shard for its local city counts, then adds them up in Python:

global city counts (merged in app from 3 partial results):
  Mumbai       7
  Pune         6
  Bengaluru    6
What just got harder:
  • ORDER BY ... LIMIT 10 — you must pull top-10 from each shard, then re-sort.
  • JOIN between two users on different shards — no single DB can do it.
  • COUNT(DISTINCT email) across shards — needs de-dup in the app.
  • A transaction spanning two shards — no longer ACID for free.
  • Latency = the slowest shard, not the average.
This is why sharded systems often keep a separate analytics DB or a search index.

8 Why adding a shard hurts

Say traffic grows and you want 4 shards instead of 3:

./shard.py reshard 4
resharding 3 -> 4: 21/30 users change shard (70%)
this is why naive hash-mod sharding is painful to scale

Changing % 3 to % 4 remaps almost every key → you'd copy ~70% of your data while the site is live. Fixes people actually use:

  • Consistent hashing — only ~1/N of keys move when you add a node.
  • Virtual buckets — hash into e.g. 4096 fixed buckets, map buckets → nodes. To rebalance you move buckets, not individual keys.
Think: run ./shard.py reshard 6. Is it better or worse than going to 4? Why does going from 3 to 6 (a multiple) move fewer rows?

★ Exercises

Exercise 1 — Prove disjointness. Write one command that shows user id 5 exists on exactly one shard and is absent from the other two.
hint 
./shard.py query-all "SELECT * FROM users WHERE id = 5;"
Two shards print (no rows), one prints the user.
Exercise 2 — Add yourself. Insert a user with your name, then confirm which shard you landed on two different ways (the router's prediction, and by querying that shard directly).
hint 
./shard.py add-user "YourName" YourCity
# note the id it prints, say 31
./shard.py where 31
docker compose exec shard2 psql -U demo -d appdb -c "SELECT * FROM users WHERE id=31;"
Exercise 3 — Break the balance. Imagine sharding by city instead of user_id. Run ./shard.py top-cities and argue why that key would create a hotspot. Which city would overload its shard?
Exercise 4 — Global top spender. Find the single user with the highest total order amount across all shards. You can't do it in one SQL query — describe the scatter-gather steps, then verify with:
hint 
./shard.py query-all "SELECT user_id, SUM(amount) t FROM orders GROUP BY user_id ORDER BY t DESC LIMIT 1;"
Each shard gives its local top spender; you compare the 3 winners by hand.
Exercise 5 — Resharding math. Before running it, predict: going from 3 → 9 shards, roughly what % of rows move? Then check with ./shard.py reshard 9. Were you close?
Exercise 6 — Kill a shard. Run docker compose stop shard1, then ./shard.py get-user 12 vs a user on shard1, then ./shard.py distribution. What still works? What fails? This is the availability story of sharding. Restart with docker compose start shard1.

✓ Cleanup

Stop the containers but keep your data for next time:

docker compose down

Wipe everything (containers + data), to start completely fresh:

docker compose down -v
Re-running the lab later: docker compose up -d and your seeded data is still there (unless you used -v). Otherwise re-run init + seed.

→ What to take away

  • Sharding lives in the app layer. The databases are ordinary and unaware.
  • Shard by the key you read by, and co-locate related data on the same key.
  • Single-key ops stay fast; anything without the key becomes scatter-gather.
  • You give up cross-shard joins, global constraints, multi-shard transactions.
  • Naive hash % N makes growth expensive — that's what consistent hashing / virtual buckets solve.
