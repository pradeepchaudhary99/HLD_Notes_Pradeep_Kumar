Redis Deep Dive

Week 2Live Demo

Redis (REmote DIctionary Server) is an in-memory data structure store used as a cache, database, message broker, and queue. The reason it shows up in nearly every system design interview is that it's not just a key-value cache — it ships with rich data structures that solve entire classes of problems (rate limiting, leaderboards, pub/sub) without extra infrastructure.

Why it's fast

  • Everything lives in RAM (sub-millisecond operations); optionally persisted to disk for durability.
  • Single-threaded execution model for command processing (Redis 6+ added threaded I/O for network reads/writes, but command execution itself is still single-threaded) — this means no locks, no race conditions between commands, and every command is effectively atomic.

Core data structures

TypeCommandsUse case
StringSET, GET, INCR, EXPIRESimple cache values, counters, feature flags, distributed locks
HashHSET, HGET, HGETALLObject-like records (e.g. a user profile) without serializing/deserializing the whole blob to update one field
ListLPUSH, RPUSH, LPOP, BRPOPSimple queues, recent-activity feeds (capped with LTRIM)
SetSADD, SISMEMBER, SINTERUnique collections — tags, "users who liked this post", mutual-friends via set intersection
Sorted Set (ZSet)ZADD, ZRANGE, ZRANK, ZINCRBYLeaderboards, priority queues, rate limiters (score = timestamp) — a skip-list under the hood gives O(log N) inserts and range queries
BitmapSETBIT, BITCOUNTExtremely memory-efficient boolean flags at scale — e.g. daily active user tracking (1 bit per user per day)
HyperLogLogPFADD, PFCOUNTApproximate distinct-count (e.g. "unique visitors today") in ~12KB regardless of cardinality
StreamXADD, XREAD, XGROUPAppend-only log with consumer groups — a lightweight Kafka-like use case
GeoGEOADD, GEOSEARCH"Find drivers within 5km" — built on sorted sets internally

Eviction policies

Set via maxmemory-policy. Matters once your dataset can exceed available RAM.

PolicyBehavior
noevictionReturn errors on writes once memory limit is hit — never silently drop data (default)
allkeys-lruEvict the least-recently-used key across the whole keyspace
volatile-lruEvict least-recently-used, but only among keys that have a TTL set
allkeys-lfu / volatile-lfuEvict by access frequency instead of recency
volatile-ttlEvict the key with the nearest expiration first
allkeys-random / volatile-randomEvict a random key — cheapest to compute

Common production choice: allkeys-lru for a pure cache; noeviction when Redis is used as a source of truth (e.g. session store) where silently losing data is unacceptable.

Pub/Sub

Redis supports lightweight publish/subscribe messaging: a publisher sends a message to a channel, and every currently-subscribed client receives it in real time.

# Terminal A (subscriber)
SUBSCRIBE notifications:user:42

# Terminal B (publisher)
PUBLISH notifications:user:42 "You have a new message"
# → Terminal A instantly receives "You have a new message"
Important limitation
Classic Redis Pub/Sub is fire-and-forget — if a subscriber is offline when a message is published, it's lost forever; there's no persistence or replay. For "at-least-once" delivery or replay, use Redis Streams (XADD/XREAD with consumer groups) instead, which persists messages and tracks per-consumer read position.

Typical use cases: real-time chat fan-out to WebSocket servers, live notifications, invalidating in-process caches across multiple app instances ("cache-bust" broadcast), simple real-time dashboards.

Persistence (so "in-memory" doesn't mean "disposable")

  • RDB (snapshotting): periodic point-in-time dumps of the whole dataset to disk. Fast restarts, compact files, but you can lose data since the last snapshot.
  • AOF (Append Only File): logs every write operation; replayed on restart. More durable (configurable fsync — every write, every second, or OS-controlled), larger files, slower restart than RDB.
  • Many production setups use both, or use AOF with periodic RDB snapshots for compaction.

Scaling Redis

  • Replication: primary-replica setup for read scaling and failover; combined with Redis Sentinel for automatic primary failover detection/promotion.
  • Redis Cluster: shards data across multiple nodes using hash slots (16,384 fixed slots, each key mapped via CRC16(key) % 16384) — a form of the consistent-hashing idea from the networking note, adapted to a fixed slot count for simpler resharding.

Live demo use cases (class walkthrough)

1. Rate limiter with sorted sets (sliding window)
ZADD  rate:user:42    
ZREMRANGEBYSCORE rate:user:42 0 ( - window_ms)
count = ZCARD rate:user:42
if count > limit: reject
Every request adds a timestamped entry, old entries outside the window are trimmed, and the count of remaining entries is the current rate — all atomic within Redis.
2. Leaderboard with ZSET
ZADD leaderboard 1500 "alice"
ZADD leaderboard 2200 "bob"
ZREVRANGE leaderboard 0 9 WITHSCORES   # top 10
ZRANK leaderboard "alice"              # alice's rank
3. Distributed lock (simplified)
SET lock:order:123  NX PX 5000
-- NX: only set if not already held; PX 5000: auto-expires in 5s so a crashed
-- holder doesn't lock the resource forever. (Production systems use the
-- Redlock algorithm across multiple Redis nodes for stronger guarantees.)
Interview takeaway
When you say "I'll add a cache" in an interview, naming Redis specifically — and which data structure you'd use beyond a plain string — is a strong signal. "I'll use a Redis sorted set keyed by score for the leaderboard" reads very differently from "I'll cache it."
