CDN, DNS & Reverse Proxies

Week 2Infrastructure

Before a request ever reaches your application code, it typically passes through DNS resolution, possibly a CDN edge, and a reverse proxy. Understanding this path is what lets you explain "why is this page slow" beyond just "the backend is slow."

DNS (Domain Name System)

Translates a human-readable hostname (www.example.com) into an IP address. It's a distributed, hierarchical, heavily-cached lookup system.

  1. Browser/OS cache — checked first, fastest.
  2. Recursive resolver (usually your ISP or a public one like 8.8.8.8/1.1.1.1) — does the actual lookup on your behalf if not cached.
  3. Root nameserver → points to the TLD nameserver (e.g. for .com) → points to the authoritative nameserver for the domain, which returns the actual IP (A/AAAA record).
Record typePurpose
AHostname → IPv4 address
AAAAHostname → IPv6 address
CNAMEAlias one hostname to another (e.g. www → example.com)
MXMail server for the domain
TXTArbitrary text — commonly used for domain verification, SPF/DKIM
NSWhich nameservers are authoritative for this domain

TTL (time to live) on a DNS record controls how long resolvers cache it — low TTL (e.g. 60s) means faster failover/changes but more lookup traffic; high TTL is cheaper but slower to propagate changes.

DNS-based load balancing: return multiple IPs, or different IPs to different regions (GeoDNS), so users are routed to the nearest healthy datacenter before any request even leaves their machine.

CDN (Content Delivery Network)

A globally distributed network of edge/PoP (point of presence) servers that cache and serve content physically close to the end user, cutting round-trip latency and offloading your origin servers.

  • Static content (images, JS/CSS bundles, videos) is the classic use case — cached at the edge with long TTLs.
  • Dynamic content acceleration: modern CDNs can also proxy dynamic requests through optimized backbone networks even when they can't cache the response.
  • Push vs pull CDN: pull — CDN fetches from origin on first request (cache miss) and caches it (most common, low maintenance); push — you proactively upload content to the CDN ahead of time (used for large media libraries with predictable access).
  • Cache invalidation: the classic hard problem — either wait out the TTL, use versioned/hashed filenames (app.a1b2c3.js, so a "new" file has a new URL and never needs invalidation), or explicitly purge via the CDN's API.
Interview usage
Whenever a design serves images/video/static assets to a wide geographic user base (Instagram, YouTube, Netflix, e-commerce product images), say "CDN" early — it's one of the highest-leverage, lowest-controversy additions to any architecture diagram.

Reverse proxy

Sits in front of your application servers and forwards client requests to them — the mirror image of a forward proxy (which sits in front of clients and forwards their requests outward).

ResponsibilityWhy it matters
TLS terminationDecrypt HTTPS once at the edge; internal traffic can be plain HTTP, simplifying certificate management
Load balancingOften the same box acts as an L7 load balancer (e.g. NGINX, Envoy, HAProxy)
CachingCache responses close to the app tier
CompressionGzip/Brotli responses before sending to the client
SecurityHide internal server topology/IPs; a single hardened entry point; can block malicious patterns (WAF)
Request routingPath/host-based routing to different backend services (a stepping stone to API gateways)

Common tools: NGINX, HAProxy, Envoy (popular in service-mesh/microservices setups), cloud-managed equivalents (AWS ALB + CloudFront, GCP Load Balancer).

Putting it together: the request path

1. Browser resolves example.com via DNS (often GeoDNS → nearest region)
2. Request hits nearest CDN edge/PoP
     - Static asset? Served directly from edge cache. Done.
     - Dynamic/API request? Proxied toward origin.
3. Request reaches the origin's reverse proxy / L7 load balancer
     - TLS terminated, routed by path/host to the right service
4. Load balancer forwards to a healthy application server
5. App server reads from cache (e.g. Redis) or falls through to the database
Interview framing
When asked "how would you reduce latency for global users," the answer almost always starts with this exact chain: push static content to a CDN, use GeoDNS/anycast to route to the nearest region, terminate TLS at the edge, and only go to origin for true cache misses.
