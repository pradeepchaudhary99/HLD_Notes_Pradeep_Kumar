Leader-Follower Replication & Leader Election

Week 2Coordination

A kitchen with ten chefs and no head chef is chaos: two people season the same soup, a third turns off the oven someone else just turned on, orders come out wrong. The fix professional kitchens use is simple — one head chef calls out every order, every other chef follows instructions and executes. If the head chef steps out, someone else immediately takes over calling orders, so the kitchen never actually stops.

Distributed databases have the exact same problem. If five replicas of a database can all accept writes independently, two clients can write conflicting values to the same row at the same instant, and now the replicas disagree about reality. The classic fix: designate one replica as the leader (all writes go through it), and the rest as followers (they just replicate what the leader did, in order).

Fig 1. Leader election exists to prevent exactly this kind of chaos.

Leader-follower replication, end to end

All writes go to the leader. The leader applies the write locally, then streams it to every follower as part of a replication log — the same ordered list of changes, replayed in the same order everywhere. Reads can go to the leader (freshest data) or to followers (more capacity, but possibly a few milliseconds/seconds stale — this is eventual consistency in practice).

Fig 2. Single-leader replication: one write path, many read paths.

Sync vs. async replication

  • Synchronous: the leader waits for (at least one) follower to confirm the write before telling the client it succeeded. Safer — a leader crash right after can't silently lose the write — but slower, and if that follower is unreachable, writes stall.
  • Asynchronous: the leader confirms the write immediately and replicates in the background. Fast, but a leader crash before replication completes can lose the last few writes.
  • Semi-synchronous (the common middle ground): wait for just one follower to ack, replicate to the rest async — bounds the worst-case data loss without paying full sync latency on every write.

The head chef goes home: leader election

Leaders die — the machine crashes, the network partitions it away, a deploy goes wrong. The cluster needs to notice quickly and promote a new leader, automatically, without a human paging in at 3am. This is leader election, and virtually every production consensus system (Raft, Paxos-derived systems, ZooKeeper's ZAB) solves it with the same shape of algorithm.

How Raft elects a leader (the one to know cold)

Every node is in one of three states. It starts as a follower, listening for periodic heartbeats from a leader. If a follower hears nothing for a randomized election timeout (e.g. 150–300ms, randomized specifically to avoid every node timing out simultaneously), it assumes the leader is dead, becomes a candidate, bumps a term number, and requests votes from every other node. If it gets votes from a majority of the cluster, it becomes the new leader and starts sending heartbeats itself.

Fig 3. Raft's three states — the randomized timeout is what prevents every node from becoming a candidate at once.

Two subtleties that separate a real understanding from a memorized diagram:

  • Terms: every election increments a monotonically increasing "term" number. If a node ever sees a message with a higher term than its own, it immediately steps down — this is what stops a stale, isolated old leader from causing confusion once it reconnects.
  • Majority quorum: a candidate needs votes from more than half the cluster (e.g. 3 of 5 nodes), not just "some" nodes. This single rule is what makes split-brain (two leaders at once) provably impossible — two different majorities of the same cluster can never both exist simultaneously, because they'd have to overlap.

Split-brain: the failure mode leader election exists to prevent

Imagine a network partition splits a 5-node cluster into a group of 3 and a group of 2. Without a quorum rule, both sides might elect their own leader — now you have two "head chefs" each accepting writes, and the two halves of your data silently diverge. This is split-brain, and it's one of the most dangerous failure modes in distributed systems because it fails silently, not loudly.

Fig 4. The majority side keeps working; the minority side refuses to elect a leader and simply stops accepting writes — trading availability for correctness, per the CAP theorem.
Always use an odd number of nodes
A 4-node cluster can split 2-2 — neither side has a majority, and the whole cluster stalls. A 5-node cluster splits at worst 3-2 — one side always has a majority. This is why Raft/ZooKeeper/etcd clusters are almost always sized 3, 5, or 7.

Real-world examples

SystemHow leader election works
MySQL / PostgreSQL replicationClassically manual or tool-assisted (e.g. Orchestrator, Patroni) — Patroni uses etcd/Consul/ZooKeeper underneath to run a Raft-like election and automate primary failover.
Apache KafkaEach partition has its own leader broker; a cluster-wide controller (elected via ZooKeeper historically, or via the built-in Raft-based KRaft mode in modern Kafka) assigns and reassigns partition leaders when brokers fail.
Redis Sentinel / Redis ClusterSentinel nodes monitor the primary and run a quorum-based vote to promote a replica if the primary is unreachable; Redis Cluster does similar failover per hash-slot owner.
etcd / ZooKeeperThese are the coordination services other systems lean on — etcd implements Raft directly; ZooKeeper implements a similar protocol called ZAB (ZooKeeper Atomic Broadcast).
MongoDB replica setsA Raft-inspired election among replica set members, triggered automatically when the primary becomes unreachable, using priorities you can configure per node.
The story to tell in an interview
"Multiple writers on the same data can conflict, so I need exactly one writer at a time — a leader. Leaders can die, so I need automatic failover — leader election with a majority quorum, so a network partition can never produce two leaders at once." That's the whole idea, and everything else (Raft states, terms, sync vs. async replication) is implementation detail supporting that one sentence.
