Networking Concepts & Load Balancers

Week 2Infrastructure

Networking refresher

  • TCP: connection-oriented, reliable, ordered, handles retransmission — used for HTTP, database connections, most application traffic.
  • UDP: connectionless, no delivery guarantee, lower overhead — used for DNS, video/voice streaming, gaming, and as the transport for QUIC (HTTP/3).
  • 3-way handshake: SYN → SYN-ACK → ACK to establish a TCP connection before any data flows. This is why connection reuse (keep-alive, connection pooling) matters for latency.
  • TLS handshake: sits on top of TCP, negotiates encryption keys — adds 1-2 extra round trips (reduced with TLS 1.3 and session resumption).

Load balancers: L4 vs L7

A load balancer distributes incoming traffic across multiple backend servers so no single machine is overwhelmed, and so the system keeps working if one server goes down.

Layer 4 (Transport)Layer 7 (Application)
Operates onIP + TCP/UDP port onlyFull HTTP request: headers, path, cookies, body
Routing decisionsBased on source/dest IP & port; forwards packetsCan route by URL path, hostname, header, cookie (e.g. /api/* → service A, /static/* → service B)
Speed / overheadVery fast, minimal processing — just shuffles packetsSlower (terminates connection, parses request) but far more flexible
ExamplesAWS NLB, LVS, basic HAProxy TCP modeAWS ALB, NGINX, Envoy, HAProxy HTTP mode
Use whenRaw throughput matters most, protocol-agnostic (e.g. non-HTTP TCP/UDP services)You need smart routing, SSL termination, request-level features (auth, rate limiting, A/B routing)
Interview one-liner
"L4 balances connections, L7 balances requests." An L4 LB can't tell two HTTP requests on the same persistent connection apart; an L7 LB can route every single request differently based on its content.

Load balancing algorithms

  • Round robin: cycle through servers in order. Simple, assumes uniform server capacity and request cost.
  • Weighted round robin: like round robin but some servers get more traffic (e.g. more powerful machines).
  • Least connections: send the next request to whichever server currently has the fewest active connections — better when request processing times vary a lot.
  • IP hash: hash client IP to consistently route the same client to the same server (useful for sticky sessions without a shared session store).
  • Consistent hashing: see below — used when you need stable routing that survives servers being added/removed.

Consistent hashing

Problem: with plain modulo hashing (server = hash(key) % N), adding or removing a single server changes N and reshuffles almost every key's mapping — catastrophic for caches (mass cache misses) or sharded databases (mass data movement).

Consistent hashing fixes this by mapping both servers and keys onto the same abstract hash ring (0 to 2³²-1, say). A key is assigned to the first server found walking clockwise from the key's position on the ring.

  • When a server is added or removed, only the keys between it and its immediate neighbor on the ring move — roughly 1/N of all keys, not all of them.
  • Virtual nodes (vnodes): each physical server is hashed to multiple points on the ring (e.g. 100–200 vnodes per server) so load is spread evenly and a single server failure doesn't dump all its load onto one neighbor.
Ring (simplified, 0-100):
  ServerA @ 10, ServerB @ 40, ServerC @ 75

  key "user:42"  → hash = 22 → next server clockwise = ServerB (40)
  key "user:99"  → hash = 80 → next server clockwise = ServerA (wraps around to 10)

  If ServerB is removed:
    only keys between ServerA(10) and ServerB(40) reassign to ServerC —
    keys between ServerB(40) and ServerC(75), and ServerC to ServerA, are untouched.

Used in: Cassandra & DynamoDB (data partitioning across nodes), Memcached client libraries (which cache server owns a key), CDN request routing, and load balancers that need session affinity that survives scaling events.

High availability of the load balancer itself

The LB is a potential single point of failure — solved with an active-passive pair (floating/virtual IP failover via something like keepalived/VRRP) or DNS-based load balancing across multiple LB instances, often layered: DNS → a pool of L4 LBs → L7 LBs → application servers.

Health checks
Load balancers continuously ping backend servers (e.g. GET /health every few seconds) and stop routing traffic to any instance that fails checks — this is what makes rolling deploys and auto-scaling safe.
