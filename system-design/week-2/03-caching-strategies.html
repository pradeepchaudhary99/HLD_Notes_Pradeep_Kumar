Caching Strategies

Week 2Performance

Caching is the single highest-leverage tool for turning a slow, expensive system into a fast, cheap one — because it exploits the fact that most real workloads are heavily read-skewed and re-read the same hot data repeatedly. The trade-off you're always managing is staleness vs. performance.

Where caches live

LayerExample
Client-sideBrowser cache, mobile app local storage
CDN / edgeCached static assets close to the user
Application-level (in-memory)In-process cache inside a service (fastest, but not shared across instances)
Distributed cacheRedis / Memcached — shared across all app instances
Database-levelQuery cache, buffer pool (e.g. Postgres shared_buffers, MySQL InnoDB buffer pool)

Cache-aside (lazy loading)

The application is responsible for managing the cache explicitly. Most common pattern in practice.

READ:
  value = cache.get(key)
  if value is None:           # cache miss
      value = db.query(key)
      cache.set(key, value, ttl=300)
  return value

WRITE:
  db.update(key, new_value)
  cache.delete(key)           # invalidate — don't update in place
  • Pros: only requested data gets cached (no wasted memory); cache failure just means falling back to the DB (resilient).
  • Cons: first request for any key is always a slow miss ("cold start" / thundering herd risk); brief window of inconsistency between DB write and cache invalidation.

Write-through

Every write goes to the cache and the database synchronously, together, before the write is considered complete.

WRITE:
  cache.set(key, new_value)
  db.write(key, new_value)     # both must succeed
  return success
  • Pros: cache is always consistent with the DB — no stale reads after a write.
  • Cons: every write pays the latency of both cache and DB; data that's never read still gets cached (wasted memory) unless combined with a TTL/eviction policy.

Write-back (write-behind)

Writes go to the cache immediately and are acknowledged to the client right away; the cache asynchronously flushes to the database later (batched or on a delay).

WRITE:
  cache.set(key, new_value)
  queue.enqueue(flush_to_db, key, new_value)   # async, batched
  return success   # fast — caller doesn't wait on the DB
  • Pros: lowest write latency; can batch/coalesce many writes to the DB (fewer, cheaper writes).
  • Cons: risk of data loss if the cache node crashes before flushing (mitigate with cache persistence/replication); more complex to implement correctly.
  • Used for: high-frequency counters (view counts, likes) where losing the last few increments on a rare crash is an acceptable trade for speed.

TTL (time to live)

Every cached entry should generally have an expiration to bound staleness and prevent unbounded memory growth. Choosing a TTL is a judgment call tied to how often the underlying data changes and how bad stale data is:

  • Session tokens: minutes to hours.
  • Product prices/inventory: seconds to a couple of minutes.
  • Rarely-changing reference data (country list, config): hours to a day.
  • Jitter your TTLs (e.g. base + random 0-30s) so a huge batch of keys set at the same time don't all expire simultaneously and hammer the DB at once.

Eviction policies (when the cache is full)

  • LRU (Least Recently Used): evict the entry that hasn't been accessed in the longest time — the default choice for most workloads, and Redis's default (allkeys-lru).
  • LFU (Least Frequently Used): evict the entry accessed the fewest times — better when access frequency matters more than recency (e.g. some items are rarely-but-regularly hit).
  • FIFO: evict the oldest-inserted entry regardless of access pattern — simple but rarely optimal.
  • Random: surprisingly competitive in some workloads, essentially zero bookkeeping overhead.

Failure modes to know

Cache stampede / thundering herd
A hot key expires, and thousands of concurrent requests all miss the cache at once and hammer the database simultaneously. Mitigations: request coalescing (only one request per key actually queries the DB, others wait on that result), early/probabilistic refresh (refresh slightly before actual expiry), or a short lock around the recompute.
Cache penetration
Repeated requests for a key that doesn't exist in the DB bypass the cache every time (nothing to cache) and hit the DB directly — can be exploited or happen accidentally at scale. Fix: cache the "not found" result too (with a short TTL), or use a bloom filter to reject definitely-nonexistent keys before touching the DB.
Cache avalanche
A large number of keys expire at (or near) the same time, causing a sudden spike of DB load. Fix: TTL jitter (mentioned above), and/or a multi-tier cache so a single layer failing doesn't fully expose the DB.
Interview framing
Default to cache-aside unless you have a specific reason not to — it's the most common, most resilient pattern. Reach for write-through when correctness after a write matters a lot and writes are infrequent. Reach for write-back when you have very high write volume and can tolerate a small risk window (e.g. counters, analytics events) — exactly the kind of thing we'll see in the Redis deep dive next.
