Partitioning & Sharding

Week 2Data Scaling

Picture a single librarian running the world's biggest library. Every book — every single one — sits on shelves only she manages. At first, that's fine: a few thousand books, a handful of visitors a day, she knows every title by heart. Then the library goes viral. Millions of visitors, tens of millions of books. The librarian is still just one person. The queue to ask her anything now wraps around the building three times.

This is exactly what happens to a database as an app grows: one machine holds all the data, and eventually one machine simply can't hold it, or can't answer fast enough. Partitioning (also called sharding when you split across separate machines) is the answer — hire more librarians, and give each one responsibility for a slice of the collection.

Fig 1. Partitioning is just hiring more librarians and giving each one a slice of the shelves.

Two very different ways to slice a table

Before picking a sharding strategy, there's a simpler, more fundamental choice: are we splitting by rows or by columns?

Vertical partitioning

Split a wide table by columns. E.g. keep users(id, name, email) on one server and rarely-accessed users_profile(id, bio, preferences, avatar_blob) on another. Each server holds all rows but only some columns. Good when a few columns are huge or accessed far less often than the rest.

Horizontal partitioning (sharding)

Split a table by rows. E.g. users with id 1–1,000,000 go to Shard 1, 1,000,001–2,000,000 go to Shard 2. Each shard holds the full schema but only some rows. This is what people usually mean by "sharding," and it's the one that actually lets you scale writes and storage without bound.

Fig 2. Vertical splits the schema; horizontal splits the dataset. Sharding almost always means horizontal.

Choosing a shard key: three strategies

The shard key (or partition key) decides which shard a row lives on. Get it wrong and you either lose the ability to query efficiently, or you create "hot" shards that get hammered while others sit idle. There are three go-to strategies, and they're the same three ideas from the CAP/consistency and load-balancing notes, applied to data storage.

Fig 3. Three shard-key strategies, each trading off differently.
StrategyHow it worksGreat forWatch out for
Range-basedContiguous key ranges (e.g. user_id 1–1M) map to a shardRange queries ("all orders this week")Hotspots — new/sequential IDs all land on the newest shard
Hash-basedshard = hash(key) % N, or better, consistent hashing (see the load balancing note)Even distribution, avoiding hotspotsRange scans now have to fan out to every shard
Geo / directory-basedA lookup table (or the key itself) maps entities to a region or shard explicitlyData residency laws (GDPR), low latency for regional usersThe directory/lookup service itself becomes critical infrastructure
Interview framing
Whichever you pick, name the shard key and justify it against the dominant query pattern. "I'd shard by user_id using consistent hashing, because almost every query in this system is scoped to a single user, so I never need to fan out across shards for the common case."

Two problems every sharded system eventually meets

The celebrity problem (hotspots)

Imagine one librarian ends up responsible for the town's single most famous author — every visitor that day wants exactly her shelf. That's the celebrity problem: a shard key that's usually fine (like user_id) can concentrate massive load on one shard when that "user" is a celebrity account with 100 million followers, or a viral post. Fixes: further sub-partition hot keys, cache aggressively in front of the hot shard, or special-case extremely hot entities onto dedicated infrastructure.

Fig 4. A "fair" hash can still create a hotspot when the traffic itself is unfair.

Resharding pain (growing the cluster)

When a shard fills up or gets too hot, you need to add more shards and move data onto them — and this is precisely the problem consistent hashing was built to minimize. With naive hash(key) % N sharding, adding one shard reshuffles almost everything. With consistent hashing (or a directory service you can update incrementally), only a fraction of the data has to move.

This is the same lesson, twice
If you've read the load balancing note, this should feel familiar — because it's the identical problem. A load balancer routes requests to servers; a sharded database routes rows to shards. Both use the same trick (consistent hashing) to survive the cluster changing size.

Real-world examples

SystemSharding approach
MongoDBRange-based or hashed sharding on a chosen shard key, coordinated by a config server; a mongos router directs each query to the right shard(s).
Apache CassandraConsistent hashing (with virtual nodes) — every node owns a range of the hash ring, exactly as in the load balancing note.
Instagram (Postgres)Logical shards distributed across physical Postgres servers, with IDs encoding the shard number directly (a Snowflake-style ID scheme) so any service can compute which shard owns a row without a lookup.
Vitess (used by YouTube, Slack)Shards a MySQL cluster transparently behind a proxy layer, supporting online resharding without downtime.
ElasticsearchSplits an index into a fixed number of shards at creation time, hash-based on document ID by default — this is why you plan shard count carefully upfront.
The story to tell in an interview
Start with the librarian: "One server can't hold this much data or handle this much traffic, so I'll split rows across N shards." Name the shard key and strategy, justify it with the dominant access pattern, then proactively flag hotspots and resharding — that's the difference between a design that sounds right and one that's actually been thought through.
