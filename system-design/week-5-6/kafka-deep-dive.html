offset:00

Why Kafka exists

Before you memorize APIs, understand the failure modes it was built to kill.

The world before an event log

Three patterns dominated, and each one hits a wall at scale:

  • Synchronous service calls. Service A calls Service B over REST/gRPC to notify it of something. Works fine until B is slow or down — now A is blocked, timeouts cascade, and adding a third interested service (C) means A has to know about C too. Coupling grows with every new consumer of the event.
  • Traditional message queues (e.g. classic AMQP brokers). A message is delivered to one consumer and then it's gone. That's perfect for task distribution ("process this job exactly once"), but terrible for "N independent systems need to react to the same event" — you'd need fan-out exchanges per consumer, and once a message is consumed, a new consumer added next month can never see history.
  • Database-as-a-queue. Producers insert rows, consumers poll WHERE processed = false. Row-level locking contention, polling latency, and it doesn't horizontally scale past a single table's write throughput.

Origin story (worth knowing for interviews)

Kafka was built at LinkedIn (2010–2011) to solve a very specific pain: the same stream of user-activity events needed to feed real-time services and be replayed later into offline Hadoop jobs — from the exact same pipe, without producers knowing or caring who was downstream. That requirement — durable, replayable, many-independent-readers — is the seed of almost every Kafka design decision.

The reframe

Stop thinking "Kafka = queue with extra steps." Think: Kafka is a distributed, append-only, replicated commit log that consumers read from at their own pace, using an offset as a bookmark. Partitioning, replication, retention, consumer groups — all of it is just "how do we make an append-only log durable and fast at cluster scale."

🎯

Interview framing: if asked "what problem does Kafka solve," don't say "it's like RabbitMQ but faster." Say it decouples producers from consumers in time (via retention/replay) and in cardinality (many independent consumer groups can read the same stream), which neither a sync call nor a classic queue can do simultaneously.

offset:01

Core mental model

Eight terms. Get these exactly right and the rest of Kafka is just engineering detail on top of them.

TermWhat it actually means
TopicA named, logical stream of records — e.g. orders. Not a single log; a topic is just a label over one or more partitions.
PartitionThe real unit: an ordered, immutable, append-only log. A topic with 6 partitions is 6 independent logs. Ordering is only guaranteed within a partition, never across the topic.
OffsetA monotonically increasing integer the broker assigns to each record within its partition on append. It's the record's address, not a global sequence — offset 5 in partition 0 and offset 5 in partition 1 are unrelated records.
ProducerWrites records to a partition. Chooses the partition via a partitioner: hash of the record key (default: sticky/murmur2 hash) or round-robin/sticky batching if no key is given.
ConsumerPulls records by polling a partition and tracks its own position (the offset it has processed) — Kafka never pushes to consumers. This single fact is why Kafka doesn't need consumer-side flow control tricks: the consumer sets its own pace.
Consumer GroupA named set of consumers that split a topic's partitions between them — each partition is owned by exactly one consumer in that group at a time. Two different groups reading the same topic get their own independent copy of the stream (this is how Kafka gets pub/sub semantics on top of a log).
BrokerOne Kafka server. It hosts some subset of partitions (as leader or follower) for the topics in the cluster.
Replica / ISREach partition is copied to N brokers (replication factor). One replica is the leader (serves all reads/writes); the rest are followers that replicate the log. The In-Sync Replica set is followers caught up close enough to the leader to be trusted in a leader election.
Common misconception

"Kafka guarantees message ordering." No — it guarantees ordering per partition. If you need all events for a given entity (e.g. one order_id) to be processed in order, you must key the record by that entity so every event for it lands in the same partition. Across partitions, there is no ordering guarantee at all.

Architecture & replication

What actually happens on disk and across brokers when a record is produced.

Leader / follower / ISR

Say topic orders, partition 0, has replication factor 3, spread across brokers 1, 2, 3. Broker 1 is elected leader for that partition — all produces and (by default) all consumes for partition 0 go through it. Brokers 2 and 3 run followers that continuously fetch from the leader to replicate the log.

→
Broker 2
Follower (in ISR)

Broker 3
Follower (in ISR)

A follower stays in the ISR (In-Sync Replica) set only while it's fetching frequently enough to be within replica.lag.time.max.ms of the leader. Fall behind that window (slow disk, network partition, GC pause) and the controller evicts it from ISR — it keeps replicating in the background, but it's no longer eligible to be elected leader until it catches back up.

When broker 1 dies, the controller picks a new leader from the current ISR — this is why ISR membership matters so much: it's the pool of "replicas we trust not to have lost data."

The unclean leader election trade-off

If every ISR member is also down, Kafka faces a choice: wait for one to come back (favors consistency, but the partition is unavailable), or promote a stale, out-of-ISR replica (favors availability, but you lose whatever records that replica never caught up on). This is controlled by unclean.leader.election.enable (default false in modern Kafka — correctly biased toward not silently losing data).

Why appends are fast: the disk trick

Kafka's headline throughput numbers come from refusing to do anything clever: every partition is a plain append-only file. Sequential writes to spinning or SSD disk are close to memory speed because there's no seeking — the OS page cache absorbs writes and flushes sequentially. Reads work the same way: a consumer reading from a known offset is just a sequential file read, and Kafka uses zero-copy (the sendfile syscall) to hand bytes straight from the page cache to the network socket without copying through user space at all.

Segments & retention

A partition's log isn't one giant file — it's broken into segments (default 1 GB or a time boundary, whichever comes first), each with a .log file plus .index/.timeindex files for fast offset/timestamp lookups. Only the newest segment is "active" (appended to); older, sealed segments are what retention policy actually deletes or compacts.

  • Time/size retention (retention.ms, retention.bytes) — delete whole segments once they age out. Default use case: event streams, logs, metrics.
  • Log compaction (cleanup.policy=compact) — instead of deleting by age, keep only the latest record per key, forever. This turns a topic into a changelog of "current state per key" — the mechanism behind Kafka Streams' KTables and CDC pipelines.

KRaft: no more Zookeeper

Older Kafka used an external Zookeeper ensemble to store cluster metadata (broker list, partition leadership, ACLs) and run controller elections. Since Kafka 3.3 (production-ready) and mandatory from Kafka 4.0, that's replaced by KRaft (Kafka Raft) — a built-in Raft consensus quorum of controller nodes, storing metadata as an internal Kafka log instead of a separate system.

🎯

"Why did Kafka drop Zookeeper?" — Operational overhead of running two distributed systems, a scalability ceiling on metadata operations (partition counts in the hundreds of thousands got slow with ZK watches), and slower controller failover. KRaft folds metadata into Kafka's own replicated-log model — the same primitive it already uses for data.

Problems / How Kafka solves them

This is the table that actually gets asked about in interviews — not "what is a topic," but "why does this design choice exist."

Problem

Producers and consumers are tightly coupled — adding a new independent system that cares about "order created" means touching the producer's code, or bolting on another queue.

Kafka's answer

Publish once to a topic. Any number of consumer groups can subscribe independently and each gets its own full copy of the stream, at its own pace, without the producer knowing they exist.

consumer group isolationpub/sub over a log
Problem

You need to sustain millions of events/sec without the broker becoming the bottleneck.

Kafka's answer

Sequential disk appends + zero-copy reads (no seeking, no user-space copy) remove disk and CPU as bottlenecks. Producers batch and compress records client-side before sending, amortizing network overhead. Partitions let you parallelize both writes and reads across brokers and disks.

linger.msbatch.sizecompression.typenum.partitions
Problem

A broker dies mid-write. Did you just lose data?

Kafka's answer

Replication factor > 1 plus ISR-aware leader election. Whether you can lose data depends entirely on the producer's acks setting — acks=0 (fire-and-forget, fastest, no durability guarantee), acks=1 (leader-only ack, can lose data if leader dies before followers replicate), acks=all (every ISR member must ack — durable, at the cost of latency).

replication.factoracks=allmin.insync.replicas
Problem

Events for the same entity (e.g. one order) must be processed in the order they happened.

Kafka's answer

Ordering is guaranteed within a partition. Key records by entity ID (e.g. order_id) — the default partitioner hashes the key so every event for the same key always lands on the same partition, giving you per-key ordering without global ordering overhead.

record key → partition hash
Problem

A slow consumer would overwhelm a broker that tries to push data as fast as it's produced.

Kafka's answer

Consumers pull via poll() — they set their own rate. The broker never pushes. Retention acts as a buffer: a consumer that's hours behind simply has more log to catch up on; it doesn't cause backpressure on the producer at all (as long as retention hasn't expired that data).

pull-based poll loopretention as buffer
Problem

A new team joins next quarter and needs to reprocess the last 30 days of order events — a classic queue already deleted them.

Kafka's answer

Consuming doesn't delete. An offset is just a per-consumer-group bookmark. Any consumer group can start fresh and seek to the earliest retained offset, replaying full history independently of every other consumer.

--from-beginningretention.ms
Problem

Network blips cause producer retries, which can write the same record twice.

Kafka's answer

The idempotent producer tags each producer with a PID and a per-partition sequence number; the broker drops retried duplicates server-side. For multi-partition atomic writes ("commit these 3 records together or none"), transactions layer on top with a transactional.id, and consumers opt in via isolation.level=read_committed.

enable.idempotence=truetransactional.idread_committed
Problem

You want a topic that represents "current state per key" (like a changelog), not an ever-growing event history.

Kafka's answer

Log compaction: set cleanup.policy=compact and Kafka periodically rewrites segments keeping only the latest record per key, discarding older ones. Delete a key entirely with a null-value "tombstone" record.

cleanup.policy=compacttombstone (null value)

Docker + KRaft setup

Two clusters: a single broker to move fast, and a 3-broker cluster for the replication/failover exercises later. No Zookeeper — KRaft only.

A. Single broker (fastest way to get moving)

Prereqs: Docker + Docker Compose v2. Create a folder, drop this in as docker-compose.yml:

# docker-compose.yml — single-broker KRaft cluster + Kafka UI

  kafka:

The listener gotcha everyone hits once

There are two ways to reach this broker: from inside the Docker network (other containers use kafka:9092) and from your host machine (your terminal / IDE uses localhost:29092). That's why there are two listener aliases — mixing them up is the #1 cause of "connection refused" when following Kafka tutorials.

CLI command reference

All CLI tools live inside the broker container. Run them via docker exec, or exec into a shell once and stay there.

open a shell inside the broker
docker exec -it kafka bash
Command names on this image

On confluentinc/cp-kafka (the image this doc's Docker setup uses), the CLI binaries have no .sh suffix — it's kafka-topics, not kafka-topics.sh. (The .sh form is correct for the raw Apache Kafka tarball distribution, which is a different install — easy to mix up since most tutorials online assume that one.) Every command below already reflects the no-suffix form. If a command comes back command not found, run find / -iname "kafka-topics*" 2>/dev/null to locate the real binary path for whatever image you're on.

From here on, commands assume you're either inside that shell (drop the docker exec -it kafka prefix) or running each line individually from the host — both are shown as one form; just prepend docker exec -it kafka if running from outside.

Topics

# list all topics
kafka-topics --bootstrap-server localhost:9092 --list

# create "orders" with 3 partitions, replication factor 1 (single broker)
kafka-topics --bootstrap-server localhost:9092 \
  --create --topic orders --partitions 3 --replication-factor 1

# describe a topic — partitions, leader, replicas, ISR
kafka-topics --bootstrap-server localhost:9092 \
  --describe --topic orders

# increase partition count (you can only go up, never down)
kafka-topics --bootstrap-server localhost:9092 \
  --alter --topic orders --partitions 6

# delete a topic
kafka-topics --bootstrap-server localhost:9092 \
  --delete --topic orders

Producing

# plain console producer — one line = one record, no key
kafka-console-producer --bootstrap-server localhost:9092 --topic orders

# with keys: type "key:value" per line
kafka-console-producer --bootstrap-server localhost:9092 --topic orders \
  --property "parse.key=true" --property "key.separator=:"

# durable producer: wait for all ISR members to ack
kafka-console-producer --bootstrap-server localhost:9092 --topic orders \
  --producer-property acks=all --producer-property enable.idempotence=true

Consuming

# from the current tail (only new messages)
kafka-console-consumer --bootstrap-server localhost:9092 --topic orders

# replay everything from the start of the log
kafka-console-consumer --bootstrap-server localhost:9092 --topic orders \
  --from-beginning

# print key, value, partition and offset for every record
kafka-console-consumer --bootstrap-server localhost:9092 --topic orders \
  --from-beginning --property print.key=true --property print.partition=true \
  --property print.offset=true

# join a named consumer group instead of an ephemeral one
kafka-console-consumer --bootstrap-server localhost:9092 --topic orders \
  --group order-processors

Consumer groups

# list all groups
kafka-consumer-groups --bootstrap-server localhost:9092 --list

# describe a group — per-partition offset, log-end-offset, and LAG

  --group order-processors --topic orders \
  --reset-offsets --to-earliest --execute

  --group order-processors --topic orders \

# which partitions have fewer in-sync replicas than they should?

Everything above is reference. This is a script — open 5 terminals side by side, run each numbered step in the terminal its badge names, and you'll watch a rebalance actually happen instead of reading about one. Uses the single-broker cluster and the orders topic (3 partitions) from earlier.

terminal 1 — producer 
order-1:created
order-2:created
order-3:created
order-4:created
ObserveAll 4 lines show up in consumer A's terminal (terminal 3) — it's the only member, so it gets everything regardless of which partition each key landed on.

terminal 4 — consumer B

ObserveBoth consumer terminals briefly stop consuming — that's the rebalance pause. Describe now shows 2 members; partitions split roughly 2/1. Send a few more keyed messages from terminal 1 and watch: each key consistently goes to the same consumer terminal every time, because that key always hashes to the same partition, and that partition now belongs to one specific consumer.
6Bring up consumer #3 — force rebalance #2, reach full parallelism
terminal 5 — consumer C 
docker exec -it kafka kafka-console-consumer --bootstrap-server localhost:9092 \
  --topic orders --group order-processors
ObserveDescribe now shows 3 members, each owning exactly 1 partition — this is the ceiling for this topic. If you started a 4th consumer right now, describe would show it as a registered member with zero partitions assigned: pure idle capacity.
7Kill consumer B — force rebalance #3, this time from a member leaving

Go to terminal 4 (consumer B) and hit Ctrl+C.

# in terminal 2, right after killing terminal 4
docker exec -it kafka kafka-consumer-groups --bootstrap-server localhost:9092 \
  --describe --group order-processors
ObserveDown to 2 members; consumer B's partition gets picked up by whichever of A or C the assignor lands it on. Send a few more messages — everything still arrives, just redistributed. 8Start a second, independent group on the same topic
new terminal — different group entirely 
docker exec -it kafka kafka-console-consumer --bootstrap-server localhost:9092 \

ObserveThis one replays every message from offset 0 — including everything sent back in step 4, before this consumer existed. This is the pub/sub fan-out from the theory section, made concrete: one topic, two groups, two independent read positions.
What just happened, mechanically

Every rebalance you triggered (steps 5, 6, 7) followed the same protocol: a member joins or leaves → the group coordinator (the broker hosting this group's partition of __consumer_offsets) detects it → all members briefly pause → partitions get reassigned → consumption resumes. With the default console-consumer, that's an eager rebalance (everyone pauses, not just the affected partitions) — see the next section for how CooperativeSticky avoids the full stop-the-world pause in production consumers.

offset:06

Consumer groups & rebalancing

The mechanism that turns "here's a log" into "here's a horizontally scalable, fault-tolerant worker pool."

Inside one consumer group, Kafka guarantees each partition is owned by exactly one consumer at a time. This is where your parallelism ceiling comes from: a topic with 6 partitions can be usefully consumed by at most 6 active consumers in one group — a 7th sits idle. Fewer consumers than partitions is fine (some consumers just own more than one partition); more consumers than partitions wastes resources.

Sizing rule of thumb

Partition count should be ≥ the maximum number of consumer instances you ever expect to run concurrently for that group. Under-provisioning partitions is the most common reason a "scale out the consumers" fix doesn't actually add throughput.

What triggers a rebalance

  • A consumer joins or leaves the group (deploy, crash, scale event).
  • A consumer misses max.poll.interval.ms between polls — the group coordinator assumes it's stuck and evicts it, even if the process is technically alive.
  • Partition count on the topic changes.

During a classic (eager) rebalance, every consumer in the group stops consuming while partitions are reassigned — a "stop the world" pause. Modern assignors reduce this:

  • Range / RoundRobin — original strategies, always eager (full stop-the-world).
  • Sticky — minimizes partition movement between rebalances, still eager.
  • CooperativeSticky — incremental: only the specific partitions that need to move are paused/reassigned; everyone else keeps consuming. Preferred default in modern clients.

Avoiding unnecessary rebalances

A rolling deploy that bounces every consumer pod one at a time can trigger a rebalance storm. Static membership (group.instance.id) tells Kafka "this consumer will be back — hold its partition assignment" instead of treating a brief restart as a leave-then-rejoin.

🎯

"How would you handle rebalance storms in production?" — Static membership for planned restarts, CooperativeSticky assignor to avoid full stop-the-world pauses, and tuning max.poll.interval.ms high enough that legitimate slow batches don't get mistaken for a dead consumer — while keeping session.timeout.ms low enough to still detect real failures quickly.

Delivery semantics — honestly

Most candidates say "Kafka supports exactly-once" and stop there. That's the wrong level of the story.

GuaranteeHow you get itWhat breaks
At-most-onceCommit the offset before processing the record.Crash after commit but before processing finishes → record is silently skipped.
At-least-onceCommit the offset after successful processing (the default posture for most manual-commit consumers).Crash after processing but before commit → the record gets reprocessed on restart. Your downstream must tolerate duplicates.
Exactly-onceIdempotent producer (dedupes retries) + transactions (atomic multi-partition writes) + read_committed consumers — or, cheaper in practice: at-least-once delivery plus an idempotent consumer that upserts by a natural key.Only holds end-to-end if every hop in the pipeline (including any external side effects like a DB write or an email send) is also idempotent. Kafka transactions guarantee exactly-once within Kafka, not for arbitrary external systems.
The honest answer for interviews

Kafka gives you exactly-once semantics for Kafka-to-Kafka pipelines (e.g. Kafka Streams read-process-write). The moment you write to an external system (a database, an email API, a payment gateway) inside that processing step, true exactly-once requires that external write to be idempotent too — Kafka can't make a non-Kafka side effect atomic with an offset commit for free.

Hands-on exercises

All exercises use the running orders topic example. Difficulty badge = replication factor you'll be reasoning about, not literal RF in every case.

01First log, first offsets

RF=1 · warm-up

Objective: see offsets get assigned in real time and prove they're per-partition, not global.

Steps
  1. Bring up the single-broker cluster (Section 04).
  2. Create orders with 3 partitions, RF 1.
  3. Open a console producer without a key and send 8–10 short messages.
  4. In a second terminal, consume with --from-beginning --property print.partition=true --property print.offset=true.
Show solution

Create the topic:

docker exec -it kafka kafka-topics --bootstrap-server localhost:9092 \
  --create --topic orders --partitions 3 --replication-factor 1

Terminal 1 — producer (no key, just type 8–10 lines, one per Enter):

docker exec -it kafka kafka-console-producer \
  --bootstrap-server localhost:9092 --topic orders

Terminal 2 — consumer with partition/offset visible:

docker exec -it kafka kafka-console-consumer \
  --bootstrap-server localhost:9092 --topic orders --from-beginning \
  --property print.partition=true --property print.offset=true

Expected: you'll see something like Partition:0 Offset:0, Partition:1 Offset:0, Partition:2 Offset:0 — offset 0 shows up three times because it's scoped per partition, not per topic. Kafka doesn't use one global counter because that would force every append across every partition to serialize through a single point — killing the parallelism partitions exist to provide.

Which offsets repeat across different partitions? Why doesn't Kafka just use one global counter for the whole topic?

02Keys and ordering

RF=1 · warm-up

Objective: prove per-key ordering only holds when you actually key your records.

Steps
  1. Using the keyed producer (parse.key=true), send several events for order-1 and order-2 interleaved, e.g. order-1:created, order-2:created, order-1:paid, order-2:paid.
  2. Consume with partition + offset printed. Confirm all order-1 events land on the same partition, in send order.
  3. Repeat without keys and observe the distribution change.
Show solution

Keyed producer:

docker exec -it kafka kafka-console-producer \
  --bootstrap-server localhost:9092 --topic orders \
  --property "parse.key=true" --property "key.separator=:"

Type these lines (order matters — send interleaved):

order-1:created
order-2:created
order-1:paid
order-2:paid
order-1:shipped
order-2:shipped

Consume with partition + offset printed:

docker exec -it kafka kafka-console-consumer \
  --bootstrap-server localhost:9092 --topic orders --from-beginning \
  --property print.key=true --property print.partition=true --property print.offset=true

Expected: every order-1 record shows the same partition number, and within that partition their offsets appear in the exact order you sent them (created → paid → shipped). order-2 lands on its own (possibly different) partition, same rule. Repeat without --property parse.key=true and you'll see the sticky partitioner batch several unkeyed records onto one partition before rotating — a different, non-deterministic distribution.

If you later increase partition count on this topic, what happens to the ordering guarantee for keys that were already hashed to old partitions?

03Consumer group scaling & the idle consumer

RF=1 · core

Objective: watch partition assignment change live as you scale a group past its partition count.

Steps
  1. Start one consumer in group order-processors on orders (3 partitions). Run --describe --group order-processors — it owns all 3.
  2. Start a second consumer in the same group. Re-run describe: partitions split roughly 2/1.
  3. Start a third — each consumer now owns exactly one partition.
  4. Start a fourth. Describe again.
Show solution

Open 4 separate terminals, run this in each one (same group, one at a time so you can describe in between):

docker exec -it kafka kafka-console-consumer \
  --bootstrap-server localhost:9092 --topic orders \
  --group order-processors

After each new consumer joins, in a 5th terminal:

docker exec -it kafka kafka-consumer-groups \
  --bootstrap-server localhost:9092 --describe --group order-processors

Expected: 1 consumer → owns partitions 0,1,2. 2 consumers → roughly 2/1 split. 3 consumers → 1 partition each. The 4th consumer's row shows up with no PARTITION assigned (or is simply absent from the partition-owner rows) — it's registered in the group but idle, contributing nothing. In production you wouldn't add partitions just to feed one more idle consumer unless you'd already sized for that headroom — you'd only add partitions if you have a genuine throughput or parallelism need beyond 3; otherwise scale back to 3 consumers and use the 4th elsewhere.

What does the 4th consumer's row look like in the describe output? What would you actually do about it in production — add partitions, or not?

04Watch lag grow and drain

RF=1 · core

Objective: build intuition for what "consumer lag" means operationally.

Steps
  1. Start a consumer in group order-processors, then kill it (Ctrl+C) while leaving the group registered.
  2. Keep producing 50–100 messages with the console producer (or a small loop script).
  3. Run --describe --group order-processors repeatedly — watch LOG-END-OFFSET climb while CURRENT-OFFSET stands still, growing LAG.
  4. Restart the consumer and watch LAG drain back to 0.
Show solution

Start then kill the consumer (Ctrl+C leaves its offset registered in the group):

docker exec -it kafka kafka-console-consumer \
  --bootstrap-server localhost:9092 --topic orders --group order-processors
# Ctrl+C after a few seconds

Produce a burst while it's dead — simplest is pasting many lines into a producer, or loop it:

for i in $(seq 1 80); do echo "msg-$i"; done | docker exec -i kafka \
  kafka-console-producer --bootstrap-server localhost:9092 --topic orders

Watch lag climb:

docker exec -it kafka kafka-consumer-groups \
  --bootstrap-server localhost:9092 --describe --group order-processors

Then restart the same consumer command from step 1 and re-run describe repeatedly — LAG should fall back to 0 as CURRENT-OFFSET catches up to LOG-END-OFFSET.

On the reflection question: alert on absolute lag only if your traffic is roughly steady — on a bursty topic, a fixed threshold (e.g. "alert if lag > 10,000") either fires constantly during normal bursts or is set so high it misses a genuinely stuck consumer during a quiet period. Lag growth rate, or lag measured in time-to-drain (lag ÷ current consume rate), adapts to the traffic shape instead of assuming it's constant.

In a real system, what would you alert on — absolute lag, or lag growth rate? Why might a fixed lag threshold be wrong for a topic with bursty traffic?

05Kill the leader — replication & failover

RF=3 · advanced

Objective: watch leader election happen for real, not just read about it.

Steps
  1. Bring up the 3-broker cluster (Section 04).
  2. Create orders with 3 partitions, replication factor 3.
  3. Run --describe --topic orders — note which broker leads partition 0.
  4. Keep a console producer/consumer running against that topic in separate terminals so you can see live impact.
  5. Run docker stop kafka-<leader-id> for the broker leading partition 0.
  6. Immediately re-run describe — a new leader should already be elected from the ISR.
Show solution

Bring up the cluster and create the topic:

docker compose -f docker-compose-cluster.yml up -d
docker exec -it kafka-1 kafka-topics --bootstrap-server localhost:9092 \
  --create --topic orders --partitions 3 --replication-factor 3

Check who's leading partition 0:

docker exec -it kafka-1 kafka-topics --bootstrap-server localhost:9092 \
  --describe --topic orders

Note the Leader: broker id in the partition 0 row, e.g. Leader: 2. In two more terminals, keep traffic flowing:

# producer
docker exec -it kafka-1 kafka-console-producer --bootstrap-server localhost:9092,localhost:9094,localhost:9095 --topic orders
# consumer
docker exec -it kafka-1 kafka-console-consumer --bootstrap-server localhost:9092,localhost:9094,localhost:9095 --topic orders

Kill the leader (substitute the container matching the leader id you found, e.g. kafka-2):

docker stop kafka-2

Re-describe from a still-running broker:

docker exec -it kafka-1 kafka-topics --bootstrap-server localhost:9092 \
  --describe --topic orders

Expected: Leader: is now one of the other two broker ids, and Isr: shrinks by one. Producer/consumer terminals typically show a brief pause or a couple of retriable errors logged internally, then resume on their own — you shouldn't need to restart them. The new leader is chosen by the controller from whichever replicas were still in the ISR at the moment of failure — an out-of-sync replica is not eligible, which is exactly the "unclean leader election" trade-off from the theory section.

Did your producer/consumer terminals hiccup, error, or just briefly pause? What determines which of the two remaining replicas becomes the new leader?

06acks=0 vs acks=all — engineer some data loss

RF=3 · advanced

Objective: feel the acks trade-off instead of just quoting it.

Steps
  1. On the 3-broker cluster, create a topic with RF 3.
  2. Produce a burst of numbered messages (msg-1 … msg-500) with --producer-property acks=0, and immediately docker stop the leader broker mid-burst.
  3. Count how many messages actually made it (consume from beginning, from a fresh group).
  4. Restart the cluster fresh, repeat the exact same test with acks=all and min.insync.replicas=2.
Show solution

Create the topic (RF 3, min ISR set for the acks=all run):

docker exec -it kafka-1 kafka-topics --bootstrap-server localhost:9092 \
  --create --topic durability-test --partitions 1 --replication-factor 3

Run A — acks=0, kill the leader mid-burst (open two terminals, run these close together):

# terminal 1
for i in $(seq 1 500); do echo "msg-$i"; done | docker exec -i kafka-1 \
  kafka-console-producer --bootstrap-server localhost:9092 --topic durability-test \
  --producer-property acks=0
# terminal 2, fired partway through terminal 1's loop
docker stop kafka-<leader-id>

Count what survived, from a fresh group so nothing's cached:

docker exec -it kafka-1 kafka-console-consumer \
  --bootstrap-server localhost:9092 --topic durability-test --from-beginning \
  --timeout-ms 5000 | wc -l

Run B — tear down, bring the cluster back up fresh, recreate the topic, repeat with:

--producer-property acks=all --producer-property min.insync.replicas=2

Expected: run A loses some tail of messages that were still sitting in the leader's page cache (never replicated) when it died — count comes in under 500. Run B's count should land at exactly 500, because the producer blocked on each batch until 2 ISR members had it. The cost you're measuring is producer-side latency/throughput — time the whole loop with time on both runs and compare; acks=all will visibly take longer per batch.

Was the message count different between the two runs? What did acks=all cost you in exchange for that difference — measure it.

07Idempotent producer vs. duplicate retries

RF=2 · advanced

Objective: see broker-side dedup happen (or not) under retry conditions.

Steps
  1. Produce a batch without idempotence enabled, using a script that retries on transient errors — briefly restart the broker mid-send to force retries.
  2. Count exact-match duplicate values on the consumer side.
  3. Repeat with enable.idempotence=true and compare duplicate counts.
Show solution

Create a small topic (RF 2 on the cluster from Section 04's 3-broker setup):

docker exec -it kafka-1 kafka-topics --bootstrap-server localhost:9092 \
  --create --topic idem-test --partitions 1 --replication-factor 2

Run A — no idempotence, force retries by restarting the leader broker mid-send:

# terminal 1 — deliberately allow retries without idempotence
for i in $(seq 1 200); do echo "evt-$i"; done | docker exec -i kafka-1 \
  kafka-console-producer --bootstrap-server localhost:9092 --topic idem-test \
  --producer-property enable.idempotence=false --producer-property retries=10 \
  --producer-property acks=all
# terminal 2, mid-burst
docker restart kafka-<leader-id>

Count exact-duplicate values:

docker exec -it kafka-1 kafka-console-consumer \
  --bootstrap-server localhost:9092 --topic idem-test --from-beginning \
  --timeout-ms 5000 | sort | uniq -c | sort -rn | head

Run B — same steps, but with --producer-property enable.idempotence=true, fresh topic.

Expected: run A's uniq -c output shows some lines with count >1 — the same evt-N appended twice because a retry fired after the original send had actually already succeeded. Run B should show every value with count exactly 1. On the reflection question: no — idempotence dedupes at the (producer-ID, partition, sequence-number) level, which only catches the broker seeing literally the same retried bytes twice. If your application code calls producer.send() a second time for the same logical event (e.g. a retry at the application layer, not the Kafka client layer), that's a brand new send with a new sequence number — indistinguishable from a genuinely new event as far as the idempotent producer is concerned.

Idempotent producers dedupe retries — but do they protect you if your application calls send() twice for the same logical event? Why or why not?

08Whiteboard: design an order pipeline

RF=3 · design

Objective: the interview-format exercise — no code, a short written design.

Prompt

Design the Kafka layer for an e-commerce order pipeline. order-service emits order.created, order.paid, order.shipped, order.cancelled. Downstream: inventory (must never double-decrement stock), notifications (best-effort, can lose the odd message), and a data warehouse (needs full replay capability for backfills).

Answer at minimum
  • Topic(s) and partition key — one topic per event type, or one topic with an event-type field? Justify it.
  • Partition count and what it's sized against.
  • Consumer group layout for the three downstream systems.
  • Which system needs exactly-once-ish guarantees, and how you'd actually build that (idempotent upsert key vs. Kafka transactions).
  • Retention policy per topic and why.
Show a model answer

Topic(s) and key: one topic, order-events, with an event_type field in the payload rather than four separate topics. Keeping every event for an order in one topic, keyed by order_id, guarantees the full lifecycle (created → paid → shipped → cancelled) is strictly ordered on one partition — split across topics and you'd need cross-topic coordination to reconstruct order-of-events, which defeats the purpose. Split into separate topics only if downstream systems need to subscribe to just one event type without filtering — not the case here, since all three consumers care about the full lifecycle.

Partitions: size for peak produce throughput first (say 12, if that comfortably covers projected peak order volume with headroom), then check it's ≥ the largest consumer group's max instance count. order_id as key keeps per-order ordering regardless of count.

Consumer groups: three independent groups — inventory-service, notification-service, warehouse-sink — each with its own offsets, scaled independently (inventory needs low lag, warehouse can run as a periodic batch job well behind).

Exactly-once-ish: inventory is the one that actually needs it (must never double-decrement stock). The practical fix is not Kafka transactions here — it's an idempotent consumer: inventory-service upserts stock adjustments keyed by order_id + event_type (e.g. "have I already decremented stock for order-123's `order.paid` event?" via a dedup table or a unique constraint) so a reprocessed message after a crash-before-commit is a no-op. Notifications stay best-effort with no dedup — an occasional double-send is an acceptable cost, not worth the complexity.

Retention: time-based retention (e.g. 7 days) is enough for inventory and notifications, which only ever need to catch up on recent lag. The warehouse sink's "full replay for backfills" requirement is the one that actually needs longer retention or a separate long-retention topic — either bump order-events' retention to cover your backfill window, or have the warehouse consumer also feed from a compacted or long-retention archival copy rather than stretching the primary topic's retention for everyone.

There's no single "correct" answer here — the value is in defending each choice under pushback (e.g. "why not RF for exactly-once instead of an idempotent consumer?", "why not split by event type?"). If your reasoning matches the trade-offs above even with different specific numbers, you're in good shape.

This is the exercise most likely to show up, reworded, in an actual system design interview. Write the answer as if defending it to a skeptical panel.

offset:09

Interview corner

Rapid-fire questions worth being able to answer in under 60 seconds each, plus the NFRs strong candidates raise unprompted.

Rapid fire

  • Why partitions instead of just more topics? Partitions are the unit of parallelism and ordering within one logical stream — splitting into separate topics loses the "one topic, many independent readers" model and forces consumers to know about N topics instead of one.
  • What happens when the broker holding a partition's leader dies? The controller (KRaft quorum) detects it via missed heartbeats, elects a new leader from the ISR, and clients refresh their metadata and reconnect to the new leader — typically sub-second to a few seconds of unavailability for that partition only.
  • Kafka vs. RabbitMQ vs. SQS — when would you choose which? Kafka: high-throughput event streams, need replay, many independent consumers, ordering per key. RabbitMQ/AMQP: complex routing topologies, per-message priority/TTL, work-queue semantics where a message truly disappears once handled. SQS: fully managed, simple decoupling, don't want to operate infrastructure, don't need replay or strict ordering at scale.
  • What does min.insync.replicas actually do? With acks=all, it's the minimum number of ISR members (including the leader) that must ack before a write succeeds. Set it to 2 with RF 3 and you can tolerate one broker failure without either losing durability or blocking writes.
  • How do you reprocess the last 24 hours of a topic without affecting live consumers? Start a new consumer group, seek/reset it to a timestamp offset (--to-datetime), and let it run independently — the live group's offsets are untouched.

NFRs to raise before being asked

Throughput
Partition count, batching/compression, expected peak vs. sustained rate.
Durability
Replication factor, acks, min.insync.replicas — state the trade-off explicitly.
Ordering
What must be ordered (per key), what doesn't need to be.
Scalability
Can you add partitions/brokers later without a redesign? What breaks if you do?
Fault tolerance
What survives a single broker loss? A single AZ loss?
Observability
Consumer lag, ISR shrink events, under-replicated partitions — what pages someone.
