Design a Notification
System

A multi-channel platform (push, email, SMS) that lets any Upstream Service say "tell this user something happened" — and reliably gets it delivered, without duplicates, without spamming them, and without a flaky third-party SMS provider becoming the reason checkout emails stop going out.

Core hard problem: fan-out + delivery guarantees under partial failure
Consistency model: at-least-once, idempotent consumers
Companion code: notification_dispatcher.py
01

Problem Framing

Strip away the bell icon and this is a fan-out and delivery-tracking system sitting between "an event happened somewhere in the company" and "a specific human was told, on a channel they chose, exactly once from their point of view." The event source (order service, comment service, marketing tool) shouldn't know or care whether the user prefers push or email, whether their device token is stale, or whether Twilio is degraded right now — it just says "tell user 42 their order shipped" and moves on.

The genuinely hard part isn't sending one notification — that's a single API call to a provider. It's sending the right one, once, to the right channel, at scale, when a third of your outbound dependencies are third-party services you don't control and can't make faster. A single celebrity comment or a "your flight is delayed" broadcast can fan out to millions of deliveries in seconds, and a slow SMS provider must never be allowed to back up the push queue.

The framing that unlocks the design
Every notification has two independent lifecycles: "was the intent to notify recorded" (fast, durable, our problem) and "did the provider actually deliver it" (slow, unreliable, largely someone else's infrastructure). Separating those — return success the instant the campaign is durably queued, then dispatch asynchronously from a Worker pool with its own retry/backoff — is what keeps a Twilio outage from ever touching the API Gateway's latency, exactly like splitting "hold" from "confirm" in a booking system.
02

Clarifying Questions

Ask these before designing anything — they materially change the architecture.

?
Scope: Transactional only (OTP, order confirmation, password reset), or also marketing/broadcast campaigns? → Assume both — transactional and marketing share the same pipeline but get separate priority queues (§7).
?
Channels: Push, email, SMS — which ones? → All three, each dispatched by the same Worker pool to a different provider — APN/FCM, SMTP, Twilio (§7).
?
Fan-out shape: Mostly 1:1 (a single user's order shipped), or do we need to support 1:N broadcast to millions (e.g. "server maintenance tonight")? → Both — broadcast is the multiplier that stresses the architecture, so design for it explicitly.
?
Delivery guarantee: Is strict exactly-once required, or is at-least-once with client-side dedup acceptable? → At-least-once + a Redis dedup cache (§8.3) — true exactly-once across our DB and a third-party provider isn't achievable without a distributed transaction neither side supports.
?
User control: Do users need per-channel opt-outs and quiet hours? → Yes — and opt-out correctness is a compliance requirement, not a nice-to-have (§8.4).
?
Ordering: Does relative delivery order across notifications matter? → No strict cross-notification ordering, except within one logical thread (e.g. chat replies), which is out of scope here.
?
Build vs. integrate for channels: Do we operate our own SMTP/SMS infrastructure? → Integrate with SMTP for email, APN/FCM for push, and Twilio for SMS; we own the Notification Service, queues, and Worker pool orchestrating them — not the wire protocol to devices.
03

Functional & Non-Functional Requirements

Functional

  • An Upstream Service triggers a campaign for one user, a segment, or a full broadcast
  • Deliver across push, email, and SMS (§7)
  • Per-channel opt-outs and quiet hours, honored per user (§6 user table)
  • Immediate and scheduled sends, the latter driven by the Scheduler Cron Job
  • Per-notification delivery status: SENT / FAILED / SUPPRESSED
  • In-app notification history, served by reading stored notifications rows
  • Admin: campaign creation, audience segmentation via segments

Non-Functional

  • At-least-once delivery with a dedup check that makes redelivery safe
  • Low latency for transactional — OTP reaches the provider in p99 < 3s
  • Priority isolation — a mega-broadcast on the standard lane never delays a transactional send on the high-priority lane
  • High burst throughput — millions of fan-out deliveries within minutes
  • No silent drops — bounded retries, then a durable, queryable FAILED status
  • Rate limiting per user to prevent notification fatigue / spam
  • Immediate honoring of opt-outs — never send after unsubscribe
The CAP framing to say out loud in an interview
The Notifications DB as a whole is fine being read with a few seconds of replica lag for things like campaign-status dashboards — a status that's briefly stale is invisible to anyone. The user-preference / opt-out check inside the Worker (§8.4) is the one read we bias hard toward freshness: it hits the primary directly, immediately before dispatch, never a lagging replica — reading a stale "still subscribed" flag and sending anyway is a compliance and trust failure, not just a UX rough edge.

This reframes the problem exactly like the ticketing waiting room: don't try to send 83,000 QPS to Twilio, queue and throttle to what each provider will actually accept, and let the queue — not the provider's rate limiter — absorb the burst.
05

API Design

Every call below enters through the API Gateway (authn, rate limiting) and is handled by the Notification Service — the single component every upstream caller talks to (§7).

POST/campaigns  { target: "user"|"segment"|"all", users / segmentId, channel, messageTemplate, priority, scheduledTime? }
Create a campaign — one user, a segment, or a full broadcast. Returns a campaignId immediately once the Notification Service has durably written the row to the Notifications DB. Idempotency-Key header required. If scheduledTime is set, the Scheduler Cron Job picks it up later (§8.1) instead of enqueueing it now.
GET/campaigns/{campaignId}/status
Aggregate status across the campaign's fanned-out notifications rows: queued / sent / failed / suppressed counts.
GET/users/{userId}/notifications?cursor=...
Paginated in-app notification history for a user, read straight from the notifications table.
PATCH/users/{userId}/preferences  { optOutChannels?, quietHoursStart?, quietHoursEnd?, timezone? }
Updates the user row in the Notifications DB — read by every Worker before it dispatches to a provider (§8.3).
POST/webhooks/provider/{provider}  { signed payload }
Late delivery receipts (e.g. an email bounce that arrives after the initial send succeeded) from SMTP/APN-FCM/Twilio. Signature-verified (§12); can transition a notifications row from SENT to FAILED after the fact.
Why campaign creation and delivery are separate steps
POST /campaigns returns as soon as the Notification Service has written the campaign row and pushed a job onto the High-Priority or Standard Queue — it never waits on SMTP, APN/FCM, or Twilio. The actual per-user send happens later in the Worker pool. This is what keeps an Upstream Service's request (e.g. Order/Auth confirming a purchase) from ever blocking on a third-party provider's latency.

Data Modeling

Deliberately one store, four tables — a single Notifications DB (Postgres works; the shapes below map just as cleanly onto MongoDB collections) rather than a polyglot spread across three databases. At this system's actual write pattern — campaigns are created far less often than notifications are fanned out, but neither approaches the row-CAS contention a seat-inventory table sees — one well-indexed relational store keeps operational complexity down without becoming a bottleneck.

TableHoldsWritten by
campaignsThe intent — one row per POST /campaigns call, whether it targets one user or ten millionNotification Service (create), Scheduler Cron Job (status transitions)
segmentsSegment membership — one row per (segmentId, userId), the audience a campaign's target can point atWhatever upstream system manages audiences (out of scope here)
notificationsThe fanned-out, per-user delivery unit — this is what Workers read from the queue and update after each attemptNotification Service (create, on fan-out), Workers (status update)
userPreferences: opted-out channels, quiet hours, timezone — read by every Worker before it dispatchesUsers, via PATCH /users/{id}/preferences

Core Schema

CREATE TABLE campaigns (
  campaign_id       BIGINT PRIMARY KEY,
  target            VARCHAR(16)  NOT NULL,   -- 'user' | 'segment' | 'all'
  users             JSONB,                   -- inline target list for small/direct sends
  message_template  TEXT         NOT NULL,
  channel           SMALLINT     NOT NULL,   -- 0 push 1 email 2 sms
  priority          SMALLINT     NOT NULL DEFAULT 0, -- 0 standard 1 high -- picks the queue at fan-out (§7)
  scheduled_time    TIMESTAMPTZ,             -- null = send now
  status            SMALLINT     NOT NULL DEFAULT 0, -- 0 pending 1 processing 2 completed
  created_at        TIMESTAMPTZ  NOT NULL DEFAULT now()
);

CREATE TABLE segments (
  segment_id  BIGINT NOT NULL,
  user_id     BIGINT NOT NULL,
  PRIMARY KEY (segment_id, user_id)
);

-- one row per (campaign, user) -- the fan-out unit the Worker pool actually processes
CREATE TABLE notifications (
  id           BIGINT PRIMARY KEY,
  campaign_id  BIGINT       NOT NULL REFERENCES campaigns(campaign_id),
  user_id      BIGINT       NOT NULL,
  channel      SMALLINT     NOT NULL,
  message      TEXT         NOT NULL,
  status       SMALLINT     NOT NULL DEFAULT 0, -- 0 queued 1 sent 2 failed 3 suppressed
  updated_at   TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX ON notifications (campaign_id, status);   -- powers GET /campaigns/{id}/status

CREATE TABLE "user" (
  user_id             BIGINT PRIMARY KEY,
  opt_out_channels    SMALLINT[]  NOT NULL DEFAULT '{}',
  quiet_hours_start   TIME,
  quiet_hours_end     TIME,
  timezone            VARCHAR(64) NOT NULL DEFAULT 'UTC'
);
Where the dedup guarantee actually lives
This architecture's fast-path dedup is Redis (§8.3), not a database UNIQUE constraint — a Worker checks a short-TTL key before processing a notification and skips it on a hit. The notifications.status column is the durable backstop: a Worker that dispatches after a cache miss still won't double-count, because it only transitions a row out of queued once, and a second attempt on an already-sent row is a no-op update, not a resend.
07

Architecture

Where this comes from

A naive first cut has the API server call SMTP/APN-FCM/Twilio inline, synchronously, inside the request handler — it works in a demo and falls over the first time a provider is slow, or someone triggers a broadcast to 100K users in one HTTP request. The fix that matters is decoupling "record the intent" from "actually deliver it" with a queue in between, so a calling service's request never blocks on a third-party's latency. Below is the resulting design.

Final Design

The API Gateway and Notification Service stay thin and synchronous; everything that can be slow — provider calls, audience fan-out, scheduled sends — happens past the queues, in the Worker pool.

Walking the request through, end to end:

  1. An Upstream Service (order confirmation, auth/OTP, a marketing tool) calls the API Gateway, which authenticates and rate-limits the call before handing it to the Notification Service.
  2. The Notification Service durably writes the campaigns row (and, for a segment/broadcast target, the fanned-out notifications rows) to the Notifications DB, then pushes a job onto the High Priority Queue (transactional) or Standard Queue (bulk/marketing) based on the campaign's declared priority — and returns immediately. It never waits on a provider.
  3. If the campaign has a scheduledTime in the future, the Notification Service does not enqueue it yet — the Scheduler Cron Job polls the Notifications DB for due campaigns and hands them to the Notification Service to enqueue at the right time (§8.1).
  4. A pool of Workers, shared across both queues but drained with priority given to the High Priority Queue, pulls jobs. For each one it checks Redis for a rate-limit token and a dedup-cache hit (§8.3), reads that user's preferences from the Notifications DB, and — if allowed — dispatches to the right provider: SMTP for email, APN/FCM for push, Twilio for SMS.
  5. The Worker writes the outcome back to the notifications row as SENT, FAILED, or SUPPRESSED (blocked by an opt-out or quiet hours — never attempted at all) (§8.4).
Why two priority lanes instead of one queue — or four
A single shared queue lets a 10M-user marketing campaign sit in front of someone's login OTP — unacceptable. Per-channel queues (one for push, one for email, one for SMS) would isolate providers from each other, but it's more infrastructure to run for a benefit this design doesn't need yet: the two-lane split by priority is the one dimension that actually matters at this scale — protecting transactional sends from bulk ones — while a single Worker pool handling all channels keeps operational surface area small. See §9 for the honest trade-off this makes.
08

Component Deep Dives

8.1 — Scheduler Cron Job & Fan-out

Two paths write to the queues, and both go through the Notification Service rather than touching Redis or the queues directly:

  • Immediate sends (the common case): the Notification Service fans a campaign out to notifications rows and enqueues them in the same request that created the campaign.
  • Scheduled sends: the campaign is written with a future scheduledTime and status = pending. The Scheduler Cron Job runs on a fixed interval (e.g. every 30s), queries campaigns WHERE status = 'pending' AND scheduled_time <= now(), and hands each due campaign back to the Notification Service to fan out and enqueue — then flips it to processing so the next tick doesn't pick it up again.

A broadcast to "all premium users in the EU" still can't be one giant query held open while millions of rows stream out — the Notification Service paginates the segment query (keyset-paginated by user_id, e.g. 1,000 per page) when it fans a campaign out to notifications rows, rather than materializing the whole audience in memory at once.

Guarding against the cron job firing a campaign twice
Two Scheduler instances (for HA) could both pick up the same due campaign on the same tick. The fix is the same CAS discipline used everywhere else in this course: UPDATE campaigns SET status='processing' WHERE campaign_id=$1 AND status='pending' — only the instance that actually flips the row proceeds to fan it out; the other sees 0 rows affected and skips it.

8.2 — Priority Queues & the Worker Pool

Workers pull from both the High Priority and Standard queues, but are configured to prefer the high-priority one — e.g. drain up to K high-priority jobs before taking one standard job, or run separate consumer counts per queue so high-priority always has spare capacity. Because it's one pool handling every channel, a Worker branches on the notification's channel field to decide which provider client to call (§9 discusses the trade-off this makes vs. per-channel isolation).

8.3 — Redis: Token Bucket & Dedup Cache

Before dispatching, a Worker makes two fast Redis checks — not a query per provider call:

// (a) token bucket — has this user already received too many notifications recently?
boolean allowSend(String userId) {
    String key = "rate:" + userId;
    long count = redis.incr(key);
    if (count == 1) redis.expire(key, Duration.ofHours(1));
    return count <= MAX_PER_HOUR;          // e.g. 20 — fatigue guard
}

// (b) dedup cache — has this exact notification already been processed?
boolean isDuplicate(Long notificationId) {
    String key = "dedup:" + notificationId;
    // SET key 1 NX EX 3600 -- true only the FIRST time this key is set
    boolean firstTime = redis.set(key, "1", SetArgs.nx().ex(3600));
    return !firstTime;                      // already present = a redelivery, skip it
}
Why a cache, not just the DB, for dedup
A SETNX against Redis is sub-millisecond and takes load off the Notifications DB entirely for the common case. It's a fast-path, not the only guarantee: the 1-hour TTL comfortably outlives any realistic queue redelivery window, and §6's notifications.status column is the durable backstop if a Worker ever dispatches after a cache miss on a genuine duplicate — a second write to an already-sent row is a no-op, not a resend.

8.4 — Preference Check & Status Writeback

After the Redis checks pass, the Worker reads the user row for opt-outs and quiet hours immediately before dispatch — not earlier, since a campaign may have sat in the Standard Queue for minutes and preferences can change in that window:

CheckIf it failsResulting status
Channel is in user.opt_out_channelsNever call the providerSUPPRESSED
Current time (in the user's timezone) falls inside quiet_hours_start–quiet_hours_endNever call the provider, unless the campaign is transactional (§14)SUPPRESSED
Provider call failsRetried per §8.5's classification; exhausted retries mark it terminalFAILED
Provider call succeeds—SENT

Keeping SUPPRESSED distinct from FAILED matters operationally — a spike in FAILED means "a provider is unhealthy, page someone" (§13), while a spike in SUPPRESSED is expected and healthy (it means opt-outs and quiet hours are working).

8.5 — Provider Dispatch & Retry Classification

Each provider call is wrapped with the same transient-vs-permanent error classification regardless of which of SMTP, APN/FCM, or Twilio the Worker is calling:

Error typeExampleAction
Transient5xx, timeout, connection resetRetry with exponential backoff: 1s → 5s → 30s, capped at N attempts, before marking FAILED
Permanent — bad targetInvalid/expired push token, hard-bounced email, disconnected numberNo retry — mark FAILED immediately, don't burn the retry budget on a request that can never succeed
Provider fully downSustained 5xx / connection failures across many sendsCircuit breaker trips for that provider; new sends on that channel fail fast to FAILED instead of queueing up behind a dead dependency

Trade-off Analysis

Two priority queues, one shared Worker pool (chosen)

✓ Bulk/marketing traffic can never starve transactional sends — the one isolation dimension that actually matters
✓ Far less infrastructure than per-channel queues — one pool, two topics
✗ Honest gap: a slow SMS provider can back up Workers that would otherwise be free to send push/email in the same priority lane

Per-channel queues (push/email/SMS each isolated)

✓ A degraded provider on one channel truly can't touch another
✗ 2× the queues, consumer groups, and scaling knobs to operate for a benefit this system doesn't need until channel-level incidents actually happen — the pragmatic choice here is to accept the coupling and mitigate it with per-provider timeouts/circuit breakers (§8.5) inside the shared pool, not a second dimension of queue splitting

Redis dedup cache + DB status as backstop (chosen)

✓ Sub-millisecond dedup check on the hot path, no DB round trip for the common case
✓ notifications.status still prevents a double-send even on a cache miss
✗ Not a hard guarantee the instant the TTL window is exceeded — mitigated by sizing the TTL well past any realistic redelivery delay

Database UNIQUE constraint as the only dedup mechanism

✓ Airtight, no TTL to size correctly
✗ Every dispatch attempt now needs a DB round trip in the hot path instead of a Redis lookup — throughput cost this design's scale (§4) doesn't need to pay

One Notifications DB, four tables (chosen)

✓ Simple to operate, easy joins for admin/reporting tooling (campaign status, per-user history)
✓ Matches this system's actual write pattern — heavy but not seat-inventory-CAS-level contention
✗ Needs sharding (e.g. by user_id on notifications) once write volume outgrows one primary

Polyglot: relational for campaigns, wide-column for notifications

✓ Scales the highest-write table independently
✗ A second storage technology to operate, backup, and monitor before this system has actually outgrown one well-indexed Postgres — premature for the scale in §4, worth revisiting only once sharding the single DB stops being enough

Failure Handling

  • A provider (SMTP/APN-FCM/Twilio) goes down mid-campaign: the circuit breaker for that provider trips (§8.5); in-flight Workers fail fast to FAILED instead of hanging, and the row can be reprocessed once the breaker's half-open probe confirms recovery.
  • A Worker crashes mid-send: the queue redelivers the job to another Worker instance. The Redis dedup cache (§8.3) usually catches the retry as a duplicate; even on a cache miss, the notifications.status update is a safe no-op if the row is already sent.
  • Redis is unavailable: the token bucket and dedup cache both degrade — the design falls back to sending without a fast rate-limit check (accepting a small burst risk) and relies on notifications.status alone for dedup, rather than blocking all sends. Correctness survives; only the cheap fast-path is lost.
  • Standard Queue backs up during a mega-broadcast: because Workers prioritize the High Priority Queue (§8.2), transactional sends keep flowing; the Standard backlog simply drains slower, which is the intended trade-off, not an incident.
  • The Scheduler Cron Job double-fires a scheduled campaign: the CAS status transition in §8.1 (WHERE status='pending') means only one instance's UPDATE succeeds — the second sees 0 rows affected and skips it.
  • Duplicate trigger from a buggy Upstream Service: the caller-supplied Idempotency-Key on POST /campaigns makes an accidental retry a no-op at the Notification Service, before it ever reaches fan-out.
12

Security

  • Trigger access: the API Gateway only accepts calls to POST /campaigns from trusted Upstream Services, authenticated via mTLS or short-lived service tokens — never open to arbitrary clients.
  • Webhook authenticity: every inbound delivery-receipt webhook is signature-verified against the provider's published secret before it's trusted to update a notifications row.
  • PII hygiene: message payloads are logged with PII fields redacted; provider request/response logs never persist full message bodies longer than needed for debugging.
  • Segment scoping: a campaign's segmentId is validated against the caller's own scope at the Notification Service — prevents one team's campaign tool from being able to blast a segment it doesn't own.
  • Self-inflicted spam protection: the API Gateway rate-limits the trigger endpoint itself, independent of the per-user Redis token bucket (§8.3), so an internal bug (e.g. a retry loop in another service) can't turn into an accidental spam storm.
  • Unsubscribe compliance: a preference change through PATCH /users/{id}/preferences is written to the user row synchronously and read fresh by the very next Worker dispatch (§8.4) — no propagation delay window. This is a legal requirement (CAN-SPAM/TCPA-style), not just good UX.
13

Observability

  • Status breakdown per campaign: live SENT / FAILED / SUPPRESSED counts from GET /campaigns/{id}/status — a FAILED spike pages on-call, a SUPPRESSED spike is informational.
  • Circuit-breaker state: live view of whether SMTP, APN/FCM, and Twilio are currently open/half-open/closed, with automatic alert on trip.
  • Queue depth & drain rate: High Priority and Standard Queue depth separately — a growing High Priority queue is the single most urgent signal in this system.
  • End-to-end latency: campaign creation → SENT, split by priority lane — the metric that actually reflects whether an OTP is landing on time.
  • Opt-out compliance audit: a hard alert (not just a dashboard) on any SENT row for a user whose opt_out_channels included that channel at send time — should always read zero.
  • Redis health: token-bucket and dedup-cache hit rates, and alerting on the degraded-mode fallback (§11) actually engaging.
  • Scheduler heartbeat: alert if the Scheduler Cron Job hasn't completed a tick in N minutes — a silent scheduler means every scheduled campaign is silently late.

Cross-Questions & Weak vs. Strong Answers

"How do you guarantee a user never gets the exact same notification twice?"

Weak
"We'd check if it was already sent before sending again."
Strong
"A naive check-then-send has the same race as check-then-book — two Workers can both check 'not sent yet' before either writes. Here it's two layers: a Redis SET NX EX dedup cache (§8.3) catches the vast majority of redeliveries in under a millisecond, and the notifications.status column (§6) is the durable backstop — a second write to an already-sent row is a no-op update, not a resend, even if the Redis check somehow missed it."

"A 10M-user marketing broadcast is clogging the pipeline and a transactional OTP is stuck behind it — what happened?"

Weak
"We'd give the OTP send higher priority in the code."
Strong
"Priority can't be a runtime hint on a shared queue — it has to be architectural. Transactional and bulk campaigns are routed to physically separate queues (§7) — High Priority and Standard — and Workers are configured to drain High Priority first. If both shared one queue, no priority field on the message would save the OTP from sitting behind 10M marketing sends; the isolation has to come from the queue topology, not application logic reading the queue."

"A user unsubscribes from marketing emails but gets one 10 minutes later anyway — how does that happen, and how do you prevent it?"

Weak
"The preference update must not have saved correctly."
Strong
"More likely: the notification was already sitting in the Standard Queue, created before the opt-out, and preferences were only checked once at fan-out time. The fix is that the Worker reads the user row fresh immediately before dispatch (§8.4), not at enqueue time — a campaign that sat queued for 10 minutes still gets an up-to-the-second freshness check, and an opted-out send is marked SUPPRESSED instead of going out."

"Workers aren't split per channel — what stops a slow SMS provider from starving push/email sends sitting in the same priority lane?"

Weak
"That can't happen since they're different notifications."
Strong
"It genuinely can — that's the honest trade-off from §9. A shared Worker pool per priority lane is simpler to run than per-channel isolation, but a Worker blocked on a slow Twilio call is a Worker not sending push. The mitigation is a tight per-provider timeout plus the circuit breaker (§8.5): once SMS is unhealthy, sends fail fast to FAILED instead of hanging, freeing that Worker for the next job — push/email — almost immediately. It's containment, not full isolation, and that's a deliberate simplicity-vs-blast-radius call, not an oversight."

"How would you support 'quiet hours' (no pushes 10pm–8am) without delaying someone's OTP that arrives at 11pm?"

Weak
"We'd just hold all notifications until quiet hours end."
Strong
"Quiet hours is a per-user field on the user row checked at dispatch (§8.4), and transactional campaigns (OTP, security alerts) are explicitly exempted from that check by campaign type — the same way the High Priority Queue exempts them from bulk-queue delay. A user's quiet-hours preference should never be able to silently delay a login code; that's a support ticket and a security concern, not a UX nicety."

"Your SMS provider goes fully down mid-campaign with thousands of sends in flight — what's the recovery story?"

Weak
"We'd wait for the provider to come back and retry everything."
Strong
"The circuit breaker (§8.5) trips after a failure-rate threshold, and new SMS sends fail fast to FAILED instead of piling up waiting on a dead dependency — that keeps Workers free for push/email in the same pool (previous question). Nothing is silently lost: every FAILED row is a durable, queryable record in notifications, so once the provider recovers (breaker half-opens and confirms health), a reprocessing job can re-enqueue exactly the rows still in FAILED for that campaign and channel — a deliberate, auditable retry, not a guess."
CODE

Companion Implementation — Notification Dispatcher

A working Python model of the Worker's per-notification pipeline from §8: Redis token bucket + dedup cache, a fresh preference read, provider dispatch with retry classification, and the SENT/FAILED/SUPPRESSED status writeback. A simulated broadcast with redelivered queue messages, opted-out users, and a flaky provider proves each outcome lands in the right bucket exactly once.

class Worker:
    """Pulls one job from a priority queue and runs it through the pipeline in §8."""

    def process(self, notification_id, user_id, channel):
        if self.redis.is_duplicate(notification_id):        # §8.3 dedup cache
            return "skipped_duplicate"

        if not self.redis.allow_send(user_id):             # §8.3 token bucket
            return self.requeue(notification_id)          # retry later, not a failure

        user = self.db.get_user(user_id)                  # §8.4 -- read fresh, not cached
        if self.is_suppressed(user, channel):
            return self.db.set_status(notification_id, "SUPPRESSED")

        try:
            self.providers[channel].send(user, self.db.get_message(notification_id))
            return self.db.set_status(notification_id, "SENT")
        except TransientError:
            return self.retry_with_backoff(notification_id)  # §8.5
        except PermanentError:
            return self.db.set_status(notification_id, "FAILED")
