URL Shortener — High-Level Design

A Bitly-style link shortener: create short aliases for long URLs and resolve billions of redirects per month with sub-100ms p99 latency.

Section 1

Problem Framing & Clarifying Questions

Restatement: We need to design a service that takes a long URL and returns a short, unique alias (e.g., bit.ly/3xK9pQ2). When a user visits the short URL, the service redirects them to the original long URL. The system must handle URL creation and — far more frequently — URL resolution (redirects) at scale, while supporting custom aliases, link expiration, and basic click analytics.

Clarifying questions a strong candidate would ask

  1. What's the expected scale — new links created per day, and redirects served per day?
  2. What's the read:write ratio? (This dominates the whole design.)
  3. Do short URLs need to be globally unique, or unique per user/workspace?
  4. Should users be able to pick a custom alias (vanity URLs)?
  5. Do links expire, or live forever by default?
  6. Do we need click analytics (count, geography, referrer, device), and how real-time does that need to be?
  7. Is this a single-region or globally-distributed user base? Any data residency constraints?
  8. What's the acceptable redirect latency (this is the hot path — users notice)?
  9. Do we need to support link editing/deactivation, and link ownership/auth?
  10. Any abuse/spam requirements (malicious URL detection, rate limiting per user)?
Assumptions locked in for this design:
  • Global uniqueness required, no per-user namespacing.
  • Custom aliases supported (opt-in), default is auto-generated.
  • Links default to no expiration, but expiration is a supported field.
  • Click analytics required but can be near-real-time (seconds-to-minutes lag acceptable) — decouples analytics from the redirect hot path.
  • Global user base, multi-region reads required; writes can tolerate more centralization.
  • Redirect latency target: p99 < 100ms server-side.
  • Basic auth for link creation/ownership; redirects are public/unauthenticated.
Section 2

Requirements

Functional Requirements

  • Must-have: Create short URL from long URL (auto-generated code). "As a user, I paste a long link and get a short one back instantly."
  • Must-have: Redirect short URL → long URL via HTTP 301/302. "As a visitor, clicking a short link takes me to the right page fast."
  • Must-have: Custom alias support. "As a marketer, I want bit.ly/summer-sale, not a random string."
  • Must-have: Link expiration (TTL). "As a user, I want promo links to stop working after a campaign ends."
  • Nice-to-have: Click analytics dashboard (counts, geo, referrer, device).
  • Nice-to-have: QR code generation per link.
  • Nice-to-have: Bulk link creation via API/CSV upload.

Non-Functional Requirements

NFRTarget
Availability99.99% for redirects (revenue/UX-critical path), 99.9% for creation
ConsistencyEventual for analytics; strong for code uniqueness at creation time
LatencyRedirect: p50 <30ms, p99 <100ms. Creation: p50 <100ms, p99 <300ms
Durability11 9's — a lost mapping breaks every distributed copy of that link forever
ScalabilityMust handle 10x traffic growth without redesign
Fault toleranceNo single point of failure in the redirect path

NFRs in tension

  • Strong consistency (uniqueness) vs. low write latency — resolved with a pre-generated key pool (§7) instead of a synchronous check.
  • Availability vs. consistency for analytics — choose AP over CP for click counters; losing a redirect to wait on a counter update is unacceptable.
  • Durability vs. cost — 11 9's implies multi-AZ/multi-region replication; justified because mapping loss is unrecoverable and breaks every shared copy of the link.
Section 3

Capacity Estimation (Back-of-the-envelope)

Assumptions: 100M new links/month; read:write ratio of 100:1 (typical for link shorteners).

Writes (creation)

100M/mo ÷ 30d ÷ 86,400s ≈ ~39 QPS avg
Peak (5x): ~195 QPS

Reads (redirects)

100:1 → 10B/mo ÷ 30 ÷ 86,400 ≈ ~3,860 QPS avg
Peak (5x): ~19,300 QPS

Storage

~400 bytes/record × 100M/mo ≈ 40GB/mo
5yr w/ indexes: ~3.6 TB

Bandwidth

Redirect response is small (301 + Location, ~200 bytes) → at 19,300 QPS peak, ~3.9 MB/s peak egress for redirects alone — trivial. Creation requests carry the long URL (~300 bytes in, ~50 out) — negligible at 195 QPS.

Cache size

Access is heavily skewed (Pareto-ish). Caching the hottest 20% of active links (~80% of read traffic): ~10M "hot" links × 400 bytes ≈ 4 GB — fits comfortably in a single Redis cluster's memory, so most reads never hit the database.

What breaks first at 10x traffic

At 10x, redirect QPS hits ~193,000 peak. The database read layer breaks first — even with caching, cache-miss traffic on cold/long-tail links overwhelms a single primary/replica set, requiring more shards and cache nodes/regions. The Key Pool Generator is second to break if writes hit ~2,000 QPS peak without enough parallel generator instances.

Section 4

API Design

POST/api/v1/links
// Request
{
  "long_url": "https://example.com/some/very/long/path?query=params",
  "custom_alias": "summer-sale",       // optional
  "expires_at": "2026-12-31T23:59:59Z" // optional
}

// Response 201
{
  "short_url": "https://bit.ly/3xK9pQ2",
  "short_code": "3xK9pQ2",
  "long_url": "https://example.com/...",
  "created_at": "2026-08-07T10:00:00Z",
  "expires_at": null
}

Idempotency: Client-supplied Idempotency-Key header, cached 24h. Auth: Required. Rate limit: Per-user token bucket (e.g. 100/min free tier).

GET/{short_code}

Returns 301 Moved Permanently (or 302 if temporary/A-B tested) with Location header. Auth: None — public by design. Rate limit: IP-based abuse throttling only.

GET/api/v1/links/{short_code}/stats
// Response 200
{
  "short_code": "3xK9pQ2",
  "total_clicks": 15234,
  "clicks_by_day": [{"date": "2026-08-06", "count": 812}],
  "top_referrers": [{"source": "twitter.com", "count": 4021}],
  "top_countries": [{"country": "US", "count": 6210}]
}

Auth: Required, owner-only. Pagination: clicks_by_day via ?from=&to=&cursor=.

DELETE/api/v1/links/{short_code}

Soft-delete (mark inactive) rather than hard-delete — short code isn't silently reusable and analytics history is preserved. Auth: Required, owner-only.

Section 5

Data Model

Link

short_code (PK), long_url, user_id (FK), created_at, expires_at, is_active, custom_alias (bool)

User

user_id (PK), email, plan_tier, created_at

ClickEvent

event_id, short_code (FK), timestamp, ip_hash, country, referrer, user_agent

Key access patterns driving the schema

  1. Redirect lookup by short_code — highest-QPS query, must be O(1)-ish → PK / KV key.
  2. List links by user_id — dashboard view → secondary index on user_id.
  3. Aggregate click counts by short_code over time — write-heavy, append-only, time-series-shaped.

SQL vs NoSQL — per-entity decision

We are explicitly not saying "NoSQL scales better" as a blanket justification — the choice is per-entity, driven by access pattern.

EntityStoreWhy
Link mappingKV store (DynamoDB/Cassandra-style)Single-key point lookup at very high QPS, flat data, no joins needed — exactly what KV stores optimize for.
User/accountRelational (Postgres)Low-volume, relationship-heavy, benefits from ACID (billing changes) — NoSQL adds complexity for no benefit here.
ClickEventWide-column / time-series (Cassandra / ClickHouse)Write-heavy, rarely updated, queried in aggregate — wrong shape for relational or the hot-path KV store.

Sharding / partitioning key

  • Link table: sharded by hash of short_code (avoids hot-spotting on sequential codes) — aligns with the dominant access pattern.
  • Trade-off: "list all links for user X" now needs scatter-gather across shards. Mitigated by keeping the user_id index in the relational store instead.
  • ClickEvent table: sharded by short_code_hash + YYYYMMDD — per-link daily aggregation stays on one shard, but a viral link doesn't create a permanently hot shard.
Section 6

High-Level Architecture

synchronous (write path) synchronous (read path) async (analytics)

Write path — create link

  1. Client sends POST /links. Hits LB → Creation Service.
  2. Creation Service pulls a pre-generated unique code from the Key Pool Generator (avoids a synchronous uniqueness check — §7) or validates a custom alias with one fast KV lookup.
  3. Writes {short_code → long_url} to the sharded Link KV Store (durable, acknowledged before responding).
  4. Returns the short URL. Target p99 < 300ms.

Read path — redirect

  1. User clicks the short link — may be served directly from CDN edge cache (best case, no origin hit).
  2. Otherwise hits LB → Redirect Service.
  3. Redis cache checked first (sub-ms). Hit → respond immediately with 301.
  4. Miss → query Link KV Store, populate cache, respond.
  5. Asynchronously, a click event publishes to Kafka — doesn't block the redirect response. This decoupling keeps redirect latency low, independent of analytics write load.
Section 7

Component Deep Dives

7.1 Key Pool Generator (Short Code Generation)

What/why: Generating a globally-unique 7-char base62 code (62^7 ≈ 3.5 trillion combos) synchronously per request would need a uniqueness check on every write — added latency and a race-condition risk under concurrency. Instead, batches of guaranteed-unique codes are pre-generated offline and handed out from a pool.

Internal design: A range-based counter (Snowflake/Ticket-Server style): each generator instance claims a non-overlapping range of a global counter, converts IDs to base62, pushes to an in-memory pool. Creation Service instances pull from local pools — no cross-request coordination at request time.

Failure modes: Instance crashes mid-range → some IDs never used, wasted but harmless given 3.5T combos. On restart, claims a new range rather than resuming, avoiding double-issuing.

7.2 Redirect Service + Cache Layer

What/why: Highest-QPS, latency-critical path — its own lean service so it scales/optimizes independently of the write path.

Internal design: LRU eviction (recency correlates with popularity). Cache-aside: read cache, on miss read DB and populate with TTL (e.g. 24h) so stale entries self-correct even without explicit invalidation.

Thundering herd: When a cache entry for a viral link expires, thousands of concurrent misses could hammer the DB simultaneously. Mitigated with request coalescing (first miss triggers the fetch; concurrent requests wait on that in-flight fetch) plus jittered TTLs.

Failure modes: Redis node down → falls through to DB (degraded latency, not outage) — cache is a performance optimization, not source of truth.

7.3 Link KV Store (sharded)

What/why: Source of truth for code→URL mapping; sharded for both storage volume and QPS beyond one node.

Internal design: Consistent hashing across shards (hash of short_code) minimizes re-sharding pain when adding nodes. Each shard 3x replicated (1 primary + 2 replicas).

Failure modes: Primary shard failure → automatic replica promotion (Raft-style leader election); brief write unavailability (~seconds) for that key range, reads continue from surviving replicas.

7.4 Click Analytics Pipeline

What/why: Decouples click tracking from the redirect hot path — analytics writes are high-volume but not latency-sensitive.

Internal design: Kafka topic partitioned by short_code hash (ordered per-link processing). Consumer group aggregates counts in 1-min tumbling windows before writing, reducing write amplification vs. one write per click.

Failure modes: Consumer lag/downtime → analytics stale, redirects unaffected. Kafka retains events (e.g. 7 days) so a consumer outage doesn't lose data if it recovers in time.

7.5 Creation Service

What/why: Separated from Redirect Service — different load profile, different dependencies (Key Pool Generator, custom-alias uniqueness checks).

Internal design: Custom aliases get one fast KV lookup before write (acceptable since custom aliases are a small fraction of total writes).

Failure modes: Key Pool Generator down → custom-alias requests still work; auto-generated requests queue/retry with backoff.

Section 8

Key Design Decisions & Trade-offs

Decision 1 — Consistency Model

Mixed: strong for code uniqueness, eventual for analytics

Options considered
Strong everywhere / eventual everywhere / mixed
Chosen
Mixed — pre-generated key pools for uniqueness, eventual consistency for click counters
Because
A duplicate short code is a correctness bug; a click count off by seconds is invisible and low-stakes.
What we give up
Analytics dashboards can show slightly stale numbers (seconds-to-low-minutes lag).
When we'd choose differently
If click counts fed real-time billing (pay-per-click), we'd need stronger consistency there too.
Decision 2 — Caching Strategy

Cache-aside with Redis + CDN edge caching

Options considered
No cache / write-through / cache-aside
Chosen
Cache-aside (lazy load) for the hottest links
Because
Read traffic is heavily skewed (Pareto); cache-aside avoids caching cold/one-off links unnecessarily.
What we give up
First request to a cold link always pays a DB round-trip; slight staleness risk on deactivated links.
When we'd choose differently
If reads were uniformly distributed, caching would give much less benefit relative to its complexity.
Decision 3 — Database Choice (per entity)

Polyglot persistence

Options considered
All-relational / all-NoSQL / polyglot
Chosen
Polyglot — KV for link mappings, relational for users, wide-column for click events
Because
Each entity's access pattern is different enough that one technology is suboptimal for at least one of them.
What we give up
Operational complexity — three systems to run, monitor, and staff for.
When we'd choose differently
At MVP scale (<10 QPS), a single Postgres instance for all three is simpler and adequate.
Decision 4 — Communication Pattern

Kafka-based async pub-sub

Options considered
Fully sync / fully async (Kafka) / fire-and-forget HTTP
Chosen
Kafka-based async pub-sub
Because
Decouples redirect latency from analytics throughput entirely; durability/replay means no event loss on temporary consumer downtime, unlike fire-and-forget HTTP.
What we give up
Additional infrastructure to operate; eventual — not immediate — analytics consistency.
When we'd choose differently
If analytics had zero durability requirement, a simpler fire-and-forget call might suffice.
Decision 5 — Short Code Generation

Pre-generated key pool (range claiming)

Options considered
Hash the long URL / synchronous auto-increment / pre-generated key pool
Chosen
Pre-generated key pool
Because
Hashing risks collisions requiring retry logic; synchronous auto-increment is a single point of write contention at high QPS.
What we give up
Extra infrastructure (the generator service) vs. "just hash the URL" simplicity.
When we'd choose differently
At very low scale, URL-hashing with a collision-retry loop is simpler and sufficient.

Section 10

Reliability, Failure Handling & Edge Cases

  • Downstream down (Key Pool Generator unreachable): Custom-alias creation still works; auto-generated creation queues with backoff, returns 503 + Retry-After if saturated.
  • Network partition: Accept AP behavior in the KV cluster — replicas keep serving (possibly stale) reads rather than going unavailable.
  • Duplicate requests: Handled via Idempotency-Key — cached original response returned instead of creating a duplicate.
  • Node crashes mid-write: Quorum writes (W=2 of 3) ensure a crash either fully commits or rolls back — no partial mapping is ever readable.
  • Cold cache after full restart: Temporary DB load spike expected; mitigated with gradual cache warming (pre-load hot list) and DB pool headroom.
  • Sudden 50x spike (viral link): CDN absorbs most of it; request coalescing prevents thundering herd on that key; autoscaling handles the rest.
  • Disaster recovery / multi-region: Link KV Store replicated cross-region (async); each region serves from local replica; DNS/traffic-manager failover on full region outage. Writes go to a "home region" per link to avoid cross-region write conflicts.
Section 11

Security & Abuse Prevention

  • AuthN/AuthZ: API-key/OAuth for creation/management; redirects remain public by design. Ownership enforced via user_id checks.
  • Rate limiting: Per-user token bucket on creation; per-IP throttling on redirects, tuned loosely to not affect legitimate viral traffic.
  • Malicious URL screening: Check submitted URLs against a phishing/malware blocklist (e.g. Safe Browsing API) at creation time; reject/flag known-bad destinations.
  • Enumeration protection: Random-ish pre-generated codes (not sequential) make scanning for live links ineffective.
  • Periodic re-scan: Existing links re-checked against updated threat-intel — a URL can turn malicious after link creation.
  • Data privacy: Store ip_hash, not raw IP; long URLs with sensitive query params encrypted at rest.
Section 12

Monitoring & Observability

Key SLIs

  • Redirect p50/p99 latency (server-side) — the single most important SLI.
  • Redirect 5xx error rate and cache hit ratio (leading indicator of DB load risk).
  • Write QPS vs. Key Pool Generator remaining pool size.
  • Kafka consumer lag (leading indicator of analytics staleness).
  • Shard-level QPS/latency skew (detects hotspotting early).

What pages on-call

  • Redirect p99 > 100ms sustained 5 min.
  • Redirect 5xx rate > 0.1% sustained.
  • Cache hit ratio drops below ~80% suddenly.
  • Any KV shard with < 2 healthy replicas.
  • Kafka consumer lag approaching the retention window.

Debugging a p99 latency spike

  1. Check cache hit ratio first — a drop points to cache-layer issues.
  2. If normal, check per-shard KV latency — isolates a hotspotted shard vs. systemic issue.
  3. Check for a correlated deploy/config change — "what changed?"
  4. Check if a specific CDN PoP/region is affected, or if it's global.
  5. Pull distributed traces for slow requests — cache lookup vs. DB query vs. network hop.
Section 13

Interviewer Cross-Questions (click to reveal — quiz yourself first)

"Why not X instead?"

Why not just hash the long URL (MD5/SHA truncated) instead of a key pool generator?
Hashing risks collisions at scale (birthday paradox becomes non-trivial at billions of URLs), requiring retry logic anyway — and it can't support two users shortening the same URL to different codes. The key pool avoids collision handling entirely and decouples generation from write-path timing.
Why 301 redirect and not 302?
301 (permanent) lets browsers cache the redirect, reducing server load — but it also undercounts repeat-click analytics, since the browser may not hit our server again. Should be configurable per link: 302 where per-click analytics matter more than caching benefit.
Why Kafka instead of writing click events directly to the analytics DB?
Direct writes couple redirect latency to the analytics DB's throughput/availability — if it's slow or down, redirects degrade too. Kafka is a durable buffer that fully decouples these concerns.
Why not one database for everything, to reduce operational complexity?
Viable at low scale — a single Postgres instance is simpler. But at thousands of QPS redirects, a single relational DB bottlenecks the hot-path lookup; polyglot trades operational complexity for independent scaling per access pattern.

Scale-up questions

What changes at 100x this scale (~2M peak redirect QPS)?
Many more KV shards; move from one global logical cluster to independent regional clusters with async cross-region sync. CDN edge caching becomes even more critical. The Key Pool Generator needs many more parallel instances, possibly a hierarchical range-allocation scheme so the coordinator doesn't bottleneck.
At 100x scale, does your consistency model still hold?
Yes on both counts. Eventual consistency for analytics holds and becomes even more clearly correct. Strong consistency on code uniqueness (via non-overlapping pools) also holds structurally — it never depended on synchronous coordination, which is exactly why it was chosen.

Failure-injection questions

The primary shard for a currently-viral link just crashed. Walk me through what happens.
Automatic replica promotion (leader election) — reads continue from remaining replicas with no interruption (3x replication). Brief write-unavailability (seconds) for that shard's key range, but the read path — what matters here — is unaffected.
Your entire Redis cache cluster goes down. What happens?
Every request falls through to the KV store directly — latency degrades from single-digit ms to direct DB read latency (still under the 100ms p99 budget for a well-indexed lookup), but DB load spikes. DB connection pools and replica capacity must be sized for "cache fully down," not just steady-state.
Kafka is down for 12 hours. What happens?
Redirects are completely unaffected — that's the point of the async design. Click analytics simply stop updating. If downtime exceeds Kafka's retention window, backfill is lost — retention should be sized generously relative to expected max outage duration.

Trade-off probing

Eventual consistency for click analytics — where does that break user trust, and how would you mitigate it?
A marketer checks their dashboard right after a campaign blast and sees a lower count than reality, momentarily thinking it underperformed. Mitigation: show a "stats updated as of [timestamp]" indicator so staleness is visible and expected, and keep the lag target tight via small aggregation windows.
Why not just make analytics strongly consistent too — is the latency cost really that bad?
Making click tracking synchronous with the redirect bounds every redirect's response time on the analytics write's latency/availability — turning a "nice to have, can be stale" feature into a dependency that can take down the core product. The real cost is coupling failure domains that shouldn't be coupled, not just latency.
Custom aliases need a synchronous uniqueness check — doesn't that contradict your "no synchronous checks" principle?
A deliberate exception, not a contradiction — custom aliases are a small fraction of total creates, so the extra read-before-write doesn't threaten the aggregate write-path SLA. If aliases became the majority path, we'd revisit with a similar pre-claimed-pool approach.
How would you detect and handle a link used for phishing after it's already been shared widely?
Periodic re-scanning against updated threat-intel feeds catches this after the fact. On detection, deactivate the link (soft-delete, redirect target becomes a warning page) — breaking the "permanent" 301 promise is justified by the abuse-prevention requirement.
Your capacity estimate assumes 100:1 read:write — what if it's actually 10:1?
The architecture doesn't fundamentally change — caching still helps (just less dramatically), and the KV write path already assumed meaningful write volume via the key pool design. Main impact: the Key Pool Generator's throughput requirement scales up proportionally.
What if two generator instances claim overlapping ranges due to a coordinator bug?
A genuine correctness bug — duplicate code issued to two different URLs. Mitigation: a cheap conditional write (compare-and-swap) at the KV store as a last line of defense, so this degrades to "wasted code, retry" instead of silent corruption.
Section 14

What a Weak vs. Strong Answer Looks Like

✕ Weak

  • Jumps straight to "hash function for the short code," skipping collision handling
  • Treats read and write paths as symmetric, missing how a 100:1 ratio should shape caching and service separation
  • Over-engineers real-time analytics before the core create/redirect flow is even solid
  • Skips capacity estimation, hand-waves "millions of users" instead of deriving real numbers

✓ Strong

  • States the read:write ratio early and visibly lets it drive decisions
  • Separates redirect and creation services deliberately, with reasons
  • Treats consistency as different per data type, not one global model
  • Derives real QPS/storage numbers, then references them later to justify sharding and caching
This design roughly mirrors publicly-discussed approaches used by Bitly and similar link shorteners (pre-generated key ranges, heavy caching due to read skew, async analytics) — not a claim about their actual internal implementation.
