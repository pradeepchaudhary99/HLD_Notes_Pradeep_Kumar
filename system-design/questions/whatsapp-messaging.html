Q: What are we actually building?

"Design WhatsApp" is really three coupled problems wearing one trench coat: a real-time delivery system (get bytes from A to B in milliseconds while both are online), a durable mailbox system (don't lose anything if B isn't online), and a fan-out system (groups, up to 1024 members, all need the same message). Say this out loud early — it signals you're not going to conflate "chat app" with "just a pub/sub problem."

Functional requirements

  • Send/receive 1:1 text messages in near real-time (target: <100ms end-to-end when both parties are online and well-connected)
  • Group messaging (up to ~1024 members per group)
  • Delivery status: sent (✓) → delivered (✓✓) → read (✓✓ blue)
  • Messages persist and deliver even if the receiver is offline, asleep, or on a plane for a week
  • Multi-device support (same account on phone + web + desktop, all in sync)
  • Media messages (images, video, voice notes) — sent as attachments, not inline blobs
  • Online/last-seen presence indicators
  • Typing indicators

Non-functional requirements

  • Availability > strict consistency for message delivery — a duplicate delivered message is annoying; a silently dropped one is a trust-breaking bug
  • At-least-once delivery with client-side de-duplication (not exactly-once — we'll justify this)
  • Ordering matters within a single chat/conversation, not globally across chats
  • Low latency for online users; bounded, reliable eventual delivery for offline users
  • End-to-end encryption (we'll scope the crypto handshake out, but the architecture must accommodate opaque ciphertext payloads server-side)
  • Massive scale: ~2–3B users, ~100B+ messages/day
Below the line (explicitly out of scope)
  • The actual E2E encryption key-exchange protocol (Signal Protocol / X3DH) — we'll treat message bodies as opaque encrypted blobs the server routes but never reads
  • Voice/video calling infrastructure (separate WebRTC-based system, different problem)
  • Status/Stories feature (that's closer to the Instagram feed problem)
  • Payments (WhatsApp Pay)
  • Spam/abuse detection pipelines
  • Media storage/CDN internals in depth — we'll touch it but the interesting parts of this interview are messaging semantics, not blob storage (that's a solved problem, same as S3-backed uploads in other systems)
The single hardest constraint to keep saying out loud

Every design decision in this system gets stress-tested against one question: "what happens if the receiver isn't connected right now?" A chat app that only works when both people are online isn't a chat app, it's a walkie-talkie. Offline handling isn't a deep dive bolted onto the design — it's the design. We'll build with that constraint present from the very first iteration.

Q: How do two online users exchange a message, at the simplest possible level?

Strip away scale for a second. Alice and Bob are both online, connected to the same server. What transport do we even use?

Why not HTTP polling?

The weak answer jumps straight to "we use WebSockets" without justifying it. The strong answer walks through why polling fails first:

  • Short polling (client asks "any new messages?" every N seconds) — either N is small and you're DDoSing your own servers with mostly-empty responses, or N is large and messages sit for seconds before delivery. Neither is acceptable for a chat app.
  • Long polling (server holds the request open until a message arrives or timeout) — better, but you're still paying full HTTP header overhead per message, reopening connections constantly, and it's fundamentally a hack around HTTP being request/response.
  • WebSockets — a single persistent, full-duplex TCP connection. Server can push to the client the instant a message arrives, with no polling overhead. This is the only sane choice for a system where median message latency needs to be double-digit milliseconds.
v1 — trivial case: both users' WebSocket connections happen to terminate on the same server

The flow: Alice's client opens a WebSocket to a chat server. Bob does the same. The server keeps an in-memory map of user_id → socket_connection. When Alice sends a message, the server looks up Bob's connection in that map and pushes directly.

Why this immediately breaks

This works for a toy demo and fails in about four different ways the moment you have more than one server: (1) Bob might be connected to a different server than Alice, (2) Bob might not be connected at all, (3) the in-memory map vanishes if the server restarts, (4) we have zero durability — if the push fails, the message is gone forever. Every subsequent iteration exists to fix one of these.

Q: What happens when the receiver is offline?

This is the question that separates a real design from a demo. Bob closes his laptop. Alice sends a message. Where does it go?

The fix is to stop treating message delivery as "push and forget" and start treating it as write-then-notify: every message is durably persisted before we even attempt real-time delivery. Real-time push becomes an optimization on top of a durable store, not the primary mechanism.

v2 — persist first, deliver-if-possible second. Offline is now the default path, not an exception.

The mental model shift

Reframe the receiver's inbox as a durable, ordered, per-user message queue — conceptually similar to an email inbox, not a live phone call. Every message gets:

  • Written to persistent storage first (this is the durability guarantee — once acked to the sender, it cannot be lost)
  • An attempt at real-time push if the recipient has an active connection
  • If no active connection: nothing else happens right now. No retry loop, no background job. The message just sits durably in the recipient's inbox.
  • On the recipient's next connection, the client fetches "everything since my last synced message" and the server replays the backlog

This one design choice — durability first, real-time delivery as a best-effort accelerant — is what makes offline handling a non-event instead of a special case. We don't need a separate "offline queue service." Online delivery and offline delivery are the same code path; the only difference is whether step 2 (push) succeeds.

What does "sync since last message" actually look like?

Each message gets a monotonically increasing sequence number per conversation (not global — global sequence numbers become a single point of write contention at this scale). The client persists the highest sequence number it has seen for each conversation. On reconnect:

GET /sync?conversations=[{id: "chat_123", last_seen_seq: 4821}, ...]
→ server returns all messages with seq > 4821 for each conversation, oldest first

This is strictly better than "server tracks unread messages and pushes them" because it's client-driven and idempotent — if the sync call fails halfway and retries, the client just asks again with the same cursor. No server-side "did I already mark this as delivered" bookkeeping needed for the sync mechanism itself.

Q: How do we scale past one WebSocket server — and how does a message find a receiver on a different machine?

This is the question you specifically flagged, so let's go slow. At 2–3B users, one server obviously can't hold every WebSocket connection. Say we have a fleet of Connection Servers (sometimes called Gateway or Edge servers), each holding maybe 500K–1M concurrent connections. Alice is connected to gateway-7. Bob is connected to gateway-142. Alice sends a message. How does it reach Bob?

The naive/weak answer: "gateway-7 asks gateway-142 directly." This requires every gateway to know about every other gateway and maintain N² potential connections between them — it doesn't scale and creates a tightly coupled mesh where gateway failures cascade.

The correct answer decouples gateways from each other entirely using two pieces: a connection registry (who is connected to which gateway, right now) and a pub/sub message bus (how a message actually gets routed to the right gateway without gateways talking to each other directly).

v3 — gateways never talk to each other. They talk to a registry (to find) and a pub/sub bus (to route). This is the answer to "sender and receiver on different servers."

Walking through it step by step

  1. Connection registration: when Bob's client opens a WebSocket to gateway-142, that gateway writes bob_user_id → gateway-142 into a shared, fast key-value store (Redis, typically with a TTL as a self-healing mechanism — more on that below).
  2. Alice sends a message. It lands on her gateway, gateway-7 — this has nothing to do with Bob.
  3. gateway-7 persists the message to durable storage (this happens regardless of whether Bob is online — durability isn't conditional).
  4. gateway-7 looks up Bob in the connection registry. Gets back gateway-142.
  5. gateway-7 does not open a connection to gateway-142. Instead it publishes the message onto a pub/sub topic that gateway-142 subscribes to (e.g., a topic keyed by gateway ID, or a consistent-hash-partitioned Kafka topic where gateway-142 owns certain partitions).
  6. gateway-142, subscribed to its own topic, receives the message and pushes it down Bob's already-open WebSocket.

Why pub/sub instead of direct gateway-to-gateway RPC?

  • Decoupling: gateway-7 never needs to know gateway-142 exists, its IP, its health, or whether it's mid-deployment-restart. It only needs to know "publish to topic X." This turns an O(N²) mesh of gateway relationships into O(N) — each gateway only talks to the bus.
  • Buffering under load: if gateway-142 is momentarily slow (GC pause, brief network blip), the message sits in the pub/sub topic instead of the publisher blocking or the message getting dropped. Kafka in particular gives you a replay-able log, not just fire-and-forget pub/sub.
  • Fan-out for groups is free: if a message needs to reach 500 group members spread across 80 different gateways, "publish once, N gateways subscribe and pull their relevant slice" is dramatically cheaper than the sender's gateway making 80 direct calls.
  • Server death is a non-event: if gateway-142 crashes mid-message, the message isn't lost — it was persisted in step 3 independent of delivery, and (depending on bus choice) may still be sitting in the topic for a replacement consumer.
Edge case: what if the registry says gateway-142, but Bob disconnected 2 seconds ago and the registry hasn't updated yet?

gateway-142 receives the pub/sub message, tries to push to Bob's socket, finds it's closed. It does not retry the push or treat this as an error — the message is already durably persisted (step 3 happened unconditionally). gateway-142 simply drops the push attempt; Bob will get the message on his next reconnect/sync. This is exactly why "persist first, push second" matters — the push path is allowed to fail silently because it was never the source of truth.

Q: How do group chats avoid making the sender pay for every recipient?

A 1024-member group is a fan-out problem hiding inside a chat app. Naively, "one message becomes 1024 writes done synchronously by whoever hit send" is a latency and reliability disaster — the sender's request now blocks on the slowest of 1024 downstream operations.

Fan-out-on-write, adapted from the social feed pattern

This is the same named pattern you used in the Instagram HLD, applied here: the sender's API call does the minimum possible work synchronously (persist one canonical copy of the message, tagged with the group ID), and a background fan-out process asynchronously creates the per-recipient delivery records / pushes to each recipient's gateway via the pub/sub bus from v3.

1. Alice sends to group_id=456 (1024 members)
2. Server persists ONE row: {msg_id, group_id: 456, sender: alice, body, seq}
3. Server returns "sent ✓" to Alice immediately — she does not wait for fan-out
4. Async worker reads group_456's member list, and for each member:
     - writes a per-user "pointer" record (or relies on group-scoped sync, see below)
     - publishes to that member's gateway topic if they're online
5. Each online member's gateway pushes the message down their socket
6. Offline members pick it up via the same sync-since-last-seq mechanism as 1:1
Group storage: don't copy the message 1024 times

Store the message body once, keyed by group_id. Each member's client, on sync, asks "give me messages in groups I'm part of since sequence N" — it reads the single shared copy. What you fan out is notifications/pushes, not the message payload itself. This is the same space-efficiency insight as fan-out-on-write in a feed system: don't duplicate the expensive payload, duplicate the cheap pointer.

Large groups: push vs pull hybrid

For very large or very "hot" groups (announcement channels, broadcast lists), pure push-fan-out to potentially-offline members wastes work. The same hybrid approach from celebrity fan-out in feed systems applies: for groups above a size threshold, skip proactive per-member pub/sub publishing for offline members entirely (they'll pull on sync anyway) and only push to members who are currently connected. This turns "fan out to 1024" into "fan out to however many are actually online right now," which for most groups at any given moment is a small fraction.

Q: What are the 2–3 decisions that actually separate a good answer from a great one here?

Decision 1 — How do we guarantee message ordering and prevent duplicates on flaky mobile connections?
Bad
Approach: trust the network, use server receipt time as order

Approach: Order messages by the timestamp the server received them. No dedup logic — assume each send is a single event.

Challenges

Mobile clients retry on timeout. If Alice's phone sends a message, the network blips before the ack comes back, and the client retries — the server now has two copies with two different receipt timestamps, potentially out of order relative to a message sent in between. Server-receipt-time also doesn't reflect user intent: two messages typed in order but sent over a lossy connection can arrive at the server out of order.

Good
Approach: client-generated message ID + per-conversation sequence number

Approach: Client generates a UUID for each message before sending (enables dedup: server checks "have I seen this UUID for this sender" and no-ops if so). Server assigns the authoritative ordering via a monotonically increasing sequence number scoped to the conversation, not global.

Challenges

Solves duplication and gives a clean ordering axis, but "monotonically increasing per conversation" needs a serialization point — if two people in a group send simultaneously, who increments the counter? A naive shared counter in a relational row becomes a write hotspot under concurrent sends into the same busy group.

Great
Approach: client UUID for dedup + server-assigned sequence via single-writer-per-conversation, with causal (not wall-clock) ordering as the mental model

Approach: Same client UUID dedup as "Good," but the sequence number is assigned by whichever single server/partition owns that conversation's write path at that moment (achieved by consistent-hashing conversation ID to a specific partition/owner — the same conversation always routes to the same sequencer, so there's no cross-node race). Explicitly frame this to the interviewer as causal ordering, not global wall-clock ordering: we guarantee "everyone sees Alice's messages in the order Alice sent them," not "everyone sees a single universal timeline across all users" — the latter is neither achievable nor necessary in a chat app.

Challenges

Requires care in the partition-ownership handoff during rebalancing/failover (brief window where two nodes could both think they own a conversation) — mitigated with a lease/fencing token, same pattern as leader election anywhere else.

Decision 2 — What delivery guarantee do we actually promise: at-most-once, at-least-once, or exactly-once?
Bad
Approach: promise exactly-once end-to-end

Approach: Try to guarantee each message is delivered exactly one time, no duplicates, no drops, across the entire pipeline (client → gateway → pub/sub → gateway → client).

Challenges

This is the textbook trap answer. True exactly-once delivery across an unreliable network is provably impossible in the general case (two generals problem) — you can get exactly-once effect via idempotency, but not exactly-once delivery at the transport level. Promising it as a delivery guarantee reveals a gap in distributed systems fundamentals.

Good
Approach: at-least-once delivery, retry aggressively on the send side

Approach: Sender retries until acked. Server may occasionally deliver a message twice (e.g., ack lost in transit, sender retries a message the server already has). Accept duplicates as a possibility.

Challenges

Without a dedup mechanism on the receiving client, "occasional duplicates" becomes "user sees the same message twice," which is a visible bug, not a backend implementation detail.

Great
Approach: at-least-once delivery at the transport layer + idempotent, client-side dedup by message UUID = exactly-once effect

Approach: Explicitly separate "delivery guarantee" (at-least-once — messages might arrive twice, that's fine and expected) from "user-visible guarantee" (exactly-once effect — the receiving client keeps a set/index of recently-seen message UUIDs and silently drops a duplicate before rendering it). This is strictly better than chasing exactly-once delivery because it's achievable, and it pushes the complexity to the place that can actually solve it cheaply: an idempotency check is O(1) hash lookup on the client, versus distributed exactly-once coordination which is extremely expensive and still has edge cases.

Challenges

Client must persist a reasonably-sized recent-message-ID cache (not the full history) and handle the rare case where a duplicate arrives long after the dedup window — acceptable trade-off, since a duplicate months later re-rendering harmlessly is a non-event compared to a lost message.

Decision 3 — How does the system know which gateway a user is connected to, and what happens when that mapping goes stale?
Bad
Approach: gateway pushes connection state to a database on connect, relies on explicit disconnect cleanup

Approach: On WebSocket open, write user → gateway to a DB row. On WebSocket close, delete the row.

Challenges

Mobile clients don't cleanly disconnect — apps get killed, phones die, networks vanish without a TCP FIN ever arriving. The registry silently accumulates ghost entries: users who are gone but still "registered" as connected to a gateway. Every message sent to them gets routed into a void, degrading perceived delivery latency (server thinks it delivered; it didn't) until the user reconnects and syncs — if the client even knows to sync.

Good
Approach: TTL-based registry entries with periodic heartbeat refresh

Approach: Store user → gateway in Redis with a TTL (e.g., 60s). Client sends a lightweight heartbeat/ping every ~30s; gateway refreshes the TTL on each heartbeat. If heartbeats stop, the entry expires on its own — self-healing, no explicit cleanup logic required.

Challenges

Solves the ghost-entry problem for silently-dead connections, but introduces a detection lag — up to one TTL window where the system still believes a dead connection is alive, and heartbeat traffic at billions of connections is non-trivial bandwidth (even if each ping is tiny, ping × 2-3B connections × every 30s adds up).

Great
Approach: TTL + heartbeat (same as Good) + gateway-owns-the-source-of-truth on push failure, with the registry treated as a cache, not ground truth

Approach: Keep the TTL/heartbeat mechanism, but add the key insight: the registry is a hint, not a guarantee, and the system is designed to be correct even when the hint is stale. When a gateway attempts a push and finds the socket actually closed (this is authoritative — the gateway physically owns that TCP connection and knows immediately), it proactively deletes the stale registry entry right then, rather than waiting for TTL expiry. This collapses the detection lag from "up to 60s" to "immediate, the moment we actually try to use the stale data" — and because delivery correctness never depended on the registry being perfectly accurate (message was already durably persisted per the v2 design), staleness in the registry is purely a latency-of-realizing-you're-stale problem, never a correctness problem.

Challenges

Requires discipline to keep this invariant true everywhere in the codebase — any code path that treats the registry as authoritative (rather than "best current guess, verify on use") reintroduces the ghost-entry class of bug.

Q: Deep dives — the mechanisms worth going one level deeper on

Deep dive 1: Offline delivery, end to end

Pattern: write-ahead durability + client-driven pull-sync

Let's fully trace what happens when a message is sent to a completely offline user, and what happens hours later when they come back.

At send time (Bob is offline)

  1. Alice's client sends the message with a client-generated UUID over her WebSocket.
  2. The gateway persists it to the durable message store — a write optimized for append (think a wide-column store or partitioned relational table, keyed by conversation ID with the sequence number as the sort key). This write is on the synchronous critical path; Alice's "sent ✓" doesn't fire until this succeeds.
  3. The gateway checks the connection registry for Bob → nothing found (either no entry, or entry present but push fails against a dead socket, per Decision 3 above).
  4. Almost nothing else happens. No retry queue, no "offline message service," no background job polling for when Bob comes back. The one action taken is a fire-and-forget push request to APNs/FCM to nudge Bob's device to sync sooner (see Deep Dive 6) — the gateway doesn't track whether it lands. The message is sitting in the durable store, associated with Bob's conversation. That's the entire "offline" mechanism — it's an emergent property of "we always persist," not a distinct subsystem.

At reconnect time (Bob opens the app after 6 hours)

  1. Bob's client opens a new WebSocket, authenticates.
  2. Client sends its local sync cursor: the last sequence number it has seen, per conversation it's part of (this can be batched — "here's my state for all 40 of my active conversations" in one call, not 40 round trips).
  3. Server queries the message store: "for each of these conversations, give me everything with seq greater than what the client already has."
  4. Results stream back, oldest-first per conversation, so the client can render history in the correct order and update its local cursor incrementally (important for resilience — if the connection drops again mid-sync, the client's cursor reflects exactly how far it got, and resuming is just "ask again with the updated cursor," no duplicate re-fetch, no gap).
  5. New registry entry is written: Bob → this gateway. Future messages to Bob now push in real time again.
Why this design avoids a whole class of bugs

Notice there's no separate "did we already try to deliver this and fail" state machine. Delivery is stateless from the sender's perspective — it either lands in real time (best effort) or it doesn't, and either way the receiver's next sync captures the true state. Compare this to a design where the server tracks "pending delivery" per offline message and retries on a schedule — that requires a scheduler, retry backoff logic, and dead-letter handling for messages that are pending for weeks (users go on long trips). The pull-based sync model sidesteps all of that: the "retry" is simply "the receiver will ask when they're ready," with no server-side timer ever needed.

Deep dive 2: What is pub/sub actually doing for us here, precisely?

Pattern: decoupled publish/subscribe as a routing indirection layer

It's worth being precise about this because "we use pub/sub" is often stated without explaining which problem it solves. In this design, pub/sub is solving exactly one problem: letting a message travel from "wherever it was received" to "wherever it needs to be pushed" without the two endpoints having a direct relationship.

Without pub/subWith pub/sub
gateway-7 needs to know gateway-142's address, health, and load — this is service discovery baked into application logicgateway-7 only needs to know "publish to bus, topic = f(recipient)" — zero knowledge of any other gateway
If gateway-142 is unreachable, gateway-7's request fails synchronously — sender's send path is coupled to receiver's server healthThe bus absorbs the message; if gateway-142 is briefly unavailable, the message waits in the topic/partition until a consumer (possibly a replacement instance) picks it up
Group fan-out to 1024 members on 200 different gateways = up to 200 synchronous outbound calls from the sender's serverGroup fan-out = one (or a few, partitioned) publish operations; subscribing gateways pull only what's relevant to their connected users
Adding a new gateway instance means updating a discovery mechanism everywhereNew gateway just subscribes to its assigned topic/partition — the publishers never needed to change

Topic/partition scheme: how does a gateway know what to subscribe to?

Two common approaches, and it's worth naming the trade-off explicitly:

  • Topic-per-gateway: each gateway instance has its own dedicated topic (or Kafka consumer group tied to specific partitions). Simple mental model, but topic count scales with fleet size, and if a gateway restarts and comes back as a "new" instance identity, you need a rebalancing story.
  • Consistent-hash-partitioned topic: a fixed number of partitions (say, 4096), user IDs hash-mapped to a partition, and gateways subscribe to whichever partitions their currently-connected users fall into (updating subscriptions as users connect/disconnect). This decouples "number of partitions" from "number of gateway instances," which scales better operationally — you don't reshuffle the whole topology every time you add a gateway.

For an interview answer, stating the trade-off between these two is more valuable than picking one dogmatically — topic-per-gateway is simpler to reason about early; consistent-hash partitioning is what you'd actually want at WhatsApp's real scale because gateway fleets autoscale constantly and you don't want topic churn on every scale-up event.

Redis Pub/Sub vs Kafka here — which, and why?

This is a great "it depends, and here's exactly what it depends on" answer:

  • Redis Pub/Sub: extremely low latency, simple, but fire-and-forget — if no subscriber is listening at publish time, the message is gone. Fine only if you've already guaranteed durability elsewhere (which we have — v2's persist-first design means Redis pub/sub losing an in-flight "real-time push attempt" is totally fine, because the durable copy still exists for sync-on-reconnect).
  • Kafka: durable log, consumers can replay, survives consumer downtime — but higher latency and more operational weight per message than Redis.

Given that we already have a separate durable message store, using Redis Pub/Sub for the "best-effort real-time nudge" layer is the right call — we don't need the pub/sub layer itself to be durable, because durability is already handled upstream. Using Kafka here would be paying for a guarantee we don't need at that specific layer. (Kafka very much earns its keep elsewhere in the system — e.g., as the backbone for the message persistence write path itself, for analytics event streams, or for the group fan-out job queue — just not necessarily as the real-time-push notification bus.)

Deep dive 3: Cross-server WebSocket routing — the full lifecycle

Pattern: connection ownership registry + push-verify-on-use

Let's zoom into the registry itself, since "Redis stores user → gateway" undersells the subtlety.

What's actually stored, and why not just user → IP

Key:   presence:{user_id}
Value: { gateway_id: "gw-142", connection_id: "conn_9f3a...", last_heartbeat: 1735000000 }
TTL:   60s, refreshed on each heartbeat

The connection_id matters beyond just the gateway — a user might reconnect rapidly (flaky network) and briefly have two "in-flight" registrations racing each other. Including a connection ID lets the gateway itself disambiguate "is this heartbeat for the connection I currently think is active, or a stale one" without needing a lock.

Multi-device: the registry isn't a single value, it's a set

WhatsApp users are commonly connected from phone + web + desktop simultaneously. This changes the registry from user_id → one gateway to user_id → set of (gateway, device, connection_id). On message delivery, the sender's gateway fans out the pub/sub publish to every entry in that set — all of Bob's devices get the message in real time, and each device independently tracks its own sync cursor (Bob might read a message on his phone and it needs to show as read on his desktop too — that's a separate read-receipt-sync fan-out using the same underlying mechanism).

Edge case: Bob is connected to 3 gateways (phone/web/desktop) — does the message get persisted 3 times?

No — persisted exactly once, keyed by conversation, independent of device count. The registry lookup fans out only the push notification step to N devices; all N devices then pull the same single stored message on their respective syncs. This is the same "store once, fan out pointers" principle from the group messaging section, applied to multi-device instead of multi-recipient.

Deep dive 4: Worked example — fanning out 10 messages to a group, with real gateway IDs

Pattern: fan-out-on-write + publish-per-gateway, not publish-per-recipient

The mechanics above are easy to state abstractly and easy to get wrong in the details — specifically, people often assume fan-out means "one publish per recipient." It doesn't. Let's trace exactly what happens, with concrete IDs, when Alice sends 10 rapid messages into a 6-person group.

Setup

Group G99 members: alice, bob, carol, dave, erin, frank

Current connection registry state:
  alice → gateway-3    (sender)
  bob   → gateway-3    (same gateway as Alice — coincidence)
  carol → gateway-7
  dave  → gateway-7    (same gateway as carol)
  erin  → gateway-11
  frank → (no entry — OFFLINE)

Message 1 of 10: send + persist

Alice's client already holds an open WebSocket to gateway-3. She sends:

{ "client_msg_id": "a1f9-...", "group_id": "G99", "body": "<ciphertext>" }

gateway-3 does two things synchronously, in order:

  1. Persist — writes exactly one row to the message store: {group_id: G99, seq: 4821, sender: alice, body}. One canonical copy, not one per recipient.
  2. Ack Alice — returns sent ✓ immediately. Alice's client does not block on the other 5 members receiving anything.

Fan-out to the other members hasn't happened yet at this point — and that's by design (Decision-1-style separation of "durable" from "delivered").

Fan-out: publish once per gateway, not once per recipient

An async fan-out worker reads G99's member list, drops Alice (sender never gets her own message pushed back), and resolves each remaining member against the connection registry:

bob   → gateway-3
carol → gateway-7
dave  → gateway-7
erin  → gateway-11
frank → not found

This is the detail worth being precise about: the worker does not issue 4 separate pushes. It groups recipients by destination gateway and publishes once per distinct gateway:

publish(topic="gw-3",  msg={seq:4821, group:G99, ...})   → covers bob
publish(topic="gw-7",  msg={seq:4821, group:G99, ...})   → covers carol AND dave, one publish
publish(topic="gw-11", msg={seq:4821, group:G99, ...})   → covers erin

3 publishes cover 4 online recipients because carol and dave happen to share gateway-7. Each gateway, subscribed to its own topic, receives the event once and then checks its own local socket table for every connected user who belongs to G99:

gateway-7 receives the publish
        → scans local sockets, finds carol AND dave are both G99 members
        → pushes to both sockets from this single subscribed event

This is the actual scaling property: fan-out cost is a function of how many distinct gateways the group's online members are spread across, not how many members there are. A 1024-member group spread across 80 gateways costs 80 publishes, not 1024 — this is exactly the number referenced back in the v4 build-up.

Frank (offline): the fourth path, which is really "no path"

No registry entry exists for frank, so no publish is even attempted for him — there's nothing to retry or queue. Message 4821 simply sits in the durable store under G99. Whenever frank reconnects, his client sends its sync cursor (e.g. last_seen_seq_for_G99: 4810), and the server returns every message from 4811 onward in one response — by the time he's back, that naturally includes all 10 of Alice's messages at once, not 10 separate replays.

Now repeat this for messages 2 through 10

Each of the remaining 9 messages runs through the exact same loop independently — persisted first with its own sequence number (4822, 4823, … 4830), then its own round of per-gateway publishes. A few details worth keeping precise if asked:

  • No batching into one blob. WhatsApp doesn't wait and coalesce 10 messages into a single push — that would add latency for no real gain, since a gateway can push several messages down an already-open socket back to back with negligible overhead per message.
  • Ordering is preserved per gateway-topic. Publishes for seq 4821 through 4830 go out in order on gw-7's topic, and gateway-7 pushes them to carol and dave's sockets in the order received — so their clients see messages 1 through 10 in order, never interleaved with something else.
  • Same-gateway sender/recipient (bob) is a genuine implementation choice, not a triviality. Bob shares gateway-3 with Alice. Does the gateway still round-trip through the pub/sub bus to deliver to a socket it already owns locally? Two valid answers: (a) uniform path — always publish through the bus even for local recipients, because it keeps the code path identical everywhere and avoids a special case that can silently drift out of sync with the "real" path; or (b) local shortcut — detect same-gateway delivery and push directly, skipping the bus hop entirely, trading a small amount of code complexity for shaving one hop of latency. Worth naming both and stating which you'd pick and why (uniformity is usually the safer default; the shortcut is a legitimate optimization once the system is mature and well-tested).
Why Redis Pub/Sub being lossy doesn't matter here

Suppose gateway-7 happens to be mid-restart exactly when the publish for message 4825 goes out. That publish is simply lost — Redis Pub/Sub has no replay for subscribers that weren't listening at publish time. It doesn't matter: carol and dave receive 4825 through 4830 together on their next sync/reconnect, because the durable message-store copy never depended on that publish succeeding. This is the same invariant repeated once more, now visible at the level of a single dropped event rather than a whole offline user: pub/sub is the best-effort accelerant; the message store is the only thing that has to be right.

Deep dive 5: How are users notified about "last seen"?

Pattern: ephemeral presence + durable last-seen write-on-disconnect + privacy-gated read

This looks like a trivial read off the connection registry and isn't — the registry as designed so far only answers "is this person online right now," and only while they're actually connected. The moment a user disconnects, their registry entry is deleted (or TTL-expires), and that data is simply gone. If "last seen 2 hours ago" is a product requirement, that timestamp has to be captured and written somewhere durable at the moment of disconnect — it cannot be reconstructed later from a registry that no longer has the entry.

Two different questions, often conflated

  1. "Is this person online right now?" — a live, boolean-ish signal, already answered by the connection registry from Deep Dive 3.
  2. "When were they last online, if not now?" — a point-in-time timestamp that must persist after the registry entry disappears.

The write path: capture last-seen on disconnect, not just presence on connect

On disconnect (clean close OR detected via heartbeat timeout):
    gateway-3 writes:  SET last_seen:bob { timestamp: 1735003600 }
                        (durable store — separate from the TTL'd registry key)
    gateway-3 deletes: presence:bob   (the live connection entry, as before)

This is a second, small piece of durable state, deliberately kept separate from the ephemeral registry. It's low-volume — one write per disconnect event, not per message — so it doesn't need Redis's speed; the same durable store already holding messages is a fine home for it.

The read path: it's not a plain lookup, it's privacy-gated

This is the detail most naive designs miss, and it's worth stating explicitly because it's a product/privacy requirement shaping the technical design, not a technical constraint in isolation — the same category of decision as the "silently drop, don't error" choice for messaging a user who blocked you, raised earlier in edge cases.

GET last_seen:bob, requested_by: alice
    → check: does bob allow last-seen visibility?        (bob's privacy setting)
    → check: does alice ALSO allow HER last-seen to show?  (reciprocity check)
    → only if BOTH are true → return bob's actual timestamp
    → otherwise → return "last seen unavailable"
Edge case: why is the reciprocity check necessary, not just a one-way flag on Bob?

If you hide your own last-seen from others, you lose the ability to see anyone else's — it's mutual, not a one-way toggle. This means the read path can't just check the target's privacy setting; it has to check both parties' settings before returning anything. Skipping this and only gating on the target's setting is the kind of bug that ships quietly and only gets caught in a privacy review, which is exactly why it's worth calling out unprompted in an interview — it signals you're thinking about the read path as a policy decision, not just a data fetch.

Should presence changes push in real time, or should clients poll?

Given the pub/sub mechanism already built out for messages, the natural answer is to reuse it rather than invent new infrastructure — a presence change is just a different event type traveling the same publish/subscribe path already used for message delivery:

When bob disconnects:
    gateway-3 publishes a "presence changed" event on the same
    channel/topic mechanism used for message delivery — just a
    different event type on the wire, not a new subsystem
The real scaling trap: don't broadcast presence to the whole contact list

Naively pushing "I went offline" to everyone who has you in their contacts is expensive at scale — a popular or business account can have presence fan-out cost comparable to a small broadcast group every time it connects or disconnects. The mitigation is the same shape as read-receipt fan-out: only push presence updates to users who currently have that specific chat open, not to the full contact list. The client tells the server "I'm actively viewing bob's chat" (subscribing to his presence specifically) and unsubscribes on navigating away — this bounds fan-out to "people looking at this conversation right now," which is a small, self-limiting set, rather than "everyone who's ever talked to this person."

Summary: the three pieces this deep dive adds on top of the existing design
  1. A durable last_seen:{user_id} write on disconnect — separate from the ephemeral, TTL'd registry entry that already existed for routing.
  2. A privacy-check layer sitting in front of any last-seen read — reciprocal visibility between both parties, not a one-way flag on the target.
  3. Presence-change events pushed through the existing pub/sub mechanism, but scoped only to viewers of that specific open chat — not a broadcast to the whole contact list.

Deep dive 6: When does the WebSocket actually exist? (the two-connection model)

Pattern: app-owned real-time socket + OS-owned always-on push channel

"Offline" has been used loosely so far to mean "no registry entry." It's worth being precise, because the client actually maintains — or benefits from — two separate connections, and they fail independently:

ConnectionHeld byPurpose
WhatsApp's own WebSocket to a Connection ServerThe WhatsApp app process — only while it has execution timeReal-time send/receive, presence, typing, receipts — everything on the wire protocol
Push socket — APNs (iOS) / FCM (Android)The operating system — always on, one per device, shared by all appsWake the app or raise a notification when WhatsApp's own socket is gone

So "offline" in the routing sense = WhatsApp's own socket is not currently registered. That is a broader condition than "the user's internet is off." It also covers: the app was backgrounded and the OS suspended it (the common case on iOS), or the app was swiped away entirely. In all of those the phone is still reachable — just via the OS push channel, not our socket.

When does WhatsApp's own socket get established?

Whenever the app has both execution time and network. Concretely:

SituationWhatsApp socket?
App is open / foregroundedYes, always — reconnects with backoff on any drop, and immediately when network returns while foregrounded
App backgrounded, Android, battery optimization offUsually yes, held for minutes–hours; reconnects on the OS network-change broadcast
App backgrounded, iOSUsually no — the OS has suspended the process; delivery relies on an APNs push to wake it
App killed / swiped away (either OS)No — only an OS push can wake the process
Internet was off, now back, app in backgroundSocket does not come up just because Wi-Fi returned. The sender's gateway pushes via APNs/FCM, the push wakes the app, and that triggers the socket — or the user opens the app

This is why on an iPhone you sometimes watch messages "arrive" the instant you open WhatsApp: they were sitting in the durable store (Deep Dive 1), and the socket that pulls them only just came up.

Deep Dive 6 — Bob's app holds no live socket. Steps 2–5 (amber) are a fire-and-forget nudge; the message itself only ever travels the durable pull-sync path (steps 7–8) once the woken app reconnects.

How the push step slots into the send path

Deep Dive 1 said "nothing else happens" when the registry lookup misses. Precisely, one thing happens, and it changes nothing about durability: the gateway fires a push request to APNs/FCM for the recipient's device token. That push is a trigger to sync sooner, not a delivery mechanism and not the source of truth.

Gateway, on registry miss for Bob (or push to a dead socket fails):
    → message is already durably persisted (unconditional, happened first)
    → send push request to APNs/FCM for bob's device token
    → done. No retry, no tracking whether the push landed.
The push carries no message content — and it doesn't need to

Messages are end-to-end encrypted, so the server cannot put the plaintext in the push payload even if it wanted to. The push is just a nudge. Android: a high-priority FCM data message wakes WhatsApp in the background → it opens its socket → runs the normal cursor-based sync → decrypts locally → posts the real notification with content. iOS: APNs delivers to WhatsApp's Notification Service Extension, which gets a short window to connect, pull, and decrypt, then rewrites the notification text; if it can't finish in time you see a generic "Message" until you open the app. Either way the content path is still "client connects and pulls from the durable store" — the push just makes that happen in seconds instead of on next app open.

Edge case: device is offline too, so the push can't be delivered right now

APNs/FCM store the pending push and retry when the device reconnects (with a limited TTL, and only the last push coalesced for some types). If it expires, nothing is lost — the message is still in the durable store, and the client's reconnect-sync picks it up regardless of whether any push ever landed. The push layer has exactly the same status as the real-time pub/sub bus from Deep Dive 2: a best-effort accelerant, never the thing that has to be right.

Deep dive 7: The control plane — group creation, profile edits, and media don't all take the message path

Pattern: one multiplexed socket for control + real-time data, separate HTTPS for bulk bytes

Everything so far has been about message delivery. But "create a group," "rename a group," "change my profile photo," "set my about text" also have to travel somewhere. Mostly they take the same WebSocket — they're just different frame types on a multiplexed protocol (a binary, tokenized descendant of XMPP). It's worth being able to name the categories:

Frame typeDirectionCarries
messageclient ↔ serverChat messages — the delivery path from v1–v4
iq (info/query)request → responseRPC-style actions: create group, add/remove participant, change subject/icon, set profile name / about, fetch group metadata, register push token, change privacy settings
notificationserver → client"Something changed that affects you" — someone added you to a group, changed the group subject, rotated their profile photo. Pushed to other members' sockets, or queued for offline members using the same offline-store + push mechanism as chat
presence / receipt / ackclient ↔ serverOnline/typing/last-seen; delivered & read receipts; protocol-level acknowledgements

So "create a group" is: client sends an iq set over its existing socket → server creates the group, replies with an iq result → server emits a notification to every other member (live socket if connected, offline queue + push if not). It reuses the fan-out machinery from v4 — the payload is just a group-metadata change instead of a chat message.

Where a genuinely different transport is used

OperationTransport
Group create, participant changes, subject/description (text)WebSocket iq
Set profile name / about (text)WebSocket iq
Upload profile photo / group icon / any photo, video, audio, documentSeparate HTTPS blob service. Client encrypts the file, uploads ciphertext to the media servers over plain HTTPS, then the socket only carries the resulting URL + media key + SHA-256. Big bytes never touch the WebSocket.
Media downloadHTTPS GET from the media CDN, decrypt with the key received over the socket
Registration / SMS-OTP verificationStateless HTTPS REST — there is no authenticated session or socket yet at that point

Deep Dive 7 — group and profile edits are iq RPCs on the very same socket as chat, and notification fan-out to other members reuses the v4 machinery. Only bulk bytes (media) and bootstrap (signup / OTP) take a separate HTTPS path.
The mental model to state in an interview

Control plane + real-time data plane → one persistent socket, where actions are request/response iq RPCs and "someone else changed something" arrives as a notification that fans out exactly like a message. Bulk bytes (any attachment, including profile and group images) → a separate HTTPS media service with client-side encryption; the socket only ever carries a pointer and a key. Bootstrap (signup, OTP) → stateless HTTPS REST, because no session exists yet. Group and profile edits are "different" only in being iq RPCs rather than message frames — same connection, same offline-queue-plus-push fan-out to everyone else.

Deep dive 8: Delivery & read receipts, and the presence / typing channel

Pattern: receipts are just messages flowing backwards + ephemeral presence that never persists

The single ✓, double ✓✓, and blue ✓✓ are not a separate subsystem — each one is a tiny message travelling back along the exact same routing path the original message took, in the opposite direction. A receipt is its own frame type (receipt) carrying a type (delivery / read / played) and the target message id(s). Everything built in v2–v4 — persist-first, registry lookup, per-gateway pub/sub, offline queue — is reused wholesale, just with sender and recipient swapped.

The four states of an outbound message

UIMeaningWho emits the signalCan the recipient suppress it?
🕓 clockNot yet acknowledged by the server (still on the sender's device)— (local only)n/a
✓ singleServer received & durably persisted the messageSender's own gateway, via the protocol ackNo
✓✓ greyMessage reached at least one of the recipient's devicesRecipient's client, automatically on receiptNo
✓✓ blueRecipient actually opened the chat / the message entered the viewport (played for a listened voice note)Recipient's client, on foregrounding the conversationYes — the "Read receipts" privacy setting
Deep Dive 8 — a receipt is just a receipt-type frame that Bob's client emits and that rides the same registry + pub/sub path back to Alice. Read receipts are coalesced: step 8 carries a single "read up to seq N", not one receipt per message.

Why read receipts are cheap: coalescing

A naive design sends one read receipt per message — open a chat with 200 unread messages and the recipient's client fires 200 receipts. WhatsApp instead sends a single cumulative receipt: { type: read, conversation: C, up_to_seq: 4830 }. The sender's client marks every message with seq ≤ 4830 as read in one shot. Delivery receipts are batched too — a client coming back online after receiving 50 queued messages sends a handful of range receipts, not 50.

Storage: high-watermark, not a row per message

Per conversation, per participant, the server keeps:
    delivered_up_to_seq : 4830     (advanced when a delivery receipt arrives)
    read_up_to_seq      : 4825     (advanced when a read receipt arrives)

Two integers per (conversation, participant) — not one status row per (message, participant). The sender's "Message info" screen for a 1:1 chat is then a trivial read of those two watermarks. This also means receipts are idempotent and monotonic: a receipt that would move a watermark backwards (out-of-order delivery, duplicate) is simply ignored.

Multi-device: when is a message "delivered" / "read"?

Delivered = it reached any one of the recipient's devices (first device to receive it emits the delivery receipt; the others are silent). Read = read on any one device — and that read state then syncs to the reader's own other devices too, so reading on your phone clears the unread badge on your desktop. That cross-device sync is the same read-receipt frame, just fanned out to the reader's own device set (the "registry is a set, not a scalar" point from Deep Dive 3) instead of only back to the sender.

Groups: the receipt fan-in problem

In an N-member group, every recipient emits a delivery receipt and (eventually) a read receipt for every message. Routed naively, one message into a 512-person group generates up to ~1022 receipt frames converging on the sender. Mitigations, roughly in order of importance:

  • Receipts go only to the original sender, never fanned out to the whole group — other members don't need to know that Carol received Alice's message.
  • The sender's client only needs counts for the "Message info" screen ("Delivered to 340, read by 210"), not per-member state in the timeline — so the sender's gateway can aggregate incoming receipts into counters and push the sender periodic summary updates rather than 1022 individual events.
  • Recipients batch aggressively — coalesced range receipts as above, plus a short delay so one receipt covers a burst of messages.
  • Above a group-size threshold, per-message delivered/read tracking is dropped entirely — the "Message info" screen just isn't offered for very large groups, which removes the fan-in cost at the source.

Privacy gating — same reciprocal rule as last seen

The "Read receipts" toggle is mutual: turn it off and you stop sending blue ticks and stop seeing others' blue ticks. So the read path checks both parties' settings before rendering blue, exactly like the last-seen reciprocity check in Deep Dive 5. Two carve-outs: delivery receipts (✓✓ grey) can never be disabled, and read receipts in groups always apply regardless of the toggle (and only surface on the Message-info screen).

The presence & typing channel: ephemeral, never persisted, never queued

"online", "last seen…", and "typing…" travel as presence frames (available / unavailable / composing / paused). This channel is deliberately the opposite of the message channel in every way:

Message / receiptPresence / typing
DurabilityPersist-first, alwaysNever written to disk — pure in-memory routing
If recipient offlineQueued, delivered on syncDropped silently — a "typing" event has no meaning 5 minutes later
Fan-out scopeAll conversation members / senderOnly clients that have declared "I have this chat open right now" (subscribe on chat-open, unsubscribe on navigate-away)
Cleanup on socket dropRegistry entry TTLs out; last-seen writtenNothing to clean — subscribers apply a client-side ~10 s TTL so a lost paused can't leave "typing…" stuck forever

The routing mechanism is still the v3 pub/sub bus — a presence event for Bob is published to the gateways holding sockets for users currently subscribed to Bob's presence, and pushed down only those sockets. The scoping (only people looking at the chat) is what stops a business account with 100k contacts from triggering a 100k-way fan-out every time it connects, the trap called out in Deep Dive 5.

Q: What other edge cases are worth raising unprompted?

Read receipts arriving before delivery receipts

Bob's phone was offline, syncs 50 messages at once, and his client marks the last one "read" as soon as he opens the chat — before the server has even finished processing "delivered" state for message #12 of 50.

Answer: Treat read-state as a high-water mark, not a per-message flag needing sequential confirmation. "Read up to seq N" implies delivered-up-to-N as well — the server can infer and backfill delivered status for anything at or before the read cursor rather than requiring each intermediate delivered-ack individually.

Message sent to a group member who left the group mid-flight

Fan-out job reads the member list at T0, starts pushing; a member leaves at T0+2s, fan-out job (using a slightly stale cached member list) still tries to deliver to them.

Answer: Not a correctness bug worth over-engineering — worst case, a departed member's client receives one extra message for a group they just left, and the client-side UI simply won't render messages for groups it's not currently a member of. Consistency here can be eventual; trying to make group-membership-at-fan-out-time perfectly atomic with group-membership-changes is solving a problem users never notice.

Clock skew across devices for message ordering

Alice's phone clock is 3 minutes fast. If ordering relied on client-reported timestamps, her messages would appear to arrive "from the future" relative to everyone else.

Answer: This is exactly why Decision 1 uses server-assigned sequence numbers, not client timestamps, as the authoritative order. Client timestamps are stored for display purposes only ("sent at 3:42 PM") — they never drive ordering or sync logic.

Sending a message to someone who blocked you

Should the message be accepted and silently dropped, or should the sender get an error?

Answer: Accept and silently no-op on the delivery side (return a normal "sent ✓" to the blocker's blockee) — this is a deliberate product/privacy decision common to messaging apps: revealing "message not delivered because you were blocked" leaks the block itself, which defeats the purpose of blocking. Worth naming explicitly since it's a case where the "correct" engineering answer is shaped by a product/privacy requirement, not a technical constraint.

Thundering herd on reconnect after a regional outage

A data center blip drops millions of WebSocket connections simultaneously. All clients try to reconnect + sync at once.

Answer: Client-side reconnect with jittered exponential backoff (never all-at-once retry), and gateway-side connection-accept rate limiting per instance with graceful shedding (reject-with-retry-after rather than accept-and-fall-over). The sync-fetch itself should be paginated/bounded per request so a client with weeks of backlog doesn't send one giant query that stalls a database connection.

Same user, message ordering across multiple devices sending simultaneously

Alice replies from her phone and, a second later without realizing, also replies from her laptop — both in the same conversation.

Answer: Both are just two independent messages competing for sequence numbers in the same conversation, resolved by whichever hits the single-writer sequencer for that conversation first (Decision 1's "Great" tier). No special-casing needed — "same user, different device" isn't semantically different from "two different users" at the ordering layer.

Q: How would this be graded across levels?

What follows is not "what's the minimum to pass" — it's what a strong candidate should be volunteering unprompted at each level, specifically for a messaging system.

Mid-level

  • Proposes WebSockets over polling with a basic justification (persistent connection, server push)
  • Identifies that messages need to be stored in a database, not just relayed in-memory
  • Recognizes offline users need some handling, even if the first instinct is "retry queue" rather than "persist-first"
  • Can sketch a basic client/server/database diagram for 1:1 messaging
  • Needs prompting to think about what happens with more than one server

Senior

  • Proactively identifies that sender and receiver may be on different connection servers and proposes a routing mechanism without being asked
  • Distinguishes at-least-once delivery + client dedup from (impossible) exactly-once delivery, unprompted
  • Designs the sync-on-reconnect mechanism with a client-side cursor, recognizing it as the actual offline-handling story rather than a bolted-on retry service
  • Understands group messaging needs async fan-out, not synchronous N writes on the send path
  • Can discuss Redis vs Kafka trade-offs for the pub/sub layer with at least a surface justification
  • Distinguishes WhatsApp's own WebSocket from the OS push channel (APNs/FCM), and knows a background/killed app is reached by a push that wakes it to sync — not by content in the push payload

Staff+

  • Frames the entire system around one invariant stated early and never violated: durability happens unconditionally before any delivery attempt — and shows how this single invariant is what makes offline handling, gateway crashes, and stale registry entries all "non-events" instead of special cases requiring separate subsystems
  • Explicitly separates causal ordering per conversation from global ordering, and explains why global ordering is neither achievable nor necessary — showing awareness of what guarantee is actually being sold to the user
  • Treats the connection registry as a cache/hint that must be safe-by-design even when stale, rather than something requiring perfect consistency — and names the specific mechanism (verify-on-push-failure) that makes staleness a latency problem, not a correctness problem
  • Reasons about multi-device as "the registry maps to a set, not a scalar" rather than treating it as an afterthought bolted on at the end
  • Can articulate precisely which layer needs to be durable (message store) vs. which layer can be best-effort/lossy (the real-time push bus) and why conflating the two either wastes infrastructure cost or creates false confidence
  • Proactively raises the group fan-out cost curve and proposes the push/pull hybrid threshold for large groups without being asked "what about a 1000-person group"
  • Discusses partition/topic design trade-offs for the pub/sub layer at the operational level (rebalancing on gateway autoscale events), not just "we use Kafka"
  • Separates the control plane from the message path — group/profile edits as iq RPCs and notification fan-out over the same socket, with media on a separate encrypted HTTPS blob service and signup on stateless REST — rather than assuming one pipe carries everything
